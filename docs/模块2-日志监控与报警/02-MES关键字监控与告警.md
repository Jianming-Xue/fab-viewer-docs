# MES 日志关键字监控 · 运行时实现规格

> 模块 2 · 日志监控与报警 ｜ 功能 1 ｜ 状态：**定版**
> 本篇定义运行时：Oracle 表与 OS 索引 / ISM 的字段、定时扫描窗口、轮次锁、每轮业务（一轮 8 步）。规则怎么配见 [`01-MES关键字监控配置.md`](01-MES关键字监控配置.md)，报警怎么展示与处置见 [`05-MES关键字告警展示.md`](05-MES关键字告警展示.md)。

## 1. Oracle 表

### 1.1 状态表 `FvLogMonitorAlarmState`

每条 issue 一行。框架 `ID` 作 PK，业务键 `LineId + Item` 作复合 UK。

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `ID` | VARCHAR2(50) | ✅ | 框架统一赋值，不出参 |
| `LineId` | VARCHAR2(128) | ✅ | 命中行 `_id` 原值（5 段，约 55~65 字符），128 留余量 |
| `Item` | VARCHAR2(30) | ✅ | 规则业务键；同一行被多条规则命中各存一行 |
| `Environment` | VARCHAR2(30) | ✅ | 取自规则表（`PROD` / `PIRUN`） |
| `Priority` | VARCHAR2(20) | ✅ | 取自规则表，`P1` ~ `P4` |
| `RuleName` | VARCHAR2(128) | — | 块 `RULENAME` 首值快照 |
| `IssueTime` | TIMESTAMP(3) | ✅ | 命中行 `LOG_TIME` |
| `ReportTime` | TIMESTAMP(3) | ✅ | 生成墙钟，首写后不变 |
| `ResolvedTime` | TIMESTAMP(3) | — | 处置时写；是否为空派生「已解决」 |
| `ResolvedUser` | VARCHAR2(64) | — | 处置人 |
| `ResolvedComment` | VARCHAR2(512) | — | 处置备注 |
| `Alarmed` | CHAR(1) | ✅ | 默认 `N`；通知器回写 `Y` |
| `LastAlarmTime` | TIMESTAMP(3) | — | 通知发出的时间，非生成时间 |

- 审计列 `createdAt` / `createdBy` / `updatedAt` / `updatedBy` 由底层统一补，不在此列。
- 辅助索引：`(Environment, Item, ReportTime DESC)` 服务汇总分组 + 明细分页；`(Alarmed, LastAlarmTime)` 服务通知器捞未发。

### 1.2 块进度表 `FvLogMonitorBlockScan`

每块一行，`BlockId` 作 UK。

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `ID` | VARCHAR2(50) | ✅ | 框架统一赋值 |
| `BlockId` | VARCHAR2(256) | ✅ | 块文档 `_id`（`REQUEST_EXEC_ID`），UK |
| `LastScannedLineId` | VARCHAR2(128) | ✅ | 上次扫到的末行身份串；末段 17 位是 `LOG_TIME` 毫秒串 |
| `TerminalFlag` | CHAR(1) | ✅ | 默认 `N`；**正常闭合且扫完置 `Y`**，进行中 / 超时封口维持 `N`（§6.5） |
| `LastScanTime` | TIMESTAMP(3) | ✅ | 服务墙钟，**只在写入 / Flag 变更 / 块重开时刷新，每轮复查不刷**；清理判据（§6.5） |

> 轮次表 `Turn` 是复用的框架表，不在此列；预置数据与每轮锁 SQL 见 §5。

- `LastScannedLineId` 是**业务进度**（扫到哪行）、`LastScanTime` 是**墙钟寿命**（活了多久），两条时间线互不替代；前者只在「结果写入 + 状态行 INSERT 都成功」之后推进（先写事实、后推进度），写超了会跳过未扫的行且静默漏报。

## 2. OS 索引模板 · 结果索引 `mes-log-monitor-issue`

**结论：只新增一个索引模板，不放进现有行 / 块索引；`dynamic: strict`；文档 `_id` = `LineId|Item`（本功能），不算字段；多存一个 `issueType` 字段，本功能恒为 `Keyword`，留给 Server hang monitor 复用同一份索引。**

### 2.1 命名与写入

| 项 | 口径 |
|---|---|
| 索引名 | `mes-log-monitor-issue-{yyyy.MM}` —— **不带环境段**，**按月**一个，与块索引同粒度 |
| 环境区分 | 由**框架 `prefix` 配置**前置在同一索引名上区分，**不按 `ENV` 拼**：`PRD` / `PIRUN` 默认都算 **Production**、索引名相同；本文各表写的是去掉 `prefix` 后的**基名** |
| 选索引 | 按 **`issueTime` 所属月份**选，不按生成墙钟 —— 崩溃重扫跨月时同一 issue 仍落同一索引，幂等才稳 |
| 读别名 | `mes-log-monitor-issue-read`，写在模板里，新索引一建自带 |
| 写别名 | **不设**；写入直接指定月索引名（`09` §一 / `04` §5.2.1） |
| 模板名 / PUT 路径 | `mes-log-monitor-issue` / `_index_template/mes-log-monitor-issue` |
| `index_patterns` | `mes-log-monitor-issue-*`；`priority` 200 |

> **`prefix` 的作用面**：索引名、读别名 `mes-log-monitor-issue-read`、模板 `index_patterns`、ISM 的 `ism_template` 都由框架 `prefix` 前置**同一前缀**（四者要一致，否则别名读不到、ISM 也挂不上）；本服务**不读 `ENV` 决定索引名**、不自己拼环境段。

> **`_id` 的幂等只在同一个索引内生效**，按月选索引必须按 `issueTime`，不能按扫描时刻 —— 这是本节最要紧的一条。

### 2.2 settings

| 项 | 值 | 说明 |
|---|---|---|
| `number_of_shards` | 1 | 与 `12-template-exec.json` 一致，起步值，压测后回填 `09` §六 |
| `number_of_replicas` | 1 | 同上 |
| `refresh_interval` | 5s | 同上 |
| `index.codec` | best_compression | 同上 |
| `policy_id` setting | **不写** | `plugins.index_state_management.policy_id` 已弃用，写进 3.x 可能被 unknown setting 拒掉（`09` §一） |

### 2.3 mapping 字段（共 4 个）

| 字段 | 类型 | 取自 | 用途 |
|---|---|---|---|
| `issueMessage` | text | 命中行 `LOG_BODY` | 问题日志原文，唯一分词字段 |
| `blockId` | keyword | 块 `_id`（`REQUEST_EXEC_ID`） | 查询时回块取业务字段的锚点 |
| `issueTime` | date（`yyyy/MM/dd HH:mm:ss.SSS\|\|epoch_millis`） | 命中行 `LOG_TIME` | 选索引、按时间检索、ISM 排序 |
| `issueType` | keyword | 写入时给定；**本功能恒写 `Keyword`** | 区分 issue 来源 —— 同一份索引后续也收 Server hang monitor 写的其他类型 |

- 文档 `_id` **按功能各自拼接**，兼作对外 `issueId`；**文档内不冗余存**，`05` 出参由 `_id` 映射：**本功能恒为 `LineId|Item`**（同一条日志行可被多条规则各自命中，不带 `Item` 会互相覆盖）；**Server hang monitor 用 `LineId|issueType`**（该功能自己保证这个组合唯一）。
- `issueType` 是**写死的入参**，不是从日志里解析出来的：本功能在 `10` 的写入处固定传 `Keyword`，不读配置、不按规则变。
- `dynamic: strict` 硬约束：写进任何表外字段整篇拒写；后续加字段必须同时改本模板与 `10` 写入代码。
- date 格式沿用行 / 块模板，因为 `issueTime` 直接取行文档的 `LOG_TIME`。

### 2.4 不存的字段

| 不存 | 从哪来 |
|---|---|
| `item` / `environment` / `priority` / `ruleName` | Oracle 状态行（`ruleName` 是扫描时快照，purge 后仍能显示） |
| `lotId` / `tId` / `hostIpAddress` | 按 `blockId` 回**块文档**取 `LOTID` / `TID` / `HOSTIP` |
| `ruleMessage` | 块文档**没有**该字段（`04` §5.3.2）⇒ 按块的 `START_LINE_ID` **再回行索引**取首行 `LOG_BODY`，两步 |
| `lineId` / `startLineId` / `logFile` / `logOffset` | Oracle `LineId` 列、`_id` 拆分、块文档、行文档分别回查，不冗余 |
| 多值原文 `ruleNames` / `lotIds` / `tIds` | 块文档本来就是 keyword 数组，要原文直接读块 |

**结论：不新建 Policy，`mes-log-exec-keep` 的 `ism_template` 扩一条匹配结果索引即可；策略靠 `ism_template` 匹配索引模式自动挂，装入顺序先 Policy 后模板。**

### 3.1 Policy 定义

| 项 | 口径 |
|---|---|
| Policy 名 | `mes-log-exec-keep`（现成，改后 `PUT _plugins/_ism/policies/mes-log-exec-keep` 幂等覆盖） |
| `default_state` | hot |

| `ism_template` | 两条：`mes-log-exec-*`（原有一条）+ `mes-log-monitor-issue-*`（**本次新增**），`priority` 均 100 |

### 3.2 时间分层

| 索引 | hot | warm | cold | 到期 |
|---|---|---|---|---|
| 行 `mes-log-line-*` | 0 ~ 30 天 | 30 天起：只读 + 副本 1 + force merge 单段 | 180 天起 | **360 天删除** |
| 块 `mes-log-exec-*` | 0 ~ 360 天 | — | 360 天起：只读，**不删** | 归档保留 |
| 结果 `mes-log-monitor-issue-*`（本次） | 0 ~ 360 天 | — | 360 天起：只读，**不删** | 归档保留 |

- **已确认（2026-11-16）：沿用现行 360 天**，不改数字、不动 `04` §5.2.5 / `09` §二 / `deploy` 的分档；`30 天` 只是行索引热转温门槛与界面查询下限。
- 冷阶段 `read_only` 对结果索引无害：按月建，360 天前的月索引不会再被写（写入按 `issueTime` 选月）。
- 三处保留期的关系：结果索引与块索引同步归档、都不删；Oracle 长期保留；唯一会丢的是**行索引原文**（360 天），影响面只有 `ruleMessage` 与 `Alarm Log` 下载，降级口径见 `04` §1322。

## 4. 运行逻辑 · 定时扫描（新建块滑动窗口）

**一句话**：每 3 分钟醒一轮，用块索引 `@timestamp` 划一个滑动窗口，只捞「窗口内新建的块」作为本轮待扫清单；游标落在轮次表 `Turn` 的 `Name = MONITOR` 行，**执行成功才往前推**。因为下一轮起点就是上一轮终点，整条链不重不漏。

### 4.1 口径

| 项 | 口径 |
|---|---|
| 窗口依据 | **块索引 `@timestamp`** = 派生服务首次建块那一刻的系统当前时刻。不是行索引 `@timestamp`（采集摄入时刻），也不是 `LOG_TIME` / `START_TIME` |
| 回答什么 | 只回答「最近新建了哪些块」；**不回答**哪些块被重放 / 闭口 / 解封过 |
| 谁用 | 派生服务之外的消费方（告警、看板、外部同步），派生服务自己不回查；本功能是其中一路 |
| 游标落点 | 轮次表 `Turn`，`Name = MONITOR` 那一行，一轮一行 |
| 窗口产出 | 本轮新建块清单 → 逐块扫行的进度记 §1.2 `FvLogMonitorBlockScan`，命中结果写 §1.1 状态表与 §2 结果索引。**本章只定「什么时候扫、扫多宽」**，判定与逐块业务见 §6 |
| 与结果索引的关系 | 结果索引按 `issueTime`（命中行 `LOG_TIME`）选月（§2.1）；本窗口按 `@timestamp` 选块。两条时间线互不替代 |

### 4.2 参数

| 中文名 | 取值 | 说明 |
|---|---|---|
| 定时器间隔 | **3 分钟** | 触发点 10:00、10:03、10:06…… |
| 初始回看宽度 | **1 分钟** | 只在第一轮冷启动、或游标丢失时用一次 |
| 索引刷新间隔 | **5 秒** | 模板现值，现场可调 |
| 右端回退量 | **10 秒** | 5 秒刷新 + 写入在途 + 各节点时钟偏差余量 |
| 单轮扫描上限 | **6 分钟** | 一轮最多吃两个定时器间隔的量；也是切追赶档的阈值 |
| 追赶上限 | **18 分钟** | 按实测处理速度反解的硬顶，不是拍脑袋放大 |

**为什么右端要回退 10 秒**：块写进 OpenSearch 返回成功不等于马上能查到，还要等下一次索引刷新。每轮先把触发时刻往回退 10 秒得到「可见水位」，窗口只查到这里。回退量跟着索引刷新间隔一起调；调大只是整条时间链往后平移，**不改变每轮扫多宽、也不改变几轮能追平**。

### 4.3 每轮怎么做

**每轮先按 §5 抢 `Name = 'MONITOR'` 的行锁，整轮扫描在锁内**；抢不到就整轮跳过，游标不动。

1. 触发时刻 − 10 秒 = **本轮可见水位**。
2. **游标** = 上一轮成功执行后推到的位置，读轮次表 `Turn` 的 `Name = MONITOR` 行；第一轮 / 游标丢失取「可见水位 − 1 分钟」。
3. 本轮窗口 = **[游标, 右端)**，含游标那一刻、不含右端那一刻；右端按 §4.4 两档算，超上限就截在「游标 + 上限」。
4. **积压** = 可见水位 − 游标，每轮触发时先算一次。
5. 执行成功，把 `MONITOR` 行的游标推到**本轮实际截到的右端**；本轮被跳过、或执行失败，游标一律不动。

```
每 3 分钟触发（10:00 / 10:03 / 10:06 …）:
    可见水位 = now − 10s
    游标     = Turn[Name='MONITOR'].游标
               或 可见水位 − 1min        # 首轮 / 游标丢失
    积压     = 可见水位 − 游标
    上限     = 6min                      # 常态档：积压 ≤ 6min
               或 min(积压, 18min)       # 追赶档：积压 > 6min
    右端     = min(可见水位, 游标 + 上限) # 本轮实际截到的右端
    窗口     = [游标, 右端)              # 含前不含后
    查 mes-log-exec-read：@timestamp ∈ 窗口
    成功     → Turn[Name='MONITOR'].游标 = 右端
    跳过/失败 → 游标不动
```

数据不是丢了，是堆在区间里等下一轮。

### 4.4 两档

| | 什么时候用 | 本轮扫多宽 |
|---|---|---|
| **常态档** | 积压 ≤ 6 分钟 | 最多 6 分钟（即 [游标, 可见水位)） |
| **追赶档** | 积压 > 6 分钟（常态一轮吃不下） | 放宽到**刚好等于积压**，最多不超过 18 分钟 |

追赶档一轮把积压清零，下一轮自动回常态档。**放宽的只有「单轮扫描上限」这一项**：游标、10 秒回退、含前不含后、成功才推游标，全都不变。

### 4.5 必须守住

1. **游标只在成功后推**，且推的是实际截到的右端，不能推可见水位 —— 否则被上限截掉的那一段会永久漏。
2. **18 分钟硬顶不能破**：积压真比它还大就分几轮吃，每轮最多 18 分钟；破了就回到「越积越多」的老问题。
3. **追赶轮自己可能超时**：一次扫 15 分钟数据可能跑过 3 分钟，把下一轮挤掉。但此时游标已经推到位，再下一轮积压只有 6 分钟，常态档一轮就能吃完 —— 连锁跳一次就收敛。
4. **已知盲区**：重放兜底 `doc_as_upsert` 补建的块没有 `@timestamp`，永远进不了这个窗口。**本版口径：不算「新建块」**；要覆盖得另按业务时间走一条路（与第 5 条同一条）。
5. **跨月**：块按月索引、按块首行日志时间归档，而 `@timestamp` 是系统时刻。在线常态两者同月，查当月索引即可；回采历史日志时会错月，那批单独按业务时间另走一条路。

### 4.6 验证过的行为

触发点 10:00 ~ 10:30，其中第 3、4、5、6、9 轮跳过：

- **只有常态档**：跳 4 轮后积压最高涨到 15 分钟，10:30 时还剩 3 分钟没追平，要等 10:33 那一轮才清零。
- **加了追赶档**：10:18 那一轮一次扫 15 分钟直接追平，之后全程常态档，**10:30 就完全无积压**，全局只触发 1 次追赶。
- 隔一轮跳一轮时，常态档每轮净追 0、积压原地不动；连续跳两轮以上，积压反而越涨越多 ⇒「几轮能追平」没有固定答案，**跳轮不停就永远追不平**，追赶档就是为这个准备的。

## 5. 轮次表 · 预置数据、启动校验与每轮锁 SQL

**结论**：轮次表 `Turn` 复用现成框架表，**不改表结构；`Name = 'MONITOR'` 这一行由初始化脚本 / 运维预置，服务启动不写、只校验（§5.2）**；每轮用 `SELECT … FOR UPDATE SKIP LOCKED` 抢这一行的行锁，整轮扫描与游标推进在同一个事务里，成功才 `COMMIT`。

### 5.1 本模块用到的列

| 列 | 类型 | 说明 |
|---|---|---|
| `Name` | VARCHAR2(30) | **唯一索引**，业务定位键。本模块固定 `MONITOR`；与别的定时任务各占一行、各一把独立行锁，互不阻塞 |
| `CursorTs` | TIMESTAMP(3) | 时间窗口游标 = 上一轮成功时**实际截到的右端**；初始 `NULL` ⇒ 走 §4.3 第 2 步的冷启动回看 |
| `Owner` | VARCHAR2(64) | 抢到本轮的节点，诊断用 |
| `StartedAt` | TIMESTAMP(3) | 本轮触发时刻，诊断用 |

> 列名为本模块口径；现场轮次表若已有等价列，直接复用、SQL 里的列名按现场对齐，**口径不变**。`MONITOR` 共 7 字符，按现成表实际列宽即可装下。`ID` 等技术主键由自增 / 框架补。

### 5.2 启动前置 · 预置数据与校验

`Name = 'MONITOR'` 这一行由**初始化脚本 / 运维预置**，服务启动**不写轮次表**。初始化脚本只需给下面两个栏位赋值（部署时一次）：

| 栏位 | 值 |
|---|---|
| `Name` | `MONITOR` |
| `CursorTs` | `NULL` |

预置只管这两列；服务启动与运行期的口径：

| 项 | 口径 |
|---|---|
| 谁写 | 初始化脚本 / 运维；服务启动**一行都不写** —— 不补行、不覆盖已有游标 |
| 启动校验 | 只读检查 `MONITOR` 行存在且可读（连不上 / 查不动一并算失败） |
| 有问题 | **直接启动失败并报错**，不降级、不静默跳过、不自动补 |
| 为什么 | `SKIP LOCKED` 返回 0 行的语义是「别人在跑」；行一旦缺失会伪装成「每轮都被跳过」⇒ 静默全停，必须在启动阶段挡住 |
| `CursorTs` | 留 `NULL` 是刻意的：第一轮（或游标丢失）按 §4.3 第 2 步取「可见水位 − 1 分钟」，**只回看一次** |
| 多实例 | 每台启动各自校验、都不写；行由部署阶段一次性预置 |

- 业务规则仍由 `01` 配置页维护，服务不预置；启动只把轮次行当**前置条件**校验，不把它当运行期脏数据来修。

### 5.3 每轮执行的 SQL

```sql
-- ① 抢轮次：本轮第一条语句，跨机互斥
SELECT Name, CursorTs
  FROM Turn
 WHERE Name = 'MONITOR'
   FOR UPDATE SKIP LOCKED;      -- 必须带 SKIP LOCKED
```

- 返回 **1 行** = 抢到，行锁从这条 `SELECT` 一直持到 `COMMIT`；返回 **0 行** = 别人在跑，**本轮事务直接结束**（还没做任何改动，提交与回滚等价）。
- **为什么必须 `SKIP LOCKED`**：不带 SKIP，后醒的节点会阻塞在行锁上排队，锁一释放接着跑第二遍 —— 周期漂移、同一刻度重复执行；带 SKIP 才是「被占用就跳过、不排队、不补跑」。
- 不引 Redis / 分布式锁：进程崩了事务回滚、行锁自动释放，不需要租约与接管。

```sql
-- ② 抢到后登记本轮归属（同一事务，失败随 ROLLBACK 一起回滚）
UPDATE Turn SET Owner = :nodeId, StartedAt = :fireAt
 WHERE Name = 'MONITOR';

-- ③ 整轮扫描成功后，推游标到「本轮实际截到的右端」，同一事务 COMMIT
UPDATE Turn SET CursorTs = :rightTs
 WHERE Name = 'MONITOR';
COMMIT;
```

- ②③ 之间就是 **§6 的一轮 8 步**：读配置 → 按窗口查块清单 → 定候选块 → 判块 → 回行取数 → 判行落表与清理（窗口宽度见 §4.3），落 §1.1 状态表 + §2 结果索引 + §1.2 块进度表。
- 跳过 / 失败：`ROLLBACK`，**游标一律不动**（§4.5 第 1 条）；数据不丢，堆在区间里等下一轮。
- **推的是 `:rightTs`（实际截到的右端），不是可见水位** —— 被 6 / 18 分钟上限截掉的那一段，推可见水位会永久漏。

### 5.4 锁的边界

| 项 | 口径 |
|---|---|
| 事务范围 | 只包本轮扫描与游标推进；通知发送等外部 IO 全在 `COMMIT` 之后、锁外 |
| 串行语义 | 不排队、不补跑；上一轮没结束，下一个 3 分钟刻度整轮跳过 |
| 同机防重入 | cron 固定速率触发，上一轮没完下次照样来 ⇒ 进程内「正在跑就跳过本次触发」标记 |
| 一轮跑过 3 分钟 | 持锁跨过下一个刻度，那个刻度被跳过；游标已推到位，收敛见 §4.5 第 3 条 |
| 崩溃 | Oracle 行锁随事务回滚自动释放，下一轮别的节点直接接管，无主备切换 |
| 相位固定节点 | 可能长期抢不到轮次，不报错、不影响正确性；排查时先看这一处 |

## 6. 每轮业务 · 从块清单到 issue

**一句话**：本章只写 §4 / §5 没写的部分 —— 抢到 `MONITOR` 行锁（§5.3 ①）之后、推游标 `COMMIT`（③）之前，一轮 8 步。窗口怎么算（§4.2 ~ §4.4）、抢锁与失败回滚（§5.3）、锁外通知（§5.4）一律引用，不重复。

### 6.1 一轮 8 步

| 步 | 做什么 | 打在哪 | 口径 |
|---|---|---|---|
| 1 | 抢 `MONITOR` 行锁；抢不到整轮跳过、游标不动 | Oracle | **已写** §5.3 ① / §4.3 |
| 2 | **读配置**：每轮重读规则表 + 通知表（**只取 `Enabled = true` 的规则**），`Environment` 去重成集合；System Misc 名单在**服务启动时**另读一次 | Oracle + System Misc | §6.2 |
| 3 | **查块清单**：按 §4.3 窗口查 `mes-log-exec-read`，**配置只嵌 `terms ENV`**；再按启动时名单排除 ServerCategory | 块索引 | §6.2 |
| 4 | **定候选块**：第一波 = 3 的全量清单；第二波起 = `(Flag='N' ∪ 窗口新块) − 已闭合块` | 进度表 + 块索引 | §6.3 |
| 5 | **逐块判块**：过 5 项检查 1~3；块分已闭合 / 未闭合（含超时封口）两种 | 块文档 | §6.4 |
| 6 | **回行取数**：按块把该块的行日志取回来，再按 `LastScannedLineId` 截掉已扫过的部分 | 行索引 | §6.4 |
| 7 | **判行 + 落表**：过关键字 / 排除词 → 记 issue list；每块写 Block Scan；清理老行 | 两源 + 进度表 | §6.5 |
| 8 | 推游标到实际右端、`COMMIT`；通知器 / SSE 锁外 | Oracle | **已写** §4.3 第 5 条 / §5.3 ③ / §5.4 |

> 第 1、8 步只作定位用，正文从 2 写到 7。

### 6.2 第 2、3 步 · 读配置与查块清单

**第 2 步（新加）**

| 项 | 口径 |
|---|---|
| 时点 | 抢到行锁**之后**、算窗口**之前**，一轮读一次；一轮之内不会有两个实例各按不同版本跑 |
| 读什么 | `FvLogMonitorCfg` **只取 `Enabled = true` 的行**（字段 `Environment` / `Item` / `Keyword` / `ExcludeKeywords` / `FollowRuleNames` / `ExcludeRuleNames` / `Priority` / `Enabled`）+ `FvAlarmCfg` 按 `AlarmCfgId` 关联 |
| 分组 | `Environment` 去重成集合；**一行 = 一条规则 = 一个关键字**，`Item + Environment` 唯一 |
| 生效 | 不缓存、不热加载；删改**与启停**都**下一轮生效**，本轮读到的版本跑到底 |
| 通知配置 | 本轮只读不用，`NotifyInterval` 与渠道由通知器在 `COMMIT` 后独立驱动（§5.4） |

- **只有 `Enabled = true` 的规则进本轮** —— 有行不等于生效；停用规则不参与检查、不进环境集合（启停口径见 `01` §4.1-7）。三个名单是 JSON 数组，未配存 `NULL` ⇒ 该项检查跳过。
- 环境值域以 Misc `mes.global.environments` 为准，与 Filebeat `fields.ENV` 大写值不齐会全落空**且不报错** ⇒ 启动时打印读到的环境集合。

**启动时读一次 · ServerCategory 排除名单（新加）**

| 项 | 口径 |
|---|---|
| 来源 | System Misc（模块 5 `FvMisc`），配置项 `Log.Monitor.ServerCategory` |
| 时点 | **服务启动时读一次**，调用公共方法；**不随轮次重读** —— 与上面第 2 步「抢锁后每轮全量重读规则表」是两回事 |
| 形态 | 一个 **Json List**；**公共方法返回什么就原样记下什么** —— 服务侧不解析、不校验、不转换、不补默认值，也不管空值与回落 |
| 用途 | **排除**：第 3 步按窗口取回块清单后，把 `SERVER_CATEGORY` 落在这份名单里的块挡掉，**不作为本轮窗口新块**进第 4 步候选 |
| 生效 | 启动时定死；改这项配置要**重启服务**才生效（规则表是下一轮生效，别混） |

- **只挡新来的**：名单只对第 3 步的**窗口新块**生效；第 4 步由 Block Scan `Flag='N'` 带回的历史块不按这份名单排除，照常进候选续扫。

**第 3 步（增强）**：按 §4.3 算出的 `[游标, 右端)` 查块索引 `mes-log-exec-read`，**配置只嵌 `terms ENV`（本轮环境集合）**，没配规则的环境直接挡在查询外；查询实现细节不在本篇。`Keyword` 与两份 Rule Name 名单**不进这一步** —— 它们是行级 / 规则级判定，归第 5、7 步。**另按上面那份启动时名单，把 `SERVER_CATEGORY` 命中的块从清单里排除掉** —— 这是取回清单后的过滤，不改查询条件。清单必须取全（翻页翻到空），中途失败按 §5.3 整轮 `ROLLBACK`、游标不动。

### 6.3 第 4 步 · 两波的候选块

| | 第一波（冷启动） | 第二波起 |
|---|---|---|
| Block Scan 状态 | 空 | 已有 `N` / `Y` 行 |
| 候选块 | **没有并集**：3 查出的全量清单 | `(Flag='N' ∪ 本轮窗口新块) − 已闭合块` |

- 第二波的排除要对**窗口新块也做一遍**：先按 `BlockId` 查 Block Scan，命中且该块已闭合就丢掉。冷启动回看 1 分钟（§4.2）、游标丢失、重放都可能把已处理过的块重新带进窗口（§4.5 第 4 条），所以这个排除不能省。
- 写死就是：`待处理 = ( BlockScan[Flag='N'] ∪ 窗口新块 ) − BlockScan[Flag≠'N']`。
- `Y` 只给**正常闭合**的块（真终态）；重开的块本来就在 `Flag='N'` 集合里、每轮自然带回，不需要额外捞回逻辑。

### 6.4 第 5、6 步 · 逐块判块与回行取数

**第 5 步**：逐块过 5 项检查的 1~3（块阶段），再按 `EXEC_STATUS` 按状态分开处置：

| # | 检查项 | 打在哪 | 否决条件 |
|---|---|---|---|
| 1 | `Environment` | 块 `ENV` | 不在本轮环境集合内 |
| 2 | 关注 Rule Name | 块 `RULENAME` | 配了名单且不在名单内；**空值放行** |
| 3 | 排除 Rule Name | 块 `RULENAME` | 在名单内；空值不生效 |

| 块状态 | 本轮怎么处置 |
|---|---|
| **已闭合**（正常结束） | 排查完就完事，第 7 步标 `Y`，不再带回 |
| **未闭合 / 进行中** | 可能还有日志正在来的路上 ⇒ 第 7 步标 `N`，保留到下一轮 |
| **超时封口** | **同样标 `N`** —— 不等于真终态、可能重开 ⇒ 每轮带回观察，见 §6.5 |

- 一律区分大小写；`RULENAME` 空值放行、多值任一命中。

**第 6 步**：**按块把这块的行日志取回来** —— 给一个块，把它范围内的日志行捞回来、还原成块内顺序；取行逻辑不在本篇展开。告警服务在这一步只做一件增量动作：拿 §1.2 的 `LastScannedLineId` 截掉上次已扫过的部分，剩下的才是本轮要判的行。

### 6.5 第 7 步 · 判行、落表与清理

| 动作 | 口径 |
|---|---|
| 判行 | `LOG_BODY` 原文过 `Keyword`（检查 4）+ `ExcludeKeywords`（检查 5），区分大小写；**一命中行一条 issue**，`issueId = LineId\|Item`（`issueType` 恒写 `Keyword`） |
| 写两源 | OS 结果索引按 `_id` 幂等写（§2.3 四字段）+ Oracle 状态行按 UK 冲突跳过；**先写事实、后推进度**，同事务 |
| 写 Block Scan | **每块都写**：正常闭合 ⇒ `Y`；未闭合 / 超时封口 ⇒ `N`，保留到下一轮由第 4 步带回 |
| 刷 `LastScanTime` | 只在「本行写入 / Flag 变更 / 块重开」时刷；**每轮复查不刷** —— 否则 `now − LastScanTime` 永远不到阈值，封口块永远清不掉 |

**清理（阈值 = 轮数 × 3 分钟 Interval）**

| 行 | 阈值 | 含义 |
|---|---|---|
| `Y` | **10 轮 / 30 分钟** | 正常闭合块，留 10 轮给重开留个可认的记录 |
| `N` | **15 轮 / 45 分钟** | 超时封口的**观察期**：每轮带回，期间重开 / 来新日志就接着扫并续期；一直健康到 45 分钟即判定不会重开，直接删行 |

- 清理动作**每 30 分钟跑一次**（10 × Interval），两条 `DELETE` 按 `LastScanTime` 判；**不加自监控**。
- 窗口单调往前推（§4.3 游标推到实际右端），老块的 `@timestamp` 落到游标左边后不会再被第 3 步查出来 —— 但 Block Scan 是按块持久化的，行还在，所以清理不能省。
- `Y` 行清掉后该块若被窗口重新捞回，第 4 步查不到「已闭合」记录 ⇒ 当新块扫一遍；`issueId` 幂等（OS `_id` 覆盖 + Oracle UK 冲突跳过）不会重复落 issue，第 7 步按当前 `EXEC_STATUS` 又标回 `Y`。正确性不受影响，只多扫一次。
- 45 分钟后强清的 `N` 行，之后该块再来日志就没人扫了 —— 这是用阈值换掉自监控的已知代价；按 5 分钟超时封口的正常链路，`N` 行走不到 45 分钟，只在异常块上发生。
