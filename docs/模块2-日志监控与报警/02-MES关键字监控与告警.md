# MES 日志关键字监控 · 运行时实现规格

## 1. 功能定位

本篇是**关键字监控的运行时实现规格**：定时扫描日志、逐块判读命中行、落成 issue，供通知与展示消费。配置侧（扫什么、按什么等级、通知给谁）见 `01`；通知怎么发、发什么格式、发给谁见 `10`；报警怎么展示与处置见 `05`。本篇只定义运行时这套机制 —— Oracle 表、扫描窗口、轮次锁与每轮 8 步。

## 2. Oracle 表

**只放两张表** —— 告警态与扫描进度；不放结果文本与规则配置（结果文本在 OpenSearch 结果索引 §3；规则配置在 `01`）。

**分两张表**：

- **表一 `FvLogMonitorAlarmState`**（§2.1）—— 告警状态：每条 issue 一行，业务键 `LineId + Item` 作复合 UK；
- **表二 `FvLogMonitorBlockScan`**（§2.2）—— 块扫描进度：只存没扫完、下一轮还要接着扫的块，每块一行，`BlockId` 作业务 UK。

表名与栏位均大驼峰、全项目统一不加引号（不加引号的标识符 Oracle 会转成大写，写 `FvLogMonitorAlarmState` 与 `FVLOGMONITORALARMSTATE` 是同一张表）；两张表统一规范如下，长度 / 可空 / UK 见表内。

**两张表统一规范**：

- **主键 `ID`**：`VARCHAR2(≤50)`、非空；由框架底层赋值，业务侧一律按业务 UK 读写、不引用 `ID`（不出参）。
- **审计四字段** `CreatedAt` / `CreatedBy` / `UpdatedAt` / `UpdatedBy`：**由底层统一控制** —— 赋值、`UpdatedAt` / `UpdatedBy` 的刷新与可空性均由框架托管，业务侧不进任何 SQL。
- 列名大驼峰、不加引号（Oracle 自动转大写）；**业务时间列**统一 `TIMESTAMP(3)`（毫秒），与行索引 `@timestamp` 对齐（审计字段除外）；字符串长度按字符校验（避免 `VARCHAR2` 字节语义抛 `ORA-12899`）。

### 2.1 表一 · `FvLogMonitorAlarmState`（告警状态）

每条 issue 一行，业务键 `LineId + Item` 作复合 UK。

| 字段 | 列名 | 长度 | 可空 | 说明 |
|---|---|---|---|---|
| 主键 | `ID` | ≤50 | 否 | 底层赋值、业务不引用、不出参 |
| 命中行身份 | `LineId` | ≤128 | 否 | 命中行 `_id` 原值（5 段，约 55~65 字符），128 留余量 |
| 规则业务键 | `Item` | ≤30 | 否 | 同一行被多条规则命中各存一行；与 `LineId` 组成复合 UK |
| 环境 | `Environment` | ≤30 | 否 | 取自规则表（`PROD` / `PIRUN`） |
| 等级 | `Priority` | ≤20 | 否 | 取自规则表，`P1` ~ `P4` |
| 规则名快照 | `RuleName` | ≤128 | 是 | 块 `RULENAME` 首值快照 |
| 命中时刻 | `IssueTime` | TIMESTAMP(3) | 否 | 命中行 `LOG_TIME` |
| 生成时刻 | `ReportTime` | TIMESTAMP(3) | 否 | 生成墙钟，首写后不变 |
| 处置时刻 | `ResolvedTime` | TIMESTAMP(3) | 是 | 处置时写；是否为空派生「已解决」 |
| 处置人 | `ResolvedUser` | ≤64 | 是 | 处置人 |
| 处置备注 | `ResolvedComment` | ≤512 | 是 | 处置备注 |
| 是否已通知 | `Alarmed` | NUMBER(1) | 否 | 布尔、**由底层控制**：`1`（true）= 已发通知，非 `1` = 未发；通知发出后底层回写（见 `10`） |
| 最后通知时刻 | `LastAlarmTime` | TIMESTAMP(3) | 是 | 通知发出的时间，非生成时间（通知侧回写） |
| 审计四字段 | `CreatedAt`/`CreatedBy`/`UpdatedAt`/`UpdatedBy` | — | 见上 | 底层统一赋值 |

**业务唯一索引**：`LineId + Item`。**辅助索引**：`(Environment, Item, ReportTime DESC)` 服务汇总分组 + 明细分页；`(Alarmed, LastAlarmTime)` 通知侧捞未发。

### 2.2 表二 · `FvLogMonitorBlockScan`（块扫描进度）

**只存「没扫完、下一轮还要接着扫」的块**，每块一行，`BlockId` 作业务 UK。**没有终态标志**：表里出现即代表这块还没闭合；本轮结束时把已闭合的块直接删掉（§6.5），下一轮读进来就是「现存的未闭合块 + 本轮窗口新块」（§6.3）。

| 字段 | 列名 | 长度 | 可空 | 说明 |
|---|---|---|---|---|
| 主键 | `ID` | ≤50 | 否 | 底层赋值、业务不引用 |
| 块身份 | `BlockId` | ≤256 | 否 | **业务 UK**；块文档 `_id`（`REQUEST_EXEC_ID`） |
| 扫描进度 | `LastScannedLineId` | ≤128 | 否 | 上轮扫到的末行身份串；末段 17 位是 `LOG_TIME` 毫秒串 |
| 最后扫描时刻 | `LastScanTime` | TIMESTAMP(3) | 否 | 本轮扫它的墙钟，**未闭合块每轮结束都刷**；兜底强清判据（§6.5） |
| 审计四字段 | `CreatedAt`/`CreatedBy`/`UpdatedAt`/`UpdatedBy` | — | 见上 | 底层统一赋值、`UpdatedAt` 无条件刷新 |

**业务唯一索引**：`BlockId`。

- `LastScannedLineId` 是**业务进度**（扫到哪行）、`LastScanTime` 是**墙钟寿命**（活了多久），两条时间线互不替代；前者只在「结果写入 + 状态行 INSERT 都成功」之后推进（先写事实、后推进度），写超了会跳过未扫的行且静默漏报。
- **行数跟着未闭合块走、不随历史累积** —— 闭合即删，表自然保持很小；`LastScanTime` 只给派生层异常（块永远不闭口）的强清当判据。

> 轮次表 `FvTurn` 是复用的框架表，不在此列；预置数据与每轮锁 SQL 见 §5。

## 3. OS 结果索引 · 见 `09` §五

结果索引 `mes-log-monitor-issue-{yyyy.MM}`（基名，环境前缀由框架 `prefix` 加），按月切、永久归档不删、一个 issue 一条。**结论：只新增这一个模板，与 Server Hang 监控共用一份、靠 `issueType` 区分来源。**

**字段清单、类型、含义、`_id` 拼接与关键口径的唯一权威在 `09-OpenSearch索引模板.md` §五**（含完整 JSON 模板 + 4 字段表），可执行配置在 `deploy/opensearch/13-template-monitor-issue.json`。本文只列**本功能实际写入什么值**，字段定义不复述，避免两处维护漂移。

**本功能写入内容**（4 个 mapping 字段 + `_id`）：

| 字段 | 类型 | 本功能写入值 | 说明 |
|---|---|---|---|
| `issueMessage` | text | 命中行 `LOG_BODY` 原文 | 问题日志原文，唯一分词字段 |
| `blockId` | keyword | 本行所属块的 `_id`（`REQUEST_EXEC_ID`） | 查询时回块取业务字段的锚点 |
| `issueTime` | date | 命中行 `LOG_TIME` | 选索引依据 + 按时间检索 + ISM 排序 |
| `issueType` | keyword | **恒写 `Keyword`** | 写死入参，不读配置、不从日志解析 |
| `_id` | ES metadata，非 mapping 字段 | **`LineId\|Item`** | 兼作对外 `issueId`、文档内不冗余存（`05` 出参由 `_id` 映射）；同一行被多条规则命中各存一条，不带 `Item` 会互相覆盖 |

其余两条口径，照 `09` §五：

- **选索引与环境**：按 `issueTime` 所属月份选、不按扫描墙钟（`_id` 幂等只在同一索引内生效，跨月重扫须落同一索引才能去重）；环境由框架 `prefix` 前置区分；读走 `mes-log-monitor-issue-read`、不设写别名。
- **ISM 不另配**：共用 `mes-log-exec-keep`、靠 `ism_template` 匹配 `mes-log-monitor-issue-*` 自动挂，hot 0 ~ 360 天、360 天后 cold 只读不删；唯一改动是 `deploy/opensearch/02-ism-exec-keep.json` 的 `ism_template` 加第二条（`09` §二 / §五）。

## 4. 运行逻辑 · 定时扫描（新建块滑动窗口）

**一句话**：每 3 分钟醒一轮，用块索引 `@timestamp` 划一个滑动窗口，只捞「窗口内新建的块」作为本轮待扫清单；游标落在轮次表 `FvTurn` 的 `Name = MONITOR` 行，**执行成功才往前推**。因为下一轮起点就是上一轮终点，整条链不重不漏。

### 4.1 口径

| 项 | 口径 |
|---|---|
| 窗口依据 | **块索引 `@timestamp`** = 派生服务首次建块那一刻的系统当前时刻。不是行索引 `@timestamp`（采集摄入时刻），也不是 `LOG_TIME` / `START_TIME` |
| 回答什么 | 只回答「最近新建了哪些块」；**不回答**哪些块被重放 / 闭口 / 超时封口过 |
| 谁用 | 派生服务之外的消费方（告警、看板、外部同步），派生服务自己不回查；本功能是其中一路 |
| 游标落点 | 轮次表 `FvTurn`，`Name = MONITOR` 那一行，一轮一行 |
| 窗口产出 | 本轮新建块清单 → 未闭合块的扫行进度记 §2.2 `FvLogMonitorBlockScan`（闭合即删），命中结果写 §2.1 状态表与 §3 结果索引。**本章只定「什么时候扫、扫多宽」**，判定与逐块业务见 §6 |
| 与结果索引的关系 | 结果索引按 `issueTime`（命中行 `LOG_TIME`）选月（§3 / `09` §五）；本窗口按 `@timestamp` 选块。两条时间线互不替代 |

### 4.2 参数

窗口参数（定时器间隔 / 初始回看 / 索引刷新 / 右端回退 / 单轮扫描上限 / 追赶上限）统一见 §7「配置参数」。

**为什么右端要回退 10 秒**：块写进 OpenSearch 返回成功不等于马上能查到，还要等下一次索引刷新。每轮先把触发时刻往回退 10 秒得到「可见水位」，窗口只查到这里。回退量跟着索引刷新间隔一起调；调大只是整条时间链往后平移，**不改变每轮扫多宽、也不改变几轮能追平**。

### 4.3 每轮怎么做

**每轮先按 §5 抢 `Name = 'MONITOR'` 的行锁，整轮扫描在锁内**；抢不到就整轮跳过，游标不动。

1. 触发时刻 − 10 秒 = **本轮可见水位**。
2. **游标** = 上一轮成功执行后推到的位置，读轮次表 `FvTurn` 的 `Name = MONITOR` 行；第一轮 / 游标丢失取「可见水位 − 1 分钟」。
3. 本轮窗口 = **[游标, 右端)**，含游标那一刻、不含右端那一刻；右端按 §4.4 两档算，超上限就截在「游标 + 上限」。
4. **积压** = 可见水位 − 游标，每轮触发时先算一次。
5. 执行成功，把 `MONITOR` 行的游标推到**本轮窗口的右端**（`右端 = min(可见水位, 游标 + 上限)`）—— **这个值就是下一轮的游标**：本轮右端 `10:00:50`，下一轮起点就是 `10:00:50`。本轮被跳过、或执行失败，游标一律不动。

```
每 3 分钟触发（10:00 / 10:03 / 10:06 …）:
    可见水位 = now − 10s
    游标     = FvTurn[Name='MONITOR'].游标
               或 可见水位 − 1min        # 首轮 / 游标丢失
    积压     = 可见水位 − 游标
    上限     = 6min                      # 常态档：积压 ≤ 6min
               或 min(积压, 18min)       # 追赶档：积压 > 6min
    右端     = min(可见水位, 游标 + 上限) # 本轮窗口右端 = 下一轮的游标
    窗口     = [游标, 右端)              # 含前不含后
    查 mes-log-exec-read：@timestamp ∈ 窗口
    成功     → FvTurn[Name='MONITOR'].游标 = 右端    # 下一轮的起点
    跳过/失败 → 游标不动
```

数据不是丢了，是堆在区间里等下一轮。

### 4.4 两档

| | 什么时候用 | 本轮扫多宽 |
|---|---|---|
| **常态档** | 积压 ≤ 6 分钟 | 最多 6 分钟（即 [游标, 可见水位)） |
| **追赶档** | 积压 > 6 分钟（常态一轮吃不下） | 放宽到**刚好等于积压**，最多不超过 18 分钟 |

追赶档一轮把积压清零，下一轮自动回常态档。**放宽的只有「单轮扫描上限」这一项**：游标、10 秒回退、含前不含后、成功才推游标，全都不变。

### 4.5 必须守住

1. **游标只在成功后推，且推的是本轮窗口的右端 —— 也就是下一轮的起点**（本轮右端 `10:00:50`，下一轮就从 `10:00:50` 起），**不能推可见水位**：追赶档被 18 分钟上限截掉的那一段会永久漏。同时它**不是「查回块里最晚的 `@timestamp`」** —— 右端是算出来的窗口边界，窗口里一个块都没查到时右端照样要推，否则游标卡死、后面全不扫。
2. **18 分钟硬顶不能破**：积压真比它还大就分几轮吃，每轮最多 18 分钟；破了就回到「越积越多」的老问题。
3. **追赶轮自己可能超时**：一次扫 15 分钟数据可能跑过 3 分钟，把下一轮挤掉。但此时游标已经推到位，再下一轮积压只有 6 分钟，常态档一轮就能吃完 —— 连锁跳一次就收敛。

## 5. 轮次表 · 预置数据、启动校验与每轮锁 SQL

**结论**：轮次表 `FvTurn` 复用现成框架表，**不改表结构；`Name = 'MONITOR'` 这一行由初始化脚本 / 运维预置，服务启动不写、只校验（§5.2）**；每轮用 `SELECT … FOR UPDATE SKIP LOCKED` 抢这一行的行锁，整轮扫描与游标推进在同一个事务里，成功才 `COMMIT`。

### 5.1 本模块用到的列

| 列 | 类型 | 说明 |
|---|---|---|
| `Name` | VARCHAR2(30) | **唯一索引**，业务定位键。本模块固定 `MONITOR`；与别的定时任务各占一行、各一把独立行锁，互不阻塞 |
| `CursorTs` | TIMESTAMP(3) | 时间窗口游标 = 上一轮成功时推到的**那轮窗口右端**（即本轮起点）；初始 `NULL` ⇒ 走 §4.3 第 2 步的冷启动回看 |
| `Owner` | VARCHAR2(64) | 抢到本轮的节点，诊断用 |
| `StartedAt` | TIMESTAMP(3) | 本轮触发时刻，诊断用 |

> 列名为本模块口径；现场轮次表若已有等价列，直接复用、SQL 里的列名按现场对齐，**口径不变**。`MONITOR` 共 7 字符，按现成表实际列宽即可装下。`ID` 等技术主键由自增 / 框架补。

### 5.2 启动前置 · 预置数据与校验

`Name = 'MONITOR'` 这一行由**初始化脚本 / 运维预置**，服务启动**不写轮次表**。初始化脚本只需给下面两个栏位赋值（部署时一次）：

| 栏位 | 值 |
|---|---|
| `Name` | `MONITOR` |
| `CursorTs` | `NULL` |

预置只管这两列；服务启动与运行期的口径：

| 项 | 口径 |
|---|---|
| 谁写 | 初始化脚本 / 运维；服务启动**一行都不写** —— 不补行、不覆盖已有游标 |
| 启动校验 | 只读检查 `MONITOR` 行存在且可读（连不上 / 查不动一并算失败） |
| 有问题 | **直接启动失败并报错**，不降级、不静默跳过、不自动补 |
| 为什么 | `SKIP LOCKED` 返回 0 行的语义是「别人在跑」；行一旦缺失会伪装成「每轮都被跳过」⇒ 静默全停，必须在启动阶段挡住 |
| `CursorTs` | 留 `NULL` 是刻意的：第一轮（或游标丢失）按 §4.3 第 2 步取「可见水位 − 1 分钟」，**只回看一次** |
| 多实例 | 每台启动各自校验、都不写；行由部署阶段一次性预置 |

- 业务规则仍由 `01` 配置页维护，服务不预置；启动只把轮次行当**前置条件**校验，不把它当运行期脏数据来修。

### 5.3 每轮执行的 SQL

```sql
-- ① 抢轮次：本轮第一条语句，跨机互斥
SELECT Name, CursorTs
  FROM FvTurn
 WHERE Name = 'MONITOR'
   FOR UPDATE SKIP LOCKED;      -- 必须带 SKIP LOCKED
```

- 返回 **1 行** = 抢到，行锁从这条 `SELECT` 一直持到 `COMMIT`；返回 **0 行** = 别人在跑，**本轮事务直接结束**（还没做任何改动，提交与回滚等价）。
- **为什么必须 `SKIP LOCKED`**：不带 SKIP，后醒的节点会阻塞在行锁上排队，锁一释放接着跑第二遍 —— 周期漂移、同一刻度重复执行；带 SKIP 才是「被占用就跳过、不排队、不补跑」。
- 不引 Redis / 分布式锁：进程崩了事务回滚、行锁自动释放，不需要租约与接管。

```sql
-- ② 抢到后登记本轮归属（同一事务，失败随 ROLLBACK 一起回滚）
UPDATE FvTurn SET Owner = :nodeId, StartedAt = :fireAt
 WHERE Name = 'MONITOR';

-- ③ 整轮扫描成功后，推游标到「本轮窗口右端」（= 下一轮的游标），同一事务 COMMIT
UPDATE FvTurn SET CursorTs = :rightTs
 WHERE Name = 'MONITOR';
COMMIT;
```

- ②③ 之间就是 **§6 的一轮 8 步**：读配置 → 按窗口查块清单 → 定候选块 → 判块 → 回行取数 → 判行落表与 Block Scan 整理（窗口宽度见 §4.3），落 §2.1 状态表 + §3 结果索引 + §2.2 块进度表。
- 跳过 / 失败：`ROLLBACK`，**游标一律不动**（§4.5 第 1 条）；数据不丢，堆在区间里等下一轮。
- **推的是 `:rightTs`（本轮窗口右端，也是下一轮的游标），不是可见水位** —— 被 6 / 18 分钟上限截掉的那一段，推可见水位会永久漏。

### 5.4 锁的边界

| 项 | 口径 |
|---|---|
| 事务范围 | 只包本轮扫描与游标推进；外部 IO（通知等）全在 `COMMIT` 之后、锁外 |
| 串行语义 | 不排队、不补跑；上一轮没结束，下一个 3 分钟刻度整轮跳过 |
| 同机防重入 | cron 固定速率触发，上一轮没完下次照样来 ⇒ 进程内「正在跑就跳过本次触发」标记 |
| 一轮跑过 3 分钟 | 持锁跨过下一个刻度，那个刻度被跳过；游标已推到位，收敛见 §4.5 第 3 条 |
| 崩溃 | Oracle 行锁随事务回滚自动释放，下一轮别的节点直接接管，无主备切换 |
| 相位固定节点 | 可能长期抢不到轮次，不报错、不影响正确性；排查时先看这一处 |

## 6. 每轮业务 · 从块清单到 issue

**一句话**：本章只写 §4 / §5 没写的部分 —— 抢到 `MONITOR` 行锁（§5.3 ①）之后、推游标 `COMMIT`（③）之前，一轮 8 步。窗口怎么算（§4.2 ~ §4.4）、抢锁与失败回滚（§5.3）、事务边界（§5.4）一律引用，不重复。

### 6.1 一轮 8 步

| 步 | 做什么 | 打在哪 | 口径 |
|---|---|---|---|
| 1 | 抢 `MONITOR` 行锁；抢不到整轮跳过、游标不动 | Oracle | **已写** §5.3 ① / §4.3 |
| 2 | **读配置**：每轮重读规则表（**只取 `Enabled = true` 的规则**），`Environment` 去重成集合；System Misc 名单在**服务启动时**另读一次 | Oracle + System Misc | §6.2 |
| 3 | **查块清单**：按 §4.3 窗口查 `mes-log-exec-read`，查询恒嵌两组 `terms`：`terms ENV` + **`terms SERVER_CATEGORY`（启动白名单，无论有无都拼）**，只有名单内类别的块被查回 | 块索引 | §6.2 |
| 4 | **定候选块**：第一波 = 3 的全量清单；第二波起 = **Block Scan 现存全部（都是未闭合）+ 本轮窗口新块**，按 `BlockId` 去重 | 进度表 + 块索引 | §6.3 |
| 5 | **逐块判块**：过 5 项检查 1~3；块分已闭合（已完成 / 中断 / 超时封口）/ 未闭合（仅进行中）两种 | 块文档 | §6.4 |
| 6 | **回行取数**：按块把该块的行日志取回来，再按 `LastScannedLineId` 截掉已扫过的部分 | 行索引 | §6.4 |
| 7 | **判行 + 落表**：过关键字 / 排除词 → 记 issue list；每块结算 Block Scan（已闭合删行 / 未闭合 UPSERT）；兜底强清陈行 | 两源 + 进度表 | §6.5 |
| 8 | 推游标到「本轮窗口右端」（= 下一轮游标）、`COMMIT` | Oracle | **已写** §4.3 第 5 条 / §5.3 ③ |

> 第 1、8 步只作定位用，正文从 2 写到 7。

### 6.2 第 2、3 步 · 读配置与查块清单

**第 2 步（新加）**

| 项 | 口径 |
|---|---|
| 时点 | 抢到行锁**之后**、算窗口**之前**，一轮读一次；一轮之内不会有两个实例各按不同版本跑 |
| 读什么 | `FvLogMonitorCfg` **只取 `Enabled = true` 的行**（字段 `Environment` / `Item` / `Keyword` / `ExcludeKeywords` / `FollowRuleNames` / `ExcludeRuleNames` / `Priority` / `Enabled`） |
| 分组 | `Environment` 去重成集合；**一行 = 一条规则 = 一个关键字**，`Item + Environment` 唯一 |
| 生效 | 不缓存、不热加载；删改**与启停**都**下一轮生效**，本轮读到的版本跑到底 |

- **只有 `Enabled = true` 的规则进本轮** —— 有行不等于启用；非 `true`（`0` / `NULL`）一律视为未启用，不参与检查、不进环境集合（启停口径见 `01` §4.1-7）。三个名单是 JSON 数组，未配存 `NULL` ⇒ 该项检查跳过。

**启动时读一次 · ServerCategory 白名单（新加）**

| 项 | 口径 |
|---|---|
| 来源 | System Misc（`FvMisc`），配置项 `log.monitor.servercategory` |
| 时点 | **服务启动时读一次**，调 `shared-business-lib` 的 **`FetchLogMonitorSrvCategoryFromSystemMisc()`**；**不随轮次重读** —— 与上面第 2 步「抢锁后每轮全量重读规则表」是两回事 |
| 形态 | **输入为空、输出为字符串数组 `string[]`**；**公共方法返回什么就原样记下什么** —— 服务侧不解析、不校验、不转换、不补默认值，也不管空值与回落 |
| 用途 | **白名单**：第 3 步查块时把名单**嵌进 `terms SERVER_CATEGORY`**，**只有类别落在名单里的块才进本轮窗口新块**、名单外的类别在 OS 侧就不返回；**这个条件恒拼、不受名单有无影响** —— 名单为空（空数组）照样拼 `terms: []`，OS 侧一条都匹配不到 ⇒ **本轮一个块都筛不出来、等于没有服务被监控**（有意如此：没配白名单就不该偷偷扫全量） |
| 生效 | 启动时定死；改这项配置要**重启服务**才生效（规则表是下一轮生效，别混） |

- **只筛新来的**：白名单只在第 3 步的**查块查询**里生效；第 4 步由 Block Scan 带回的未闭合块**不走这条查询**，不按这份名单过滤，照常进候选续扫。
- **空白名单的边界**：名单为空时第 3 步一条都取不回 ⇒ 新块一个不进；但已在 Block Scan 里的未闭合块仍按原进度续扫到闭口为止（它们不经过这条查询）。要彻底停某个类别的监控，用停规则或停服务，别指望空白名单 —— 白名单管的是「新块进不进门」。

**第 3 步（增强）**：按 §4.3 算出的 `[游标, 右端)` 查块索引读别名 `mes-log-exec-read`，查询恒嵌**两组条件**：`terms ENV`（本轮环境集合，没配规则的环境直接挡在查询外）+ **`terms SERVER_CATEGORY`（启动时那份白名单，恒拼）**。只有名单内的类别才被查回来，**名单外的类别在 OS 侧就不返回** —— 块量很大时取回再丢会白拉一整批文档。**名单为空也照样拼这一项**（空数组），拿到的就是空清单、本轮无新块；**不写「空名单就跳过该条件」**，那等于悄悄放全量进来。`Keyword` 与两份 Rule Name 名单**不进这一步** —— 它们是行级 / 规则级判定，归第 5、7 步。中途失败按 §5.3 整轮 `ROLLBACK`、游标不动。

**查块 DSL**（窗口依据打 `@timestamp`，不是 `START_TIME`；以下以 §4.3 第二轮、触发点 `10:03` 为例，窗口 `[09:59:50, 10:02:50)`）：

```json
GET /mes-log-exec-read/_search
{
  "size": 200,
  "track_total_hits": false,
  "query": {
    "bool": {
      "filter": [
        {"terms": {"ENV": ["PROD", "PIRUN"]}},
        {"terms": {"SERVER_CATEGORY": ["FAB", "LIST"]}},
        {"range": {"@timestamp": {
          "gte": "2026-11-18T09:59:50.000+08:00",
          "lt":  "2026-11-18T10:02:50.000+08:00"
        }}}
      ]
    }
  },
  "sort": [{"@timestamp": "asc"}, {"_doc": "asc"}],
  "_source": ["ENV", "HOSTIP", "SERVER_ID", "system.name",
              "RULENAME", "EXEC_STATUS", "START_TIME", "END_TIME",
              "START_LINE_ID", "END_LINE_ID"]
}
```

- **查询侧只嵌三样**：`terms ENV` + 窗口 `range` + **`terms SERVER_CATEGORY`（白名单）**（值填启动时那份名单，示例 `FAB` / `LIST`）。**白名单恒拼、不看有无**：名单为空就拼 `"SERVER_CATEGORY": []`，空 `terms` 匹配不到任何文档 ⇒ 清单为空、本轮无新块（这是想要的默认语义，不是要绕开的坑）；`Keyword` / 两份 Rule Name 名单不进（行级 / 规则级判定）。
- **时间打 `@timestamp`、用 `[gte, lt)` 左闭右开**，与 §4.3 的窗口语义一致；**不打 `START_TIME`**（那是业务时间，回采时会错月）。
- **翻页用 `search_after` 带 `[@timestamp, _doc]` 两个值**：首屏不带，后续页把上一页最后一条的这两个值填进去；**一直翻到返回空数组**，清单才算取全。`_doc` 不能省——同毫秒建块会重值，只靠 `@timestamp` 会静默漏块。
- **`_source` 给全第 5 / 6 步要用的块信息**：`_id` 即 `BlockId` 默认返回；`ENV` / `HOSTIP` / `SERVER_ID` / `system.name` / `START_TIME` / `END_TIME` / `START_LINE_ID` / `END_LINE_ID` 是 `FetchMESRuleFullLogs()` 的输入，`RULENAME` / `EXEC_STATUS` 给第 5 步判块；**`SERVER_CATEGORY` 已进查询条件、不再取回**（省传输），大字段 `LOG_RAW` 也不在这里取。
- 索引走读别名 `mes-log-exec-read`，不自己拼月索引名；`prefix` 由框架前置（§3 / `09` §五）。

### 6.3 第 4 步 · 两波的候选块

| | 第一波（冷启动） | 第二波起 |
|---|---|---|
| Block Scan 状态 | 空 | 只存上轮结束时留下的**未闭合**块 |
| 候选块 | **没有并集**：3 查出的全量清单 | **Block Scan 现存全部 ∪ 本轮窗口新块**，按 `BlockId` 去重 |

- **没有 Flag，也没有「减已闭合块」这一步**：Block Scan 里存在的块从定义上就是没扫完的 —— 闭合的在上轮结束时已经删掉了（§6.5）。所以第二波就是两份清单直接并起来，`BlockId` 重复的合并成一条（窗口新块正好也是上轮未闭合块时会出现）。
- 写死就是：`待处理 = BlockScan[全部] ∪ 窗口新块`，按 `BlockId` 去重；BlockScan 那一份不带任何状态过滤。
- **窗口回捞不靠 Block Scan 挡**：冷启动回看 1 分钟（§4.2）、游标丢失、重放，都可能把已扫过的**闭合块**重新带进窗口；这类块在 Block Scan 里没有记录，会被当新块重扫一遍。正确性由 `issueId` 幂等兜住（OS `_id` 覆盖 + Oracle UK 冲突跳过），代价只是多扫一次，换来的是 Block Scan 不用留终态行、不用维护两档清理阈值。
- Block Scan 里留下的只有**进行中**的块（闭口三态都算闭合，对齐 `06` §4「除进行中外都算闭口」；超时封口即终局、不再重开），每轮自然带回，不需要额外捞回逻辑。
- **第一波别当成「一定为空」**：只有首次部署时 Block Scan 才是空的；服务重启时里面可能还留着上次没扫完的块，这类残留照第二波的算法一并续扫 —— 它们的 `@timestamp` 早落在游标左边，窗口再也不会把它们捞回来，只能靠这张表。

### 6.4 第 5、6 步 · 逐块判块与回行取数

**第 5 步**：逐块过 5 项检查的 1~3（块阶段），再按 `EXEC_STATUS` 按状态分开处置：

| # | 检查项 | 打在哪 | 否决条件 |
|---|---|---|---|
| 1 | `Environment` | 块 `ENV` | 不在本轮环境集合内 |
| 2 | 关注 Rule Name | 块 `RULENAME` | 配了名单且不在名单内；**空值放行** |
| 3 | 排除 Rule Name | 块 `RULENAME` | 在名单内；空值不生效 |

| 块状态（`EXEC_STATUS`） | 本轮怎么处置 |
|---|---|
| **已闭合 · 已完成 / 中断 / 超时封口**（三态都算闭口，对齐 `06` §4） | 排查完就完事，**第 7 步删行**、不再带回；超时封口即终局、不再重开（尾行按终态处理、不进块） |
| **未闭合 · 仅进行中** | 日志可能还在来 ⇒ **第 7 步 UPSERT 进度行**，下轮由第 4 步带回；被派生层闭口后，下一轮结束自然删行 |

- 一律区分大小写；`RULENAME` 空值放行、多值任一命中。

**第 6 步**：**按块把这块的行日志取回来** —— 调 `shared-business-lib` 的 **`FetchMESRuleFullLogs()`**，**输入＝块信息对象**（第 3 步查回的块，含四个 `term` 与 `START_TIME` / `END_TIME` / `START_LINE_ID` / `END_LINE_ID`）、**输出＝该块全部行日志对象集合**（已还原成块内真实顺序，见下）。**取行与二级重排都在公共方法内部，服务侧不自拼 DSL、不自己重排**。告警服务拿返回结果后只做一件增量动作：按 §2.2 的 `LastScannedLineId` 截掉上次已扫过的部分，剩下的才是本轮要判的行。块与块逐块调用，不并发拉。

**行序 · 二级重排（口径同 `06` §7）**

一个块的行可能跨多个日志文件（滚动切换），OS 取回的是分页顺序、不是日志真实发生顺序。不摆正就判行，截断点会错、命中也会乱序。重排是**每页取回即排一次**（不是整块取完再排），跨页按页序累积：

| 步 | 做什么 |
|---|---|
| 1 · 分堆 | 按 `LOG_FINGERPRINT` 分堆（一个文件一堆）；一页 200 行通常只分两堆 |
| 2 · 堆内 | 按 `LOG_OFFSET` 升序 |
| 3 · 堆间 | 两堆时取各堆首行（`LOG_OFFSET` 最小那行）的 `LOG_TIME` 排堆，堆内仍按 `LOG_OFFSET`；不另设 tie 规则 |
| 4 · 复用 | 记下 `LOG_FINGERPRINT` 的排序顺序，下一次重排直接用，不再回行文档点查 `LOG_TIME` |

- **谁做**：`FetchMESRuleFullLogs()` 内部完成取行 + 二级重排，返回已还原成块内真实顺序的集合；服务侧只消费结果（第 6 步）。
- **截断只在重排后的序列上做**：`LastScannedLineId` 是上一轮序列末行的身份串，在本轮重排后的序列里定位它、截掉之前的部分；定位不到（原文行已被 360 天清理）就按全量重扫，`issueId` 幂等兜住、不会重复落 issue。
- **两轮之间行序必须稳定**，否则截断会漏行：单调性守门由公共方法负责 —— 同指纹内 `LOG_TIME` 随 `LOG_OFFSET` 单调不减、堆间前堆末行 `LOG_TIME` ≤ 后堆首行 `LOG_TIME`，违例只计数告警、不自动修复。
- **模块 2 不做**：不自己排序、不缓存行序、不跨轮比对行集合，也不把「上次扫到哪」记成行数或时间戳 —— 只认 `LastScannedLineId`。

### 6.5 第 7 步 · 判行、落表与 Block Scan 整理

| 动作 | 口径 |
|---|---|
| 判行 | `LOG_BODY` 原文过 `Keyword`（检查 4）+ `ExcludeKeywords`（检查 5），区分大小写；**一命中行一条 issue**，`issueId = LineId\|Item`（`issueType` 恒写 `Keyword`） |
| 写两源 | OS 结果索引按 `_id` 幂等写（§3 / `09` §五 四字段）+ Oracle 状态行按 UK 冲突跳过；**先写事实、后推进度**，同事务 |
| **整理 Block Scan** | **每块结算，一轮结束时统一落一次**：本轮处理过的块，**已闭合**（已完成 / 中断 / 超时封口三态）⇒ **`DELETE` 掉它的行**（不管之前有没有这行）；**仅进行中** ⇒ **`UPSERT` 一行**，已有行就更新 `LastScannedLineId` + `LastScanTime`，没有就新插 |
| `LastScanTime` | 未闭合块**每轮结束都刷**（就是这轮扫它的时刻）；它只做兜底强清的寿命判据，不再有「每轮复查不刷」的讲究 |

**兜底强清（阈值 = 轮数 × `MonitorInterval`；参数见 §7）**

| 行 | 阈值 | 含义 |
|---|---|---|
| 未闭合（表里唯一一种行） | **15 轮 / 45 分钟** | 正常链路：块被派生层闭口后，下一轮结束时自然 `DELETE`；45 分钟还留着说明派生层异常（块永远不闭口），强清止损 |

- 强清**每 30 分钟跑一次**（10 × `MonitorInterval`），一条 `DELETE` 按 `LastScanTime` 判；**不加自监控**。
- 窗口单调往前推（§4.3 游标推到本轮窗口右端），未闭合块的 `@timestamp` 落到游标左边后不会再被第 3 步查出来 —— 只能靠 Block Scan 带回，所以这张表是续扫的唯一依据，不能省。
- 强清的行，之后该块再来日志就没人扫了 —— 这是用阈值换掉自监控的已知代价；按超时封口的正常链路，进行中块很快被闭口删行、走不到 45 分钟，只在派生层异常的块上发生。
- 删行（正常闭合或强清）后该块若被窗口重新捞回，会当新块重扫一遍（§6.3）：`issueId` 幂等（OS `_id` 覆盖 + Oracle UK 冲突跳过），不会重复落 issue。

## 7. 配置参数

本表只收**关键字监控**运行时读的应用参数；业务配置（规则、阈值、收件人）在 `01` / `03`，不在本表。改值不动判定逻辑，走 git 同步版本；默认值均为初值，压测后回填。

| 参数 | 说明 | 默认值 |
|---|---|---|
| `MonitorInterval` | 定时扫描触发间隔，触发点 10:00 / 10:03 / 10:06 …（§4） | 3min |
| `InitialLookback` | 首轮冷启动 / 游标丢失的回看宽度（§4.2 / §4.3） | 1min |

| `CatchUpCap` | 追赶档硬顶，按实测速度反解（§4.4） | 18min |
| `ScanRowStaleRounds` | Block Scan 未闭合行兜底强清轮数；强清任务每 10 轮跑一次 = 10 × `MonitorInterval`（§6.5） | 15 轮 / 45min |
