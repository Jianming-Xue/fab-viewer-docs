## 一、Oracle 表

只放**调度态**，四张调度表，不放日志、块文档与业务配置（日志与块在 OpenSearch；Hang 判定配置在模块5）。表名与栏位均大驼峰、全项目统一不加引号（不加引号的标识符 Oracle 会转成大写，写 `FvTask` 与 `FVTASK` 是同一张表）；主键与审计字段的赋值、各栏位长度 / 可空 / UK 见 §1.1 统一规范。

### 1.1 四张调度表

四张表统一规范：

- **主键 `ID`**：`VARCHAR2(≤50)`、非空；由框架底层赋值，调度逻辑一律按业务 UK 读写、不引用 `ID`。
- **审计四字段** `CreatedAt` / `CreatedBy` / `UpdatedAt` / `UpdatedBy`：由底层统一赋值、不进任何 SQL；`UpdatedAt` / `UpdatedBy` 每次写操作无条件刷新；新建后未更新时 `UpdatedAt` / `UpdatedBy` 可空。长度 `CreatedAt`/`UpdatedAt` = 63（`VARCHAR2(63)`），`CreatedBy`/`UpdatedBy` ≤50。
- **业务时间戳与审计 `UpdatedAt` 分开**：审计 `UpdatedAt` 归底层；业务侧另设专名——`FvTask.ProgressAt`（进度戳）、`FvStream.RecalcAt`（归属重算时刻），由 SQL 显式写、不受审计刷新影响。
- 列名大驼峰、不加引号（Oracle 自动转大写）；**业务时间列**统一 `TIMESTAMP(3)`（毫秒），与行索引 `@timestamp` 对齐（审计两个 At 字段除外，见上）；字符串长度按字符校验（避免 `VARCHAR2` 字节语义抛 `ORA-12899`）。

**`FvTurn` · 轮次表**

当前预置两行（`Cycle = 'FAST'` 与 `'SLOW'`），不随轮次增长；表结构可容纳其他定时循环，本节只写本次用到的 FAST / SLOW。既是本轮行锁（`SELECT … FOR UPDATE SKIP LOCKED`），又是快轮次游标的账；慢轮次那行游标留空。

| 字段 | 列名 | 长度 | 可空 | 说明 |
|---|---|---|---|---|
| 主键 | `ID` | ≤50 | 否 | 底层赋值、调度逻辑不引用 |
| 轮次 | `Cycle` | ≤8 | 否 | **业务 UK**；本次只落 `FAST` / `SLOW` 两值、各一把独立行锁，未来其他定时循环可加值 |
| 区间左端 | `FromTs` | TIMESTAMP(3) | 是 | 本轮扫描左端 = 上一轮 `ToTs`；慢轮次留空 |
| 快轮次游标 | `ToTs` | TIMESTAMP(3) | 是 | = `now − ScanDelay`（停摆时封顶 `FromTs + ColdLookback`）；慢轮次留空 |
| 持有节点 | `Owner` | ≤64 | 是 | 抢到本轮的 Scheduler 节点 |
| 开始时刻 | `StartedAt` | TIMESTAMP(3) | 是 | 本轮开始时刻 |
| 审计四字段 | `CreatedAt`/`CreatedBy`/`UpdatedAt`/`UpdatedBy` | — | 见上 | 底层统一赋值 |

**业务唯一索引**：`Cycle`。

**`FvTask` · 待办表**

一行一条流（不是一块），快慢两个循环共用一张。四张表里只有这张会被 Worker 改。

| 字段 | 列名 | 长度 | 可空 | 说明 |
|---|---|---|---|---|
| 主键 | `ID` | ≤50 | 否 | 底层赋值、调度逻辑不引用 |
| 流键 | `StreamKey` | ≤160 | 否 | **业务 UK**，`ENV\|HOSTIP\|SERVER_ID` 三段竖线相连；MERGE / 领活 / 收工都按它 |
| 来源 | `Reason` | ≤16 | 否 | `NEW_LINE`（快轮次新行）/ `SILENCE`（慢轮次静默超期） |
| 归属 Worker | `Worker` | ≤64 | 否 | 当前归属，Scheduler 每轮按当前环校正 |
| 状态 | `Status` | ≤16 | 否 | 只两态：`Pending`（待领）/ `Processing`（已领未收工）；无 `Retry` / `Dead` / `Idle` |
| 进度戳 | `ProgressAt` | TIMESTAMP(3) | 否 | `Processing` 时领活写、每跳长 IO 前推进；`Pending` 时是入队戳。**只在状态迁移那一刻写，同状态覆盖不动**（SQL 显式写、触发器兜底）；与审计 `UpdatedAt` 各管各 |
| 审计四字段 | `CreatedAt`/`CreatedBy`/`UpdatedAt`/`UpdatedBy` | — | 见上 | 底层统一赋值、`UpdatedAt` 无条件刷新 |

**业务唯一索引**：`StreamKey`。**普通索引** `(Worker, Status)` —— Worker 领活那条原子 UPDATE 的走法，摘环判据（名下有没有超期的 `Processing` / `Pending`）也走它。一行一条流、处理完就删；表只回答「这条流有没有活」和「有没有人在处理」。

触发器（业务戳归业务戳、底层审计归底层审计）：

```sql
CREATE OR REPLACE TRIGGER FvTask_keep_enqueue
BEFORE UPDATE ON FvTask
FOR EACH ROW
WHEN (OLD.Status = 'Pending' AND NEW.Status = 'Pending')
BEGIN
  :NEW.ProgressAt := :OLD.ProgressAt;
END;
```

**`FvNode` · 心跳表**

一台节点一行，节点自己 upsert，Scheduler 只读。

| 字段 | 列名 | 长度 | 可空 | 说明 |
|---|---|---|---|---|
| 主键 | `ID` | ≤50 | 否 | 底层赋值、调度逻辑不引用 |
| 节点标识 | `NodeId` | ≤64 | 否 | **业务 UK**，节点标识 |
| 角色 | `Role` | ≤16 | 否 | `SCHEDULER` / `WORKER` |
| 状态 | `State` | ≤16 | 否 | `ONLINE` / `DRAINING` / `DEGRADED`（连败降级）。**`DRAINING` 是服务退出时由自身主动标记**——收到终止信号就在退出钩子里把本节点改成它，表示有序下线、不再接新活；后两种都不进环、不接新活 |
| 最后心跳 | `LastSeen` | TIMESTAMP(3) | 否 | 判死 = `now − LastSeen > 3 × 心跳间隔` |
| 连败次数 | `FailStreak` | NUMBER(6) | 否 | 连续处理失败数，成功归零；到 `FailStreakLimit` 自降 `DEGRADED` |
| 最后成功 | `LastOkAt` | TIMESTAMP(3) | 是 | **只作诊断、不参与判活**（空闲节点天然陈旧，拿它判活会误摘） |
| 启动时刻 | `StartedAt` | TIMESTAMP(3) | 否 | 节点启动时刻 |
| 降级时刻 | `DegradedAt` | TIMESTAMP(3) | 是 | 进 `DEGRADED` 时刻，回 `ONLINE` 清空；退出基准 `now − DegradedAt ≥ SuicideAfterSeconds` |
| 审计四字段 | `CreatedAt`/`CreatedBy`/`UpdatedAt`/`UpdatedBy` | — | 见上 | 底层统一赋值 |

**业务唯一索引**：`NodeId`。

`State` / `FailStreak` / `LastOkAt` / `DegradedAt` 都由节点自己写、Scheduler 只读别人的；参与判活的只有 `State` 与 `FailStreak`。Scheduler 也是这里的一行（`Role = 'SCHEDULER'`、启动 `State='ONLINE'`、退出改 `DRAINING`）：服务启动时插入、心跳周期只刷 `LastSeen`、优雅下线由退出钩子改 `State`（各栏位存什么见 §三 7）。它不参与任何调度决策，唯一用途是让「Scheduler 全挂」这个故障能报出来（没有这条心跳且非 `DRAINING`，新日志不再被发现而 Worker 仍在消耗存量，表面看不出异常）。

**`FvStream` · 流归属表**

哈希环的落点，Scheduler 每轮重算写进来，是待办表归属列的唯一依据。

| 字段 | 列名 | 长度 | 可空 | 说明 |
|---|---|---|---|---|
| 主键 | `ID` | ≤50 | 否 | 底层赋值、调度逻辑不引用 |
| 流键 | `StreamKey` | ≤160 | 否 | **业务 UK**，同待办表 |
| 归属 Worker | `Worker` | ≤64 | 否 | 当前环上该流的落点 |
| 环版本 | `RingVer` | NUMBER(10) | 否 | 环版本号，Worker 增减时 +1 |
| 重算时刻 | `RecalcAt` | TIMESTAMP(3) | 否 | 归属最后重算时刻；业务戳，与审计 `UpdatedAt` 分开 |
| 审计四字段 | `CreatedAt`/`CreatedBy`/`UpdatedAt`/`UpdatedBy` | — | 见上 | 底层统一赋值 |

**业务唯一索引**：`StreamKey`。**普通索引** `(Worker)`。

四张表的关系：`FvTurn` 固定两行不增长；`FvTask` 与 `FvStream` 都以 `StreamKey` 为业务 UK、逐行对应；`FvNode` 一台节点一行。`ID` 只是底层技术主键，调度侧全部读写仍按业务 UK（`Cycle` / `StreamKey` / `NodeId`）。

## 二、OS 块索引字段

块索引 `mes-log-exec-{yyyy.MM}`（基名，环境前缀由框架 `prefix` 加），按月切、永久归档不删。一块 = 一次请求执行；`_id` = `REQUEST_EXEC_ID`，在块整个生命周期里不变。

**字段清单、类型、含义与取值口径的唯一权威在 `09-OpenSearch索引模板.md` §四**（含完整 JSON 模板、32 字段表、3 组 nested 子字段与关键约定），可执行配置在 `deploy/opensearch/12-template-exec.json`。本文不再复述字段表，避免两处维护漂移。

派生侧只需记住两条与写法直接相关的口径，其余照 09 §四：

- **业务时间窗一律打 `START_TIME`**，不打块上的 `@timestamp`（块 `@timestamp` = 首次建块的系统当前时刻，与行索引同名不同义，不进业务时间窗）。
- **两种时间格式别混**：`@timestamp` / `CLOSE_TIME` 走墙钟 `strict_date_optional_time||epoch_millis`；`START_TIME` / `END_TIME` / `LAST_LINE_TIME` 与三个 nested 里的时间子字段走日志格式 `yyyy/MM/dd HH:mm:ss.SSS`。

## 三、Scheduler

Scheduler 是单点进程：扫行索引归流、推游标、算哈希环写归属、兜底回收卡住的活。它无状态、不持活——游标与待办都在 Oracle，挂掉一台不影响别的。Scheduler 与 Worker 可分开部署、可同机（单机起步时同进程跑两个角色）。

### 1 职责与部署

- **职责**：快轮次扫行索引发现新流；慢轮次扫块索引发现静默流；按心跳摘节点、算哈希环写归属；4a / 4b 校正存量。Scheduler 只查询行 / 块索引做归流派活，不写块文档、不看行正文。
- **部署位置**：Logstash 服务器，与采集 / 加工层同机，不搭在 MES 应用服务器上，自己发布、与 MES 版本解耦。**前提**：各节点 NTP 在跑、偏差 < 1 秒（秒级 cron 对齐、`ORDER_BY` 14 位时间戳、`ProgressAt` 比较都吃系统时钟）。**起步规模**：3 台 AP 服务器 × 5 个 Worker = 15 个；加 Worker 就是起一个容器，环变更由 Scheduler 自动完成。不引 Quartz / XXL-Job / K8s CronJob——它们只提供「按 cron 唤起任务」，而轮次唯一性、按三元组分流、按心跳摘环与兜底回收都得落在自己的表上。
- **与 Worker 的关系**：Scheduler 决定「哪条流的活、给谁」，Worker 决定「这块日志怎么切、什么时候算完」；两者靠四张 Oracle 表传话，谁也不直接找谁。
### 2 启动与轮次表

#### 2.1 启动校验

进程启动时按 `Cycle = 'FAST'` 与 `Cycle = 'SLOW'` 各读一行 `FvTurn`；**任一行读不到就直接报错、进程不启动**，不自动补建。轮次行是建表时预置的固定两行，缺行说明部署或初始化出错；自动补建会掩盖错误，还可能重置游标造成漏扫。

#### 2.2 两把行锁

两个轮次各一把行锁（`Cycle='FAST'` / `'SLOW'`），一个轮次的全部动作在抢到锁的那台上的一个事务里跑完，持锁到 `COMMIT`；Worker 处理在锁外。

### 3 哈希环与名单

#### 3.1 哈希环：一条流固定一个 Worker

键是锁流三元组 `ENV + HOSTIP + SERVER_ID`；每台 Worker 按 `NodeId + '#' + 0 … V` 展开 V 个虚拟点贴到 0 ~ 2^64 的环上，对三元组算 `murmur3_128` 取 64 位无符号 `h`，顺时针第一个点就是主人（越过最大点绕回第一个）。四个参数固定死，否则两台 Scheduler 算出两个环：

| 参数 | 取值 |
|---|---|
| 哈希函数 | `murmur3_128` 取 64 位无符号（无符号比较，别用 `Math.abs()`，`Long.MIN_VALUE` 会算歪） |
| 虚拟节点数 V | 100 ~ 200 |
| 挂点与排序 | 按 `NodeId` 字典序，逐点挂 `NodeId + '#' + i` |
| 取点 | 顺时针第一个 `≥ h`（`ceilingEntry`），越过最大点取 `firstEntry` |

环成员只放**进环名单**里的 Worker（心跳未过期 + `ONLINE` + `FailStreak` 没到顶 + 名下没有超期卡住的待办——正常 `Processing` 不算卡住）；只有 Scheduler 算环，落点写进 `FvStream.Worker`，并据此写 `FvTask.Worker`（**例外**：该流正 `Processing` 时 `FvTask.Worker` 粘原值、不写新落点，见 4.2），Worker 不自己算、领活读待办表。虚拟节点不进表、不注册。

#### 3.2 读心跳算名单：Worker 的四种形态

每个轮次读一次 `FvNode`（`Role='WORKER'`）与 `FvTask`，按下面的口径把 Worker 分类、算出当前环。一轮只读一次，进环名单两处共用（4.2 派新活、§5 的 4a 校正）；基础名单为空则整轮作废（见 4.3）。

下面每处 `:now − :阈值` 的算法一致：**把「时长阈值」换成「截止线时间点」**。字段时间 **≥ 线** = 未过期，**< 线** = 已超期。三档差值固定为：① 判死线 `now − 30s`（`DeadThresholdSeconds` = 3 × `HeartbeatSeconds`）② 摘环线 `now − 30s`（`PendingStaleSeconds`，管 `Pending`）③ 回收线 `now − 300s`（`ReclaimAfterSeconds`，管 `Processing` 的摘环与回收）。**进环名单对 `Processing` 只认③、不认「名下有 `Processing`」本身**——这是同流新行粘住原 Worker 的关键。

**1. 基础名单（兜底）**——心跳未过期且 `State='ONLINE'`，不看失败次数、不看名下待办。它是「还有没有机器能干活」的底线，为空则整轮回滚；进环名单被摘空时退用它搭环（带病运行）。

```sql
SELECT NodeId FROM FvNode
 WHERE Role = 'WORKER' AND State = 'ONLINE'
   -- 差值① 判死线 = :now − :DeadThresholdSeconds = now − 30s（= now − 3 × HeartbeatSeconds）
   -- LastSeen >= 该线 = 心跳未超时；早于该线 = 已判死、不进任何名单
   AND LastSeen >= :now - :DeadThresholdSeconds;
```

**2. 进环名单（活着且健康）**——基础名单之上再加两档：`FailStreak` 没到顶、名下没有卡住的待办。卡住只认超期：`Processing` 进度戳超回收线（`ReclaimAfterSeconds`，300s）或 `Pending` 超摘环线（`PendingStaleSeconds`，30s）；**正常处理中的 `Processing` 不算卡住、不摘环**。搭环只用这一份，落点写进 `FvTask.Worker` / `FvStream.Worker`。

```sql
SELECT n.NodeId FROM FvNode n
 WHERE n.Role = 'WORKER' AND n.State = 'ONLINE'
   AND n.FailStreak < :FailStreakLimit             -- 默认 3
   -- 差值① 判死线 = :now − :DeadThresholdSeconds = now − 30s（= now − 3 × HeartbeatSeconds）
   -- LastSeen >= 该线 = 心跳未超时
   AND n.LastSeen >= :now - :DeadThresholdSeconds
   AND NOT EXISTS (
         SELECT 1 FROM FvTask t
          WHERE t.Worker = n.NodeId
            -- Processing 只摘超时的：正常处理中（进度戳未过回收线）不摘环，
            -- 同流新行仍落回原 Worker 接着处理，不重新摊派
            AND ( (t.Status = 'Processing' AND t.ProgressAt < :now - :ReclaimAfterSeconds)
               -- 差值③ 回收线 = :now − :ReclaimAfterSeconds = now − 300s（Processing 摘环也用这条）
               -- ProgressAt 早于该线 = 真卡死，才摘环并交由 4b 触发①整批重排
               -- 差值② 摘环线 = :now − :PendingStaleSeconds = now − 30s（与判死线同量级）
               -- Pending 的 ProgressAt 早于该线 = 老待办没人领，该 Worker 摘环
               OR (t.Status = 'Pending' AND t.ProgressAt < :now - :PendingStaleSeconds) )
       );
```

**3. 卡住的（不进环 / 待回收）**——判定不看心跳，分两种：节点还活着但名下待办卡住（心跳正常、线程卡死），或节点死了 / 降级了。

- 名下待办卡住：`Processing` 进度戳超 `ReclaimAfterSeconds`（300s）或 `Pending` 超 `PendingStaleSeconds`（30s）没人动 → 摘环、不进环；**正常 `Processing`（进度戳还在刷新）不算卡住**。其中 `Processing` 由 4b 触发①退回 `Pending`、按当前环改派重放。
- 节点死了 / 降级：心跳超判死线，或 `State='DEGRADED'` → 进退活名单，名下 `Processing` 由 4b 触发②立刻退回。

```sql
-- 3a 摘环 / 4b 触发①：名下有卡住待办的 Worker
SELECT DISTINCT Worker FROM FvTask
 WHERE (Status = 'Processing'
          -- 差值③ 回收线 = :now − :ReclaimAfterSeconds = now − 300s（> 两次进度刷新最大间隔）
          -- Processing 的 ProgressAt 早于该线 = 卡住待回收
          AND ProgressAt < :now - :ReclaimAfterSeconds)
    OR (Status = 'Pending'
          -- 差值② 摘环线 = :now − :PendingStaleSeconds = now − 30s
          -- Pending 的 ProgressAt 早于该线 = 老待办没人领
          AND ProgressAt < :now - :PendingStaleSeconds);

-- 3b 退活名单 / 4b 触发②：判死或降级
SELECT NodeId FROM FvNode
 WHERE Role = 'WORKER'
   AND (
         -- 差值① 判死线 = :now − :DeadThresholdSeconds = now − 30s
         -- LastSeen 早于该线 = 心跳超时、节点判死
         LastSeen < :now - :DeadThresholdSeconds
         OR State = 'DEGRADED'
       );
```

**4. 优雅停机（`DRAINING`）**——人为下线，几份名单都不进、不接新活：名下 `Processing` 让它跑完、不打断，`Pending` 由 4a 改派给别人。

```sql
SELECT NodeId FROM FvNode
 WHERE Role = 'WORKER' AND State = 'DRAINING';
```

- **一轮只算一次进环名单**：派新活（4.2）与 4a 校正（§5）共用同一份，各算一次会得到两个不同的环——新活写一个落点、旧行改另一个落点。
- **进环名单被摘空时退用基础名单**搭环，至少留一台在环里，本轮照常跑完、游标照常推进；这是带病运行，卡住的活仍靠第 3 类那两条回收。基础名单也为空（全员掉线 / 全员 `DEGRADED`）才整轮作废。

### 4 快轮次（30 秒）

#### 4.1 抢锁与定区间

cron `0/30 * * * * *`（6 位带秒位），每分钟 0 秒与 30 秒。`SELECT … WHERE Cycle='FAST' FOR UPDATE SKIP LOCKED` 返回 1 行即抢到、持锁到 `COMMIT`，返回 0 行即别人在跑、本轮直接结束（未做任何改动）。同机用「上一轮没跑完就跳过本次触发」防重入。

一轮五步。**步号 = 执行顺序**；「节」列标出该步写在哪节，节号不随步号递增——② 落在 3.2、④ 落在 §5，都是快慢共用的逻辑，不占本节的小节号。

| 步 | 做什么 | 落在哪 | 节 |
|---|---|---|---|
| ① 抢锁与定区间 | `SELECT … FOR UPDATE SKIP LOCKED` 抢 `FvTurn` 行锁；`[FromTs, ToTs)`：`FromTs` = 上一轮 `ToTs`（为空 = 冷启动回看），`ToTs` = `now − ScanDelay`（停摆时封顶） | `FvTurn` | 4.1 |
| ② 读心跳算名单 | 按四类形态分 Worker、算当前环（见 3.2） | — | 3.2 |
| ③ 归流派活与写待办 | 行索引 `composite` 聚合（`ENV`/`HOSTIP`/`SERVER_ID` 三源 + `system.name` 过滤），`@timestamp ∈ [FromTs, ToTs)` 左闭右开，`must_not` 剔 `SERVER_CATEGORY ∈ COMM_RCV/COMM_SND/POLL`（这三族照采照落、派生层不建块）；逐流算环落点写待办 | 行索引 + `FvTask` | 4.2 |
| ④ 校正存量 | 4a 归属校正 + 4b 兜底回收，快慢轮次共用（见 §5） | `FvTask` + `FvStream` | 5 |
| ⑤ 推游标与整轮作废 | 本轮结束把算出的 `ToTs` 写回作下一轮左端；基础名单为空则整轮回滚、游标不推 | `FvTurn` | 4.3 |

定区间口径：

- **左端 `FromTs`** = 上一轮 `ToTs`；游标为空（新起服务）= `now − ColdLookback`（冷启动回看，默认 1h，配置值）。左端取上一轮右端而不是墙钟窗口——停摆再恢复时墙钟窗口会把停摆那段跳过去、永久漏扫。
- **右端 `ToTs`** = `now − ScanDelay`（延迟余量，默认 10s，配置值）。OS refresh 5s，取 10s 覆盖两个刷新窗口，此刻 `now − 10s` 之前入库的行必然已可见。
- **停摆保护**：若 `now − ScanDelay − FromTs > ColdLookback`，右端封顶为 `FromTs + ColdLookback`——一轮最多推进一个回看窗口，分轮追平，既不漏扫也不撑爆单轮。
- **比较字段**：只比行索引 `@timestamp`（入库时刻，Logstash 写出时赋当前时刻），**不用 `LOG_TIME`**（业务机时钟可能被校正）。
- **无缝推进**：区间左闭右开 `[FromTs, ToTs)`，本轮右端直接作下一轮左端，轮次之间无空隙、步长 = 周期 30s；周期与 `@timestamp` 脱钩，不设「延迟区 / L ≥ 周期」约束。

#### 4.2 归流派活与写待办

**(1) 查行索引归流**：一个轮次打一次。三个 `composite` 源就是锁流三元组，一个桶 = 一条流；`after_key` 翻页，翻完才算归完（区间口径见 4.1）。读走别名 `mes-log-line-read`：

```json
POST mes-log-line-read/_search
{
  "size": 0,
  "track_total_hits": false,
  "query": { "bool": {
    "filter": [
      { "term": { "system.name": "MES-300Works" } },
      { "range": { "@timestamp": { "gte": "2026-11-19T09:00:00.000+08:00",
                                   "lt":  "2026-11-19T09:00:30.000+08:00" } } }
    ],
    "must_not": [
      { "terms": { "SERVER_CATEGORY": ["COMM_RCV", "COMM_SND", "POLL"] } }
    ] } },
  "aggs": {
    "streams": {
      "composite": {
        "size": 1000,
        "sources": [
          { "env":      { "terms": { "field": "ENV" } } },
          { "hostip":   { "terms": { "field": "HOSTIP" } } },
          { "serverId": { "terms": { "field": "SERVER_ID" } } }
        ]
      }
    }
  }
}
```

- **区间左闭右开**：`gte FromTs` + `lt ToTs`，就是 4.1 算出的 `[FromTs, ToTs)`。`FromTs` = 上轮右端（冷启动取 `now − ColdLookback`），`ToTs` = `now − ScanDelay`（停摆时封顶）。示例里的两个时刻只示意形态，实际每次按本轮游标算。
- **时间字段是 `@timestamp`（入库时刻）**，不是 `LOG_TIME`。`@timestamp` 在 Logstash 写出前覆盖成当前时刻，与「可见」只差 refresh（≤5s）；`ScanDelay` 10s 覆盖两个刷新窗口。
- **翻页**：响应的 `after_key` 原样填进 `composite.after` 再打一次，直到无 `after_key`；`size` 是每页**桶数**、不是行数。首屏不带 `after`。键名跟 `sources` 里的别名一致（`env` / `hostip` / `serverId`），不是字段名。
- **`size: 0`、不取 `_source`**：归流只认三个 `composite` 源，行正文由 Worker 自己拉；子聚合也不需要——游标无条件推 `ToTs`，不取本批 `max(@timestamp)`。
- **过滤**：`system.name` 先把行收窄到 MES；`must_not` 剔 `SERVER_CATEGORY ∈ COMM_RCV/COMM_SND/POLL`（这三族照采照落、派生层不建块）。按**类别**比、不按带编号的 `SERVER_ID` 比。

**(2) 写待办**：一条流一句 `MERGE`，不存在则插、已存在覆盖回 `Pending`（含 `Processing` 也覆盖——语义是「处理期间这条流又来了新行」）；`Reason = 'NEW_LINE'`。**正在 `Processing` 的流粘住原 Worker**：`Worker` 列不写本轮环落点、保持原值，新行继续喂给手上那个人，不重新摊派；只有那条 `Processing` 超时被 4b 触发①收回后，落点才按当前环重排。这样即便环成员变了（有机器上下线），同流的活也不会在半途换人。新落点只用于新流和 `Pending` 行。覆盖不打断正在跑的 Worker，而是给它一个自检：Worker 收工那句 `DELETE … WHERE Status='Processing'` 会因行已被覆盖成 `Pending` 而影响 0 行，删不掉、留在表里等下一轮领走。**拿 `Status` 本身当版本号，不需要额外令牌列。** 待办单位是「流」不是「块」，块由 Worker 自己切、Scheduler 连行正文都不看。

```sql
MERGE INTO FvTask t
USING (SELECT StreamKey, Worker FROM TABLE(:本轮流清单)) s
   ON (t.StreamKey = s.StreamKey)
 WHEN MATCHED THEN UPDATE
   SET t.Status = 'Pending',
       t.Worker = CASE WHEN t.Status = 'Processing' THEN t.Worker ELSE s.Worker END,  -- Processing 粘原 Worker
       t.Reason = :reason,
       t.ProgressAt = CASE WHEN t.Status = 'Processing' THEN :now ELSE t.ProgressAt END
 WHEN NOT MATCHED THEN INSERT (StreamKey, Status, Worker, Reason, ProgressAt)
   VALUES (s.StreamKey, 'Pending', s.Worker, :reason, :now);
```

#### 4.3 推游标与整轮作废

- **无条件推**：无论有没有读到新日志，本轮结束都把算出的 `ToTs` 写回 `FvTurn.ToTs`，作为下一轮左端；有没有活都推进，轮次之间不留空隙。
- **唯一例外——没有可用 Worker**：基础名单为空就没有落点，整轮回滚事务——游标不推、待办不写，等同本轮没跑；等 Worker 回来从原 `FromTs` 重扫，那批行一行不少。能走到这句的只有全员掉线或全员 `DEGRADED`。

### 5 校正存量：4a 与 4b

这是快轮次五步表的第 ⑤ 步（节 4.1 表）。第 ③ 步「归流派活」只管本轮新发现的活，这两句管「第 ③ 步不会再碰到的老行」——节点没了、环变了，都不会出现在增量行里。两句都用 `FvStream` 关联出当前环落点，`:新环落点` 逐行不同、不能当单值绑定变量。

```sql
-- 4a 归属校正：环变过，把非处理中的行改到新落点。只搬地址，不动时间戳
MERGE INTO FvTask t
USING (SELECT StreamKey, Worker AS newWorker FROM FvStream) s
   ON (t.StreamKey = s.StreamKey AND t.Worker <> s.newWorker AND t.Status <> 'Processing')
 WHEN MATCHED THEN UPDATE SET t.Worker = s.newWorker;

-- 4b 兜底回收：两个触发源，任一命中就把 Processing 放回 Pending
MERGE INTO FvTask t
USING (SELECT StreamKey, Worker AS newWorker FROM FvStream) s
   ON (t.StreamKey = s.StreamKey AND t.Status = 'Processing'
       AND (t.ProgressAt < :now - :ReclaimAfterSeconds   -- ① 节点还活着，但这条卡住了
            OR t.Worker IN (:退活名单)))                   -- ② 节点死了 / 降级了
 WHEN MATCHED THEN UPDATE
   SET t.Status = 'Pending', t.Worker = s.newWorker, t.ProgressAt = :now;
```

- **4a 跳过 `Processing`**：那条活还在原 Worker 手上跑，此刻动归属只会制造半截状态——它要么正常收工（行被 `DELETE`），要么由 4b 回收。**4a 不写 `ProgressAt`**：搬地址不改变「这条流从什么时候开始等人捞」，刷成 `now` 会让摘环判据永远看不到老行。
- **4b 触发①**：`ProgressAt` 在 `Processing` 上是**进度戳**——领活写一次，处理途中每跳长 IO（分页拉行 / 写块 / 读库）之前推进一次。判据是「距上次进度刷新超过阈值」，不是「这条流跑了多久」：合法跑十分钟的大流不会被误放回，某跳卡死则最多一个阈值就被捞回。阈值只需大于「两次进度刷新的最大间隔」。误放只白做一段（重放幂等），不出错数据。
- **4b 触发②**：判死阈值（`3 × 心跳间隔`，默认 30s）比回收阈值（默认 300s）快一个数量级——节点都判死了，不必再干等五分钟；降级同理。退回后归属按当前环重写、从锚点重新重放，不交接（进度在块文档上、不在 Worker 内存里）。

### 6 慢轮次（5 分钟）

cron `0 0/5 * * * *`（6 位带秒位），每 5 分钟一次——恰好卡在静默期（10min）的一半，块进入静默后最多再等一个周期必被发现。同样抢 `Cycle='SLOW'` 的行锁、同样读心跳算名单与 4a/4b 校正、基础名单空同样整轮作废。差别只在「发现」这一步——快轮次问「谁刚写了日志」，它问「每条流的最后一块是不是好久没写」：

- 查询只碰块索引，`Reason = 'SILENCE'`，**只认每条流的最后一块**（`ORDER_BY` 降序第一）、不看同流其余块，不推游标。分桶本身不排序、不限流（`composite` 翻页 size 200）；桶内取最新块要排序。读走别名 `mes-log-exec-read`：

```json
POST mes-log-exec-read/_search
{
  "size": 0,
  "track_total_hits": false,
  "query": { "bool": { "filter": [
    { "term": { "system.name": "MES-300Works" } }
  ] } },
  "aggs": {
    "streams": {
      "composite": {
        "size": 200,
        "sources": [
          { "env":      { "terms": { "field": "ENV" } } },
          { "hostip":   { "terms": { "field": "HOSTIP" } } },
          { "serverId": { "terms": { "field": "SERVER_ID" } } }
        ]
      },
      "aggs": {
        "latest": {
          "top_hits": {
            "size": 1,
            "sort": [ { "ORDER_BY": { "order": "desc" } } ],
            "_source": ["ORDER_BY", "EXEC_STATUS", "LAST_LINE_TIME", "RULENAME"]
          }
        }
      }
    }
  }
}
```

- **两把尺，各管一件事**：取「最后一块」按 `ORDER_BY`（块处理序，建块时写死、单调增）；判「是否静默」按取回那块的 `LAST_LINE_TIME`（末行日志时间，日志格式 `yyyy/MM/dd HH:mm:ss.SSS`）。**不能用 `LAST_LINE_TIME` 排序定最后一块**——它会随重放回写，只说明「哪块最近有行」、不说明「哪块最后建」；先建的处理中块末行时间可能比后建的新块还晚，按它 desc 会取错块。
- **取块过程**：query 层**不加** `EXEC_STATUS` / `LAST_LINE_TIME` 前置过滤——先把超期块筛出来再取最新，取到的可能是老残留块、不是当前边界块。改为每桶 `top_hits` 按 `ORDER_BY` 降序取 1 篇，就是该流的边界块；应用层再判它 `EXEC_STATUS='进行中'` 且 `now − LAST_LINE_TIME ≥ N`（N = 静默期 `SilenceMinutes`，默认 10 分钟，配置值，**归 Worker 的参数、见 §五**；解析成时刻后比 `now−N`，别按墙钟 ISO 解析），命中才写待办，同流更早的块一律不看。慢轮次只拿它「发现」该封口的流，真正封口判定在 Worker 静默封口兜底（§四 6.6）；两边必须用同一个 `N`。
- **与 Worker 同一把尺**：排序键 `ORDER_BY` 与 Worker 取块（§四 1）完全相同，慢轮次认定的边界块就是 Worker 会封口的那块，发现与封口必然一致。`ORDER_BY` 建块时写死、不受 `doc_as_upsert` 重放影响（不像 `@timestamp` 补建为空），排序稳定；慢轮次只负责把流交出去、不指定封哪块。
- **桶 = 流，不是块**：三个 `composite` 源拼成 `streamKey`，命中才写一条待办；一条流最多一条。翻页同快轮次（`after_key` 原样回填），首屏不带 `after`，`composite` 桶不排序、不带 `sort`。
- **只扫块索引**：判静默要的「块末行日志时间」块文档上有（`LAST_LINE_TIME`）；慢轮次不推游标，query 没有任何时间区间参数——停摆再久，块还挂「进行中」就照样扫得到。
- **静默已降为极低频兜底**（人为杀进程一类，概率约 0.1%）：正常执行由 `PUB_SEND_SMALL` 秒级闭口，根本走不到静默；因此这个轮次绝大多数时间是空转，查询命中极少是设计预期。
- 它只负责「把该看的流交出去」，块怎么封由 Worker 决定；不在调度事务里跨库改块（汇总索引写入方只有 Worker）。覆盖待办走与快轮次同一句 `MERGE`，不刷 `ProgressAt`（走同状态覆盖不动那一条规则）。

### 7 节点登记与心跳上报

Scheduler 也是 `FvNode` 里的一行（`Role = 'SCHEDULER'`）。这条记录**只作指标、不参与任何判活**——Scheduler 是单点、没有别人摘它，算环只取 `Role = 'WORKER'` 的行；它的唯一用途是让「Scheduler 全挂」可被发现（心跳停更且非 `DRAINING`，新日志不再被发现而 Worker 仍在消耗存量，表面看不出异常）。

**心跳节奏**：Scheduler 每 **10s** 上报一次，复用 Worker 的 `HeartbeatSeconds`（默认 10s，见 §五），不新增 Scheduler 专属参数。心跳由独立定时器驱动，不挂在快 / 慢轮次锁里——轮次抢锁失败或卡住都不影响 `LastSeen` 刷新。

**三个写库时机**：

| 时机 | 动作 | 写哪些栏位 |
|---|---|---|
| 服务启动 | 不存在则插入自己这一行 | `NodeId` / `Role` / `State` / `LastSeen` / `FailStreak` / `StartedAt` 全填（见下表） |
| 此后每 10s（心跳周期） | 已存在则只刷新心跳时刻 | **只写 `LastSeen = now`**，其余栏位一律不动 |
| 收到终止信号（优雅下线） | 退出钩子同步改本节点 | **只写 `State = 'DRAINING'`**；`LastSeen` / `FailStreak` / `StartedAt` 一律不动 |

**启动插入时各栏位存什么值**（`NodeId` 为业务 UK，一行一条）：

| 栏位 | 存什么值 |
|---|---|
| `NodeId` | `scheduler-<部署注入的固定槽位名>`（如 `scheduler-01`），按 §7.1 生成法则；前缀与 Worker 分开，不重名 |
| `Role` | 固定 `SCHEDULER` |
| `State` | 启动时 `ONLINE`；Scheduler 不降级，收到终止信号时由退出钩子改 `DRAINING` |
| `LastSeen` | 当前时刻 `now` |
| `FailStreak` | 固定 0（列非空，Scheduler 不参与失败降级，占位） |
| `StartedAt` | 当前时刻 `now`（本次启动时刻，之后不再改） |
| `ID` / 审计四字段 | 底层统一赋值，业务写入不涉及 |

心跳每 10s 只刷 `LastSeen`，`FailStreak` 恒 0、`StartedAt` 保持启动值；`State` 启动 `ONLINE`、优雅退出改 `DRAINING`。外部看 `Role = 'SCHEDULER'` 那行的 `LastSeen` 停更且 `State <> 'DRAINING'` 才报「Scheduler 全挂」（见 §六）；`DRAINING` 是计划内退出标记，随后心跳停更是预期。

**优雅下线怎么更新**：Scheduler 的退出钩子只做一件事——按自己的 `NodeId` 把 `FvNode.State` 改成 `DRAINING`，不删行、不改别的栏位；改完即停心跳定时器。`DRAINING` 对 Scheduler 只是指标：它不在环里、不参与判活，Worker 照常领存量待办；与 Worker 下线同一套状态值，Worker 的 `DRAINING` 由 §三 3.2 第 4 点处理名下待办（名下 `Processing` 跑完、`Pending` 由 4a 改派）。

#### 7.1 NodeId 生成法则

`FvNode.NodeId` 既是业务 UK，又是哈希环的挂点种子（`NodeId + '#' + i`，见 3.1），还写进 `FvTask.Worker` / `FvStream.Worker` 作归属值——所以必须**全局唯一 + 跨重启稳定**：

- **谁生成**：部署层注入（容器环境变量 / 编排配置），进程启动时读入，不在代码里现算、不用随机数。
- **格式**：`<角色前缀>-<固定名>`，Worker 用 `worker-<槽位名>`、Scheduler 用 `scheduler-<槽位名>`；前缀把两类角色分开，保证不与 Worker 重名。
- **跨重启稳定的硬要求**：同一个部署槽位重启 / 重建后必须拿到**相同的 `NodeId`**。环的虚拟点按 `NodeId` 展开，ID 一变落点全变、待办全被改派，重建一台等于洗一次牌；毒丸流那条（§六）"NODE_ID 不变 → 环不变 → 仍落同一台"也依赖这一点。
- **长度**：按 `FvNode.NodeId` 的 ≤64 字符约束，槽位名取短名即可。
- Worker 起步 3 台 × 5 个 = 15 个槽位，每槽位一个固定 `NodeId`（如 `worker-ap1-01`）；Scheduler 单点一个（如 `scheduler-01`）。

**NodeId 的写入（Scheduler 与 Worker 同一套）**：进程启动时读入部署注入的 `NodeId`，写进 `FvNode.NodeId`（业务 UK）——只在「服务启动」那个时机写全栏位（Scheduler 见 §三 7、Worker 见 §四 1.1），此后的心跳与终止都按这个 `NodeId` 定位本节点那一行，**不改写 `NodeId` 本身**。同一个值还作为归属值写进 `FvTask.Worker`（Scheduler 归流派活时写）与 `FvStream.Worker`（Scheduler 重算环时写）；Worker 自己不写这两列，只按 `Worker = 自身 NodeId` 领活。因为同槽位重启拿到相同 `NodeId`，重启后定位的还是 `FvNode` 里同一行、环上虚拟点也不变。

配置参数统一见 §五「配置参数」（Scheduler 与 Worker 合表，本节不重复维护）。

## 四、Worker

单线程循环：处理完就再查，没有 cron、不并发，所以不需要同机防重入。领到一条活 = 一次「轮询领活 → 取块分流 → Case 1/2/3 → 二级重排 → 重放归并 → 写块 → 收工」。进程内不缓存，`FvTask` 是唯一来源。`Reason = NEW_LINE`（新行）/ `SILENCE`（静默）只是来源标记，**两类不分开处理**——都先走 Case 1/2/3，静默封口是流程走完后的统一兜底（§6.6）。

### 1 启动与登记

Worker 是独立进程，部署与启停同 Scheduler（可同机、可分开）。**Worker 没有轮次表，启动不做轮次校验**——轮次表（`FvTurn`）是 Scheduler 派活机制的前提，Worker 既不读轮次游标、也不抢轮次锁，与这层无关。启动时只做一件事：登记自己到心跳表 `FvNode`。

#### 1.1 节点登记与心跳上报

Worker 是 `FvNode` 里的一行（`Role = 'WORKER'`），节点自己写、Scheduler 只读。写法与 Scheduler（§三 7）完全相同：**三个写库时机 + 启动插入时各栏位存什么值**，两张表写清即可，不另写 SQL。

**三个写库时机**：

| 时机 | 动作 | 写哪些栏位 |
|---|---|---|
| 服务启动 | 不存在则插入自己这一行 | `NodeId` / `Role` / `State` / `LastSeen` / `FailStreak` / `StartedAt` 全填（见下表） |
| 此后每 `HeartbeatSeconds`（10s，心跳周期） | 已存在则只刷新心跳时刻 | **只写 `LastSeen = now`**，其余栏位一律不动 |
| 收到终止信号（优雅下线） | 退出钩子同步改本节点 | **只写 `State = 'DRAINING'`**；`LastSeen` / `FailStreak` / `StartedAt` 一律不动 |

**启动插入时各栏位存什么值**（`NodeId` 为业务 UK，一行一条）：

| 栏位 | 存什么值 |
|---|---|
| `NodeId` | `worker-<部署注入的固定槽位名>`（如 `worker-ap1-01`），按 §三 7.1 生成法则；每槽位一个固定值、跨重启不变，与 Scheduler 前缀不同 |
| `Role` | 固定 `WORKER` |
| `State` | 启动时 `ONLINE`；降级与退出由 §六失败三档写，收到终止信号时由退出钩子改 `DRAINING` |
| `LastSeen` | 当前时刻 `now` |
| `FailStreak` | 启动时 0（列非空占位；降级累加 / 恢复清零见 §六失败三档） |
| `StartedAt` | 当前时刻 `now`（本次启动时刻，之后不再改） |
| `ID` / 审计四字段 | 底层统一赋值，业务写入不涉及 |

心跳由独立定时器驱动，不挂在领活循环里——领活卡住不影响 `LastSeen` 刷新。`NodeId` 按 §三 7.1 生成法则取值、与 Scheduler 不重名；`State` / `FailStreak` / `DegradedAt` 的写（降级、退出）见 §六失败三档。Worker 置 `DRAINING` 后名下 `Processing` 跑完、`Pending` 由 Scheduler 的 4a 改派（那是 Scheduler 的活、Worker 不碰）。

### 2 领活（1s 轮询）

每 `PollIntervalSeconds`（1s）查 `FvTask` 里 `Worker = 我` 且 `Status='Pending'` 的候选，原子占位——影响 1 行才算领到，影响 0 行说明被别人领走或已被覆盖，跳过、进入下一轮。进程内不缓存：

```sql
UPDATE FvTask SET Status = 'Processing', ProgressAt = :now
 WHERE StreamKey = :pick AND Status = 'Pending';
```

- **进度戳（`ProgressAt`）**：领活写一次；处理途中每跳长 IO（分页拉行 / 写块 / 读库）之前推进一次——判据是「距上次刷新超阈值」不是「跑了多久」，合法大流不被误放回、卡死最多一个回收阈值就被捞回（4b 触发①见 §三 5；回收归 Scheduler，Worker 只负责推进）：

```sql
UPDATE FvTask SET ProgressAt = :now
 WHERE StreamKey = :pick AND Status = 'Processing';
```

  进度刷新失败只记日志、继续处理（辅助动作，不中断正事）。`Pending → Pending` 的同状态覆盖由触发器兜住、不刷戳（见 §1.1 表规范）。
- **活两类**：`NEW_LINE`（快轮次新行）/ `SILENCE`（慢轮次静默），由 Scheduler 写待办时的 `Reason` 区分；两类**不分开处理**，都先走 Case 1/2/3（静默封口兜底见 §6.6）。

### 3 取块与分流

按 Scheduler 给的 `StreamKey`（`ENV|HOSTIP|SERVER_ID` 三元组）在**块索引** `mes-log-exec-read` 上按 `ORDER_BY` **降序**取最新一块（`size: 1`），它是当前边界，新行只会落在它之后。

> **进度戳**：本跳是 OS 长 IO，执行前按 §2 检查 `ProgressAt`——距上次刷新超阈值才推进，不是每跳都写。

```json
POST mes-log-exec-read/_search
{
  "size": 1,
  "track_total_hits": false,
  "query": { "bool": { "filter": [
    { "term": { "ENV": "..." } },
    { "term": { "HOSTIP": "..." } },
    { "term": { "SERVER_ID": "..." } }
  ] } },
  "sort": [ { "ORDER_BY": { "order": "desc" } } ]
}
```

**判「哪块最新/最后」一律按 `ORDER_BY` 降序**——取块、Case 分流、尾部兜底（§6.4）三处同尺；`ORDER_BY` 建块时写死、单调增、不受重放回写影响。超时封口的块照常参与「哪块最新」判定、不被跳过。

| 最新块状态 | 走哪个 Case |
|---|---|
| 一条流一块都没有 | Case 1：翻找 `REQ_BEGIN` 建第一个块（§4） |
| 进行中 | Case 2：从 `StartTime` 逐页重放（§6） |
| 已完成 / 中断 / 超时封口（终态） | Case 3：从 `EndTime` 往后翻找下一个 `REQ_BEGIN` 建新块（§5）；**超时封口按「完成」处理** |

终态三态语义不同但都不可再写：`已完成` = 正常执行结束、`中断` = 被重启截断、`超时封口` = 静默兜底截断。

- **流转**：Case 1 / Case 3 若建成新块（新块=进行中），本轮不结束，**带着 Case 进入 Case 2**；没找到 `REQ_BEGIN` 建不成块，本轮直接结束、删 Task，下一轮重来。
- **老块收尾**：取块的同时，把同一条流上 `ORDER_BY` 比最新块小、且仍是「进行中」的块**直接封「中断」**——不重放、不动右端三参数（取块上已有的值）。这类块只可能是更早那篇的边界没被识别到（处理期间宕机 / 重启 / 环境名变更留下的残留），边界已不可能靠「下一条开始标志到达」补上（后面的行早被新块切走）。快慢轮次派来的活都做这一步。

### 4 Case 1：无块建块

从行索引读该流的行，卡点字段 = 行文档 **`@timestamp`**（入库时刻），条件 **`@timestamp > now − ColdLookback`**（1h，严格 gt、真左开），**不设右端**，按 `@timestamp` 排序。

> **进度戳**：每翻一页都是一次 OS 长 IO，翻页前按 §2 检查 `ProgressAt`——距上次刷新超阈值才推进，不是每页都写。

```json
POST mes-log-line-read/_search
{
  "size": 200,
  "track_total_hits": false,
  "query": { "bool": { "filter": [
    { "term": { "system.name": "MES-300Works" } },
    { "term": { "ENV": "..." } },
    { "term": { "HOSTIP": "..." } },
    { "term": { "SERVER_ID": "..." } },
    { "range": { "@timestamp": { "gt": "2026-11-19T09:00:00.000+08:00" } } }
  ] } },
  "sort": [ { "@timestamp": { "order": "asc" } }, { "_id": { "order": "asc" } } ]
}
```

- **200 行/页翻页**：首屏不带 `search_after`；每页取回先做二级重排（§7），再从第一页开始找 `MSG_KIND = REQ_BEGIN`，找到即停页；没找到用本页排序后末行的 `@timestamp` / `_id` 作 `search_after` 翻下一页，直到翻页结束。示例时刻只示意形态，实际按 `now − ColdLookback` 算。
- **命中 Begin**：用该行**建块**，但**不重放**，只解析块首行（七个业务字段，见 §8.1 第一类，算法见 `06-附录A-块首行解析方案.md`）；建完 Case 1 结束。**成功则带着 Case 进入 Case 2**（§6）。
- **翻完都没找到**：本轮结束、**删 `FvTask` 那条 Task**，不看后续 Case；下一轮仍以 `now − ColdLookback` 重新检索（每轮从 1h 前起，不推进起点）。

### 5 Case 3：闭口块续建

最新块为闭口块（正常闭口 / 中断 / 超时封口三态）时往下找新的首行块建块。三种闭口态**这一段流程完全相同**，唯一区别是 `PUB_SEND_SMALL` 回填（仅正常闭口）。从行索引读，卡点字段 = 行上 `LOG_TIME`，条件 **`LOG_TIME > 该块 EndTime`**（与 `LastLineTime` 同值，严格 gt、真左开），**不设右端**，按 `LOG_TIME` 排序。

> **进度戳**：每翻一页都是一次 OS 长 IO，翻页前按 §2 检查 `ProgressAt`——距上次刷新超阈值才推进，不是每页都写。

```json
POST mes-log-line-read/_search
{
  "size": 200,
  "track_total_hits": false,
  "query": { "bool": { "filter": [
    { "term": { "system.name": "MES-300Works" } },
    { "term": { "ENV": "..." } },
    { "term": { "HOSTIP": "..." } },
    { "term": { "SERVER_ID": "..." } },
    { "range": { "LOG_TIME": { "gt": "2026/11/19 09:00:00.000" } } }
  ] } },
  "sort": [ { "LOG_TIME": { "order": "asc" } }, { "_id": { "order": "asc" } } ]
}
```

- **补 `END_LINE_ID`（仅正常闭口）**：每页二级重排后，第一页开头几行若碰到 `MSG_KIND = PUB_SEND_SMALL`，只把该最新闭合块的 `END_LINE_ID` 改成**最后一个 `PUB_SEND_SMALL` 行的行 ID**；碰不到不重写。**中断 / 超时封口跳过本步、不重写 `PUB_SEND_SMALL`**。只改 `END_LINE_ID` 一个字段，不动 `END_TIME` / `LAST_LINE_TIME`。
- **往后找 `REQ_BEGIN` 建块**：和 Case 1 一样继续翻找 `REQ_BEGIN`（200/页、二级重排、找到即停），命中则解析首行建块、带着 Case 进 Case 2。翻完都找不到 → 删 Task、本轮结束，下一轮重来。

### 6 Case 2：未闭口块重放

来源：Case 1 / Case 3 新建的块，或扫描时发现的未闭口块——总之都是未闭口块。下一轮重扫的未闭合块与新建块走同一套：都是**跨页压缩累积**，翻页拿到最后一个 `PUB_SEND_SMALL` / `SERVER_START` 作结束重放；重放前先压缩、跑 Hang 匹配（§8.7）。

两个闭口标签的口径（沿用）：

- `PUB_SEND_SMALL` **只打标签不落字段**：regex `FwPublication::sendSmall:\d+ byte msg .*? reply is \S+`、护栏 `^(?!COMM_).+`（业务族打、COMM 不打，POLL 也打），加工层现成、派生层直接消费；reply 值不进库，块级成败看 `RULE_RESULT`（§8.6）、不看 `PUB_SEND_SMALL`。一块内多条时取**最后一条**定末行（撞第一条就封会把后面的发送截在块外）。
- `SERVER_START` **只闭不建**：撞到它把当前块封「中断」、不建新块，重启后下一个 `REQ_BEGIN` 才建新块；标签来源唯一（行首 `DTPFsrv` + 行内 `Command mailbox name:` 两条件都命中），启动序列变了则派生层不报错、重启闭口回落到静默兜底（最长 10min）。

#### 6.1 取行

从行索引读，起点 = 块的 `StartTime`，卡点字段 = 行上 `LOG_TIME`，条件 **`LOG_TIME >= StartTime`（左闭 gte，刻意含块首行）**，**不设右端**，按 `LOG_TIME` 排序。

> **进度戳**：每翻一页都是一次 OS 长 IO，翻页前按 §2 检查 `ProgressAt`——距上次刷新超阈值才推进，不是每页都写。

```json
POST mes-log-line-read/_search
{
  "size": 200,
  "track_total_hits": false,
  "query": { "bool": { "filter": [
    { "term": { "system.name": "MES-300Works" } },
    { "term": { "ENV": "..." } },
    { "term": { "HOSTIP": "..." } },
    { "term": { "SERVER_ID": "..." } },
    { "range": { "LOG_TIME": { "gte": "2026/11/19 09:00:00.000" } } }
  ] } },
  "sort": [ { "LOG_TIME": { "order": "asc" } }, { "_id": { "order": "asc" } } ]
}
```

对照：Case 1 `@timestamp > now−1h`、Case 3 `LOG_TIME > EndTime`、Case 2 `LOG_TIME >= StartTime`——Case 2 是左闭、有意含块首行，另两个是严格 gt。

#### 6.2 二级重排

200/页，**每翻一页都按 §7 做二级排序**，排完再找闭口标志。

#### 6.3 重放定位与跨页累积

排序后从 `_id = 块的 START_LINE_ID` 那行往后找 `MSG_KIND = SERVER_START` 或 `PUB_SEND_SMALL`，用 Start Line ID 到「最后一个 `PUB_SEND_SMALL` / `SERVER_START` 之前」的行重放：

- **本页找到**：先清理 `MSG_KIND = OTHER` 行（参与重放的行都已排好序），跑 Hang 匹配（§8.7），再重放、闭口。
- **本页没找到 → 跨页累积**：
  1. 对「Start Line ID → 本页最后一行」压缩，只保留参与重放的行（含 Hang 标志行）；
  2. 以本页最后一行的 `LOG_TIME` 作**左端（gte）**再翻 200 行一页，继续找；
  3. 找到 → 闭口当前块，把**之前各页压缩留存的行一起拿出来统一重放**（不是只重放当前页）。
- **重放后往前翻建新块**：闭口重放完和 Case 3 一样，以闭口块的 `EndTime` 作**左开（gt）**翻页找新 `REQ_BEGIN` 建块，重复到翻页结束；新页仍找不到闭口标志就回到跨页累积，直到找到或翻页结束。

#### 6.4 尾部块兜底

按 `ORDER_BY` 降序判定为**流上最后一个块**（尾部块）、从 Start Line ID 一路翻到末尾都没碰 `PUB_SEND_SMALL` / `SERVER_START` 时：

1. **不留到下一轮**，以当前块 Start Line ID 到翻到的最后一行做重放；重放前照旧压缩、找 Hang List。
2. **End 只取最后一行的值**：`END_LINE_ID` = 最后一行 ID；`END_TIME` = 最后一行 `LOG_TIME`；`LAST_LINE_TIME` 同值。建块时确定的字段不变。
3. **状态保持「进行中」**：这条兜底重放**不封口**，`EXEC_STATUS` 维持进行中，终态字段（`CLOSE_TIME` / `TOTAL_COST_MS` 等）不在此写；封口交给 §6.6 静默兜底。

#### 6.5 非尾部块翻到末尾没找到

该块**不闭口**，留到下一轮再做；本轮收尾**清理 Task**（删掉，避免一直挂 `Processing`）。下一轮仍是未闭口块、再进 Case 2，起点仍是其 `StartTime`。

#### 6.6 静默封口兜底

Case 1/2/3 走完后，对**该流上所有块**逐一检查超时封口——不只看最后一个块；只对仍「进行中」的块判，已闭口的跳过：

1. **统一入口**：不按 `Reason` 分流，`NEW_LINE` / `SILENCE` 都先走 Case 1/2/3；封口兜底只在 Case 流程之后做。
2. **Case 2 已封口**：块已在 Case 2 撞 `PUB_SEND_SMALL` / `SERVER_START` 正常闭口 → 不处理静默期，按正常闭口收尾。
3. **仍进行中 + SILENCE**：块仍「进行中」且 task `Reason = SILENCE` 时，逐块算 `now − 该块 LAST_LINE_TIME`，**≥ 10min**（`SilenceMinutes`）改「**超时闭口**」。`NEW_LINE` 任务不做静默封口。
4. **字段回归 `LAST_LINE_TIME`**：与 06 旧第③档、慢轮次（§三 6）同尺；`LAST_LINE_TIME` 走日志格式 `yyyy/MM/dd HH:mm:ss.SSS`、按日志格式解析、不走墙钟 ISO。新差异只在流程：不按 reason 分流先走 Case、封口兜底只在 SILENCE 做、检查范围扩到全流所有进行中块。

封成「超时封口」后不再解封、不再重放（静默封口即终局）；原来「封口 → 尾行到达 → 重新打开」（`REOPEN_LOG`、路 4 重启支、≥3 行门槛）整段取消、块索引字段里也没有 `REOPEN_LOG`。静默之后才到的尾行按终态处理（Case 3 从 `EndTime` 往后找下一个 `REQ_BEGIN`），不撞开始标志就不进任何块——概率约 0.1% 而接受。

### 7 每页二级重排（Case 1/2/3 共用）

每页 200 行可能来自不同文件或同一文件，取回顺序不是日志真实顺序，做后续动作前必须摆回真实顺序。**每翻一页都排一次**：

1. 按 `LOG_FINGERPRINT` 分堆（一个文件一堆）。MES 日志一页 5 万多行，99.99% 的 200 行只分两堆（经验概率、非硬封顶）。
2. **只有一堆**：堆内按 `LOG_OFFSET` 升序。
3. **两堆**：以每堆 `LOG_FINGERPRINT` 回行文档找该堆**首行**（堆内 `LOG_OFFSET` 最小或为 0 那行）的 `LOG_TIME`，按 `LOG_TIME` 排堆；堆内仍按 `LOG_OFFSET` 升序。不再另设 tie 规则。

> **进度戳**：这里每堆一次回行文档点查也是 OS 长 IO（每翻页、每堆各一次），执行前按 §2 检查 `ProgressAt`——距上次刷新超阈值才推进，不是每次都写。

```json
POST mes-log-line-read/_search
{
  "size": 1,
  "_source": ["LOG_TIME"],
  "query": { "bool": { "filter": [
    { "term": { "LOG_FINGERPRINT": "..." } }
  ] } },
  "sort": [ { "LOG_OFFSET": { "order": "asc" } } ]
}
```

4. **记指纹顺序供下轮复用**：每次重排后记下 `LOG_FINGERPRINT` 的排序顺序，作下一次重排的依据——下次直接用、不再回行索引找 `LOG_TIME`（省一次点查）。

排完的序列逐行标 5 位序号（建块拼 `ORDER_BY` 用）。**这不等于 `LOG_TIME` 序**：同厘秒多行只有 offset 分得出先后、跨滚动点两个文件各自从 0 起算 offset、业务机时钟可能被校正。重排时顺带守门：同指纹内 `LOG_TIME` 随 `LOG_OFFSET` 单调不减（违例按文件计数告警）、堆间「前堆末行 `LOG_TIME` ≤ 后堆首行 `LOG_TIME`」（违例按流计数）；值已写进索引、不自动修复，只暴露。

（原「20000 行一个单位整体排一次、堆间 tie 比文件首行 `LOG_TIME`」口径作废。）

### 8 重放归并算法

拿到参与重放的行后先剔 `MSG_KIND = OTHER` 行；参与重放的都是 §7 排好序的序列。按下面各节归并出块字段。

#### 8.1 闭口写块字段

- **一、块首行解析出的七个业务字段**（建块时定、闭口不再算）：`RULENAME` / `LOTID` / `EQPID` / `PORTID` / `CARRIERID` / `USERID` / `TID`——字段名**无下划线**，按出现顺序追加、同值去重、取不到留空；算法见 `06-附录A-块首行解析方案.md`（唯一权威），本文不写。只解析块首行这一行、一块一次，块已存在且七字段有值就不解析。
- **二、建块时确定、闭口不再算的其余字段**：
  - **非首行解析、照抄或派生**：`ENV` / `HOSTIP` / `SERVER_ID`（锁流三元组，从行文档照抄）、`SERVER_CATEGORY` / `SERVER_NUMBER`（加工层从 `SERVER_ID` 反推）、`system.name`（采集端注入常量）——这六个不是首行解析来的，别混进七字段。
  - **建块即定**：`START_LINE_ID` / `REQUEST_TYPE` / `ORDER_BY` / `START_TIME`，另含 `@timestamp`（只在建块 `_create` 写一次）。
- **三、闭口时新算**：
  - `END_LINE_ID` = 最后一个 `PUB_SEND_SMALL` 行的 ID（Case 3 回填、Case 2 闭口一致；尾部兜底取最后一行）。
  - `END_TIME` = 最后一个 `PUB_SEND_SMALL` 行的 `LOG_TIME`（尾部兜底取最后一行）。
  - `LAST_LINE_TIME` = `END_TIME`（同值）。
  - `CLOSE_TIME` = 当前时刻。
  - `EXEC_STATUS` = `已完成`（撞 `PUB_SEND_SMALL` 的正常闭口）。
  - `TOTAL_COST_MS` = `END_TIME − START_TIME`（首尾相减）。

#### 8.2 COST_BREAKDOWN · CALL 类

按行的 `CALL_SYS` 分类，每个 `CALL_SYS` 开一行：`Item = CALL`、`Group = 该 CALL_SYS`。从上到下逐轮配对：

1. 碰 `MSG_KIND = CALL_REQ` → 计数 +1、标记本轮开始；
2. 碰 `CALL_RSP` / `CALL_NOWAIT` / `CALL_ERR` → 结束本轮、算耗时：
   - `CALL_NOWAIT` 结束 → 本轮耗时 0；
   - `CALL_RSP` / `CALL_ERR` 结束 → 开始与结束两行时间差（毫秒）；
   - 扫到结束都拿不到这三个标志 → 耗时 0。
3. 耗时 0 的两类轮（`CALL_NOWAIT`、拿不到结束标志）**仍计入 `Count`**，耗时记 0。
4. 聚合：轮数 → `Count`、最大单轮 → `Max_MS`、各轮之和 → `Sum_MS`。
5. 边界：第一轮开始行 `LOG_TIME` → `First_Begin_TS`；最后一轮 `CALL_RSP` / `CALL_ERR` 结束行 `LOG_TIME` → `Last_End_TS`。

#### 8.3 COST_BREAKDOWN · LOCK 类

取 `MSG_KIND = LOCK_BEGIN` 的行，每个开一行：`Item = Lock`、`Group = LOCK_OBJ + ':' + LOCK_ID`。

1. 配对：`LOCK_BEGIN` 之后**第一个 `LOCK_END`** 且 `LockObj` / `LockId` 能对上的作结束行；
2. 耗时：两行时间差（毫秒），同时写 `Sum_MS` 和 `Max_MS`（单轮、二者相等）；`Count` 恒 1；
3. 边界：Begin 的 `LOG_TIME` → `First_Begin_TS`、End 的 `LOG_TIME` → `Last_End_TS`；
4. 找不到对应 `LOCK_END`：`Sum_MS` / `Max_MS` 记 0、`Count` 仍 1、`Last_End_TS` 为空。

#### 8.4 块级成本汇总

- `COST_SUM_MS` = 三部分之和：① `COST_BREAKDOWN` 全部行 `Sum_MS` 之和；② `INNER_RULES` 全部行 `END_TIME − START_TIME` 毫秒和（`END_TIME` 为空不计）；③ `HANG_LIST` 全部行 `HANG_COST_MS` 之和。
- `UNACCOUNTED_COST_MS` = `TOTAL_COST_MS − COST_SUM_MS`（总耗时扣掉已归类的 CALL / Lock / InnerRule / Hang，剩下的未归类耗时）。

#### 8.5 INNER_RULES

去掉 `Inner Rule` 值 = 块 `RULENAME` 的行，其余从上到下扫：碰 `MSG_KIND = INNER_RULE_START` 开一行（`Name` = 该行 Inner Rule Name、`Start_Time` = 该行 `LOG_TIME`）；往下找**第一个**「Inner Rule Name = 该 Start 的 Rule Name」且 `MSG_KIND = INNER_RULE_END` 的行，其 `LOG_TIME` 写 `END_TIME`；碰不到则 `END_TIME` 保持空。

#### 8.6 ERR_CODE / RULE_RESULT / LOCK_SEQ

- `ERR_CODE`：汇总全部 `MSG_KIND = RULE_ERR_LINE` 行的 `ERR_CODE`，**并集去重**写入块的 `ERR_CODE` keyword 多值数组（非空不代表块失败）。
- `RULE_RESULT`：取**最后一行** `MSG_KIND = RULE_REPLY` 的 `Rule Result` 值写入块 `RULE_RESULT`。
- `LOCK_SEQ`：做 LOCK_BEGIN 统计时，按重放序列**首次出现**的 `LOCK_OBJ|LOCK_ID` 逐个追加到块的 `LOCK_SEQ` 数组——首现定序、同值去重、数组保序、空 `LOCK_ID` 不进序列。

#### 8.7 HANG_LIST

1. **配置读取**：只有每轮需要执行 Case 2 时才读 `FvSrvHangConfig` 表（模块5），读取点在 Case 2 执行开始前；先按 `enabled = false` 过滤、只留 `true`；再用块 `RULENAME` 过滤出该块可用配置。不全量抓、内存短缓存 TTL 5 分钟（配置增多后迁 Redis）；查失败按「退回 `Pending`、计一次失败」处理，不按「未命中」静默跳过。
2. **压缩打标**：用行的 `Log Body` 与配置的 `start Line Like` / `end Line Like` 比较，四种模式（前模糊 / 后模糊 / 精确 / 前后均）；行符合则压缩保留、并记该行的 `Hang Reason` 与是 `Hang Start` 还是 `Hang End`。只有 `RULENAME` 命中启用配置的块才做 Hang 匹配。
3. **重放配对**：带 `Hang Reason` 的行排序后从头到尾重放：碰 `Hang Start` 找**第一个相同 `Hang Reason` 的 `Hang End`**。
4. **写 HANG_LIST**：`Hang Start` 存在 `Hang Reason` 时算时间差，**差值 > 0** 才写一行：`Start Line ID` / `Start Line Log` / `Start Time` = Start 行的 ID / `LOG_BODY` / `LOG_TIME`；`End` 几个值 = End 行对应值；`Hang Reason` = 该行 Reason；`Hang Cost Ms` = 差值毫秒。找不到 End、或差值 ≤ 0 不记。

### 9 写块、收工与幂等

写块字段赋值见 §8.1、重放归并字段见 §8。写入的幂等机制**本轮待讨论、暂沿用现状**：

- 建块（批次①）用 `_create`，已存在返回 409 忽略——不用 upsert，否则重叠重放会把已闭口终态覆盖回「进行中」。
- 重放推进（批次②）与闭口（批次③）用 `doc_as_upsert`，只带本次动过的字段；`doc` 是部分更新、不带整篇。
- 单调校验：②③ UPSERT 前先比已存 `END_TIME`，新的**不小于**它才写、比它小丢弃本次写（「不小于」而非「严格大于」——封口那次不推进右端）。
- `@timestamp` 只在建块 `_create` 写一次，`doc` 不带、②③不改。
- 写进「块首行时刻」那个月的索引（跨月执行的块写进当前月会漏捞）；索引名不带环境段、环境靠框架 `prefix`、`ENV` 照抄行文档。

`doc_as_upsert` 语句形态（写别名按框架配置）：

> **进度戳**：写块（建块 `_create` 与批次②③的 `doc_as_upsert`）是 OS 长 IO，写前按 §2 检查 `ProgressAt`——距上次刷新超阈值才推进，不是每次都写。

```json
POST mes-log-exec-write/_update/<doc_id>
{
  "doc_as_upsert": true,
  "doc": {
    "END_LINE_ID": "...", "END_TIME": "...", "LAST_LINE_TIME": "...",
    "CLOSE_TIME": "...", "EXEC_STATUS": "已完成",
    "TOTAL_COST_MS": 0, "COST_SUM_MS": 0, "UNACCOUNTED_COST_MS": 0
  }
}
```

一条流任一时刻只有一个执行体：哈希归属固定到一台 Worker、那台单线程一次只跑一条；真并发也不出错（UPSERT 幂等 + 单调校验）。除 `CLOSE_TIME` / 块 `@timestamp` 这类显式取当前时刻的字段外，其余派生值都是输入的确定函数、不含随机成分，同一输入重放多次结果一致。

**收工**：

```sql
DELETE FROM FvTask WHERE StreamKey = :pick AND Status = 'Processing';
```

影响 0 行不是错误、是自检命中——说明处理期间这条流又来了新行、待办已被覆盖回 `Pending`；行还在表里，下一轮轮询自然领走、从锚点重放到追平。「我处理期间有没有新活」交给数据库原子写，不交给时间窗或状态猜测，收工侧不需要再查一次。

## 五、配置参数（Scheduler 与 Worker 共用）

Scheduler 与 Worker 写同一份应用配置（与 Oracle 栏位同用大驼峰、不用下划线），**不各维护一套**：两边都读的参数只在下表出现一行，用「归属」列标明是 Scheduler 独有 / Worker 独有 / 两者共有。当前默认值如下，压测后回填。改值不动判定逻辑，改配置走 git 并同步文件头「配置版本」行、拷现场前备份上一份为 `.bak`。

| 参数 | 归属 | 说明 | 默认值 |
|---|---|---|---|
| `FastCycleSeconds` | Scheduler | 快轮次周期，cron `0/{N}` 秒 | 30s |
| `SlowCycleSeconds` | Scheduler | 慢轮次周期，取静默期一半（= `SilenceMinutes` ÷ 2） | 5min |
| `ScanDelay` | Scheduler | 快轮次右端 `ToTs = now − ScanDelay`，覆盖 OS refresh（5s），取两个刷新窗口 | 10s |
| `DeadThresholdSeconds` | Scheduler | 心跳判死：`now − LastSeen > DeadThresholdSeconds`，超线即摘出环 | 30s |
| `PendingStaleSeconds` | Scheduler | 摘环 / 待办卡住：`ProgressAt < now − PendingStaleSeconds`（= 判死阈值） | 30s |
| `ReclaimAfterSeconds` | Scheduler | 4b 回收①：`Processing` 进度戳超它没推进；须 > 两次进度刷新的最大间隔 | 300s |
| `PollIntervalSeconds` | Worker | 领活轮询周期，新活到达延迟上限 | 1s |
| `ReplayPageSize` | Worker | Case 取行每页行数；每页取回即做二级重排（§四 7） | 200 |
| `RetryWriteTimes` | Worker | 写块文档失败的进程内重试次数（解析、读库不重试，§六） | 3 |
| `RetryWriteBackoff` | Worker | 写块重试退避序列 | 1s / 2s / 4s |
| `SuicideAfterSeconds` | Worker | 降级观察窗：`DEGRADED` 且超它、手上没推进即退出重建（§六）；= 3 × `ReclaimAfterSeconds` | 900s |
| `ColdLookback` | 两者共有 | 冷启动左端 `now − ColdLookback`：Scheduler 作快轮次左端 / 停摆恢复单轮上限，Worker 作 Case 1 起点、每轮从此处重新检索（§四 4） | 1h |
| `SilenceMinutes` | 两者共有 | Worker 静默封口 `now − LAST_LINE_TIME ≥ SilenceMinutes`（§四 6.6）；Scheduler 慢轮次复用它发现待封口块（§三 6），并定 `SlowCycleSeconds` = 它 ÷ 2 | 10min |
| `HeartbeatSeconds` | 两者共有 | 节点心跳间隔（两角色同一张 `FvNode` 表）；判死线 = 3 × 它 | 10s |
| `FailStreakLimit` | 两者共有 | 连续失败数到顶即降级：Scheduler 退环、Worker 失败三档降级（§六） | 3 |

档次关系（密到疏）：领活 1s ＜ 判死 = 摘环 30s（= 3 × 心跳 10s）＜ 回收 300s ＜ 降级退出 900s（= 3 × 回收）；进度刷新间隔不单独定值，只要求 `ReclaimAfterSeconds` 大于两次刷新的最大间隔；`SuicideAfterSeconds` = 3 × `ReclaimAfterSeconds`、`SlowCycleSeconds` = `SilenceMinutes` ÷ 2。任一层调到与相邻层同量级，都会出「正常处理被误杀」或「故障迟迟不被发现」。新口径不再有「单位行（`unit_rows` 20000）」概念——取行按 `ReplayPageSize` 200 行/页翻、每页排一次序。

## 六、异常、兜底与恢复

失败与健康判定机制留在这里（它们直接决定 Worker / Scheduler 的行为），邮件出口不落在本文——发不发、发给谁由运维侧接。

**失败三档**（都只看本机失败累计 `FailStreak`，成功一次归零）：

| 档 | 触发 | 动作 |
|---|---|---|
| ① 进程内重试 | 写块文档失败（解析与读库不重试） | 重试 3 次、退避 1s / 2s / 4s；到头记日志 |
| ② 降级 | `FailStreak ≥ FailStreakLimit`（3） | `State = 'DEGRADED'`、写 `DegradedAt = now`：不进环、不接新流，手上那条继续跑完；成功一次回 `ONLINE`、`DegradedAt` 清空 |
| ③ 退出 | `DEGRADED` 且 `now − DegradedAt ≥ SuicideAfterSeconds`（900s），且手上那条没在推进 | 手上那条退回 `Pending`、进程退出，由编排重建（很可能换宿主机） |

- 降级是止损：Worker 失败要么自己坏了（换台机器好）、要么手上是毒丸流（换谁都一样）；摘环防止更多流被拖下水，能不能自愈交给手上那条活证明。第三档解决「降级后一直没恢复」——降级后不再有新活，只有手上那条能证明，它是毒丸就一轮轮重来，满窗退出换环境是唯一能真正改变环境的动作。
- 退出判定挂在**心跳点**上（不是失败路径）：降级后卡死（干活线程卡住、心跳照发）、降级后无活可干，两种都覆盖。基准取 `DegradedAt`（降级那一刻），不是 `LastOkAt`（跨生命周期的值，拿它当基准会一降级就误判满窗）。
- **不拿 `LastOkAt` 判活**：空闲一整天的健康节点此值必然陈旧，拿它判活会在流量来的瞬间把好机器摘出环。区分「闲着」与「卡着」靠待办表上的摘环判据（§三 3.2）。

**其余异常与兜底**：

| 情况 | 处理 |
|---|---|
| 拉行 / 读 Oracle 超时 | 这条活退回 `Pending`、`FailStreak + 1`；连退回都没写成，`ProgressAt` 变老后由 4b 兜住 |
| 进度刷新失败 | 只记日志、继续处理（它是「让 4b 别误伤」的辅助动作，失败不该中断正事） |
| 解析失败 / 行 `_id` 构造失败 | 判脏数据，跳过该行并计数，不中断该流 |
| `COST_SUM_MS > TOTAL_COST_MS` | 记异常 |
| Worker 掉线（心跳超阈值） | 摘环重算归属；非 `Processing` 行由 4a 校正，`Processing` 那行立刻由 4b 退回 |
| 节点活着但某条待办卡住 | 4b 触发①：进度时间戳超阈值即退回、按当前环改归属；心跳抓不到这类故障 |
| 全员掉线 / 全员 `DEGRADED` | 基础名单也补不出人 → 本轮整体作废（游标不推、待办不写），数据一行不丢、派生停摆，是正确的保守行为 |
| 毒丸流让节点反复「降级 → 退出 → 重建」 | `NODE_ID` 不变 → 环不变 → 同一条毒丸流又落到它头上；本期只保证可见，根治需流级隔离（已知限制） |
| 抢轮次锁失败 / Scheduler 在锁内挂掉 | 本轮放弃 / 事务整体回滚（游标没推、待办没写、归属没改），下一轮从原 `fromTs` 原样重来，不漏不重 |
| Scheduler 全挂 | `FvNode` 里 `Role = 'SCHEDULER'` 那行的 `LastSeen` 停更且 `State <> 'DRAINING'`，外部据此发现；`DRAINING` 是优雅下线的计划内标记、不报警；不产生新待办，已有待办 Worker 照常干，新日志靠持久游标在恢复后补上 |

**Scheduler 与 Worker 配置参数统一见 §五**，不再各维护一套；两边心跳共用 `HeartbeatSeconds`（默认 10s）。

**启动与恢复**：进程重启不需要恢复任何状态——锚点在块文档里，下一轮从锚点重新重放即可（选「重放」而非「内存状态机」的主要收益）。Worker 重启：待办表里 `Worker = 我` 且 `Pending` 的行下次轮询直接捞回；手上停在 `Processing` 的，`ProgressAt` 变老后由 4b 放回。Scheduler 重启：无影响，游标与待办都在 Oracle，错过一轮下一轮补上。两个角色都重启：进行中的块仍是进行中，慢轮次迟早扫到并按静默期封口，不会永久悬挂。
