## M01 `FetchLogMonitorSrvCategoryFromSystemMisc()` — 启动读 ServerCategory 白名单

**方法名**：`M01_FetchLogMonitorSrvCategoryFromSystemMisc()`

**入参**：无。

**出参**：`string[]`。

**逻辑**

1. 用配置 item `log.monitor.servercategory` 读配置。
2. 配置的 `valueType` 不为 `Json` 时，返回值为空（`[]`）。
3. `valueType` 为 `Json` 时，先对 `value` 解析成字符串数组：无法解析、或解析得到的数组为空，则进入第 4 步；否则直接输出解析得到的字符串数组。
4. 对 `defaultValue` 解析成字符串数组：解析失败则输出为空（`[]`）；解析成功则输出得到的字符串数组，**无论其是否为空**。

## M04 `FetchMESRuleFullLogs()` — 按块取全部行并还原写入顺序

**方法名**：`M04_FetchMESRuleFullLogs()`

**入参**

| 参数 | 取值 | 说明 |
|---|---|---|
| `blockId` | string | 块索引中块的 `_id` |

**出参**：`MESRuleRawLogEntity` 对象。

| 字段 | 类型 | 说明 |
|---|---|---|
| `RuleName` | string | 块上的 `RULE_NAME` |
| `Tid` | string | 块上的 `TID` |
| `StartTime` | datetime | 块上的 `START_TIME` |
| `RawLogs` | Map<number, string> | K = M05 赋予的 `OrderNumber`，V = 该行 `LOG_RAW`；按 K 升序即写入顺序 |

**逻辑**

1. 入参 `blockId` 为空时，方法报错。
2. 以 `blockId` 作为块索引的 `_id` 取块信息，取回字段：`ENV` / `HOSTIP` / `SERVER_ID` / `system.name`、`START_TIME` / `END_TIME`、`START_LINE_ID` / `END_LINE_ID`、`RULE_NAME`、`TID`。
3. 块信息为空时，方法报错。
4. 用块上的四个 `term` + `START_TIME` / `END_TIME` 查行索引：`START_TIME` / `END_TIME` 与行上的 `LOG_TIME` 比较，**上下界均为闭区间**。取回字段：`LOG_FINGERPRINT` / `LOG_OFFSET` / `LOG_RAW` / `_id`。分页取全后转第 5 步重排。
5. 把第 4 步行结果映射成 M05 入参 `lines`：`_id → LineId`、`LOG_FINGERPRINT → LogFingerPrint`、`LOG_OFFSET → LogOffset`，`OrderNumber` 置 0；**不传 `LOG_RAW`**，原文由本方法按 `LineId` 自行保留。调 M05：`tieMode` 固定 `NO_TIE`，**不传 `knownOrder`**。取回出参 `MESRuleLineLogEntity[]`（每行已带从 1 起的 `OrderNumber`）与 `knownOrder`（本方法不使用，不进 M04 出参）。
6. 在 M05 返回的 `lines` 中按 `LineId` 定位 `START_LINE_ID` 与 `END_LINE_ID` 两行，取两行 `OrderNumber` 之间的全部行（**含两端**）；`OrderNumber` 保持 M05 赋值，**不重新编号**。
7. 按裁剪后各行的 `OrderNumber` 建 K-V：Key = `OrderNumber`，Value = 本方法第 4 步按该行 `LineId` 取回的 `LOG_RAW`，组成出参 `RawLogs`；`RuleName` / `Tid` / `StartTime` 分别取块上的 `RULE_NAME` / `TID` / `START_TIME`。

## M05 `ReorderMESRuleRawLogs()` — MES 规则行日志重排（输出行顺序编号与指纹顺序）

**方法名**：`M05_ReorderMESRuleRawLogs()`

**入参**

| 参数 | 取值 | 说明 |
|---|---|---|
| `lines` | `MESRuleLineLogEntity[]` | 待排序行集合。对象字段：`LogFingerPrint` / `LogOffset` / `LineId` / `OrderNumber`（**不含原文，原文由调用方自行组织**）；**入参对象的 `OrderNumber` 恒为 0** |
| `tieMode` | `WITH_TIE` / `NO_TIE` | 排序口径开关 |
| `knownOrder?` | Map<number, string> | 可选，不传视为数量 0。K = 顺序编号（从 1 开始），V = `LogFingerPrint` 字符串 |

**出参**：排序后的 `MESRuleLineLogEntity[]`（`OrderNumber` 从 1 开始逐行赋值）+ 最终的 `knownOrder`。

**逻辑**

1. 提取 `lines` 中所有 `LogFingerPrint` 并去重，得指纹集合。
2. 指纹集合数量 = 1：直接按 `LogOffset` 排序；从 1 开始生成 `knownOrder`（唯一指纹的顺序编号为 1），并逐行赋 `OrderNumber` 后输出。
3. 指纹集合数量 > 1，按 `tieMode` 分支：
   - `NO_TIE`，或 `WITH_TIE` 但传入的 `knownOrder` 数量 ≤ 1：对集合中每个 `LogFingerPrint`，从**行文档**取该指纹 `LogOffset` 最小那行的 `LogTime`（入参实体不带 `LogTime`，须回查行索引），按 `LogTime` 给指纹排序，从 1 开始生成新的 `knownOrder` 用于最终排序。
   - `WITH_TIE` 且传入的 `knownOrder` 数量 > 1：先检查指纹集合是否全部落在传入 `knownOrder` 中。全部落在 ⇒ 不再给指纹排序，直接用传入的 `knownOrder` 做最终排序；有任何一个不在 ⇒ 退回上一条，按各指纹最小 `LogOffset` 行的 `LogTime` 重新排序、生成新的 `knownOrder`。
4. 拿到最终 `knownOrder` 后，对 `lines` 先按 `LogFingerPrint` 分堆 → 堆内按 `LogOffset` 升序（**此时不赋 `OrderNumber`**）→ 堆间按 `knownOrder` 的编号顺序排，得到堆间 + 堆内的完整序列。
5. 对完整序列从 1 开始逐行赋 `OrderNumber` 并输出，同时输出最终的 `knownOrder`。

## M06 `ParseMESRuleInfo()` — 块首行解析（Rule / TXN 分流）

**方法名**：`M06_ParseMESRuleInfo()`

**入参**

| 参数 | 取值 | 说明 |
|---|---|---|
| `ruleMessage` | String | 块首行原始日志，一整行（含时间戳与服务名前缀）；解析方案权威见 `06-附录A` |

**出参**：`MESRuleParsedResultEntity` 对象。

| 字段 | 类型 | 说明 |
|---|---|---|
| `RequestType` | String | `Rule` / `TXN` |
| `KVParameters` | Map<String, List<String>> | 请求头 + `attributes` 合成出的 KV **全集**：固定键与动态键条目都在，K = 键名，V = 值集合 |
| `XMLParameters` | Map<String, List<String>> | `XMLDATA` 解析出的 XML KV；非 XML 形态或解析失败为空 |
| `SpecialFields` | Map<String, List<String>> | 要写进块文档的 7 个业务字段：`RULENAME` / `LOTID` / `EQPID` / `PORTID` / `CARRIERID` / `USERID` / `TID`；按出现顺序追加、同值去重 |

**逻辑**

1. **门禁分流**：看首行标志 `FwEventManager:message to process: :>>L` / `:>>T`，定 `RequestType = Rule` / `TXN`。Rule 走第 2~4 步，TXN 只走第 5 步。
2. **Rule · 剥壳切段**：砍到 `:>>L `（含尾空格）→ 砍第一个空格前的方法名 → 定位 `attributes={` → 从 `{` 起计数扫到归 0，摘出 `attributes` 段，剩下为请求头。全程挂 `inQuote`（`"` 翻转）与 `esc`（`\` 跳下一字符）两个状态位，引号内的 `{` `}` 空格 `=` 一律当字面量、不参与结构判断。
3. **Rule · 合成 `KVParameters`**：请求头用等号定位法（扫所有 `=`，Key 回退到第一个空格、首个起点为 0，Value 到下一个 `=` 的 Key 起点，各剥首尾一对引号）；`attributes` 内部按归 0 切块（每块带 `{}`），剥外层后按**第一个空格**切 Key/Value；`class=ASSOC` 形态声明块去掉前缀后再切，须恰好 2 块、各取块内第二段。请求头 KV 与 `attributes` KV 合成 `KVParameters`。
4. **Rule · XML**：集合里有 `K = XMLDATA` 时，把 Value 交标准 XML 解析器，标签名即 Key（小驼峰、不二次解析），`<txId>` 在 `<msgHeader>` 下、其余在 `<msgBody>` 下，**重复出现的兄弟节点整组不取**，结果进 `XMLParameters`；无 `XMLDATA` 或解析失败 ⇒ 空。
5. **TXN**：砍到 `:>>T` → 取剩余串第一个空格前的 token 作 TxnName → 以 `ruleName = TxnName` 放进 `KVParameters`；其余六个字段无从取起。
6. **`SpecialFields`**：在 `KVParameters` 里按字段配置表查（键名归一化后落标准字段），取到就写、取不到留空；动态键条目（键本身是业务对象 ID）留在 `KVParameters`、**不进** `SpecialFields`。
7. **兜底**：`attributes={` 找不到、计数没归 0、`class=ASSOC` 块切出不是 2 块 ⇒ 整条不解析、七字段留空；`key = value` 空 Key 跳过；块内无空格 ⇒ 值留空；`TXN` 取不到 TxnName ⇒ `RULENAME` 留空。**解析不到一律留空，不打 MISS 标记、不截断**；纯字符串扫描不用正则，两端实现须逐字节一致。

## M08 `GenerateMESLogIndexNameByTime()` — 按时间算带时间戳的索引名

**方法名**：`M08_GenerateMESLogIndexNameByTime()`

**入参**

| 参数 | 取值 | 说明 |
|---|---|---|
| `time` | datetime 或 string | 定索引的时间值。可为 Oracle 行的 `IssueTime`（datetime），或从 id 末段取出的 17 位毫秒串 `yyyyMMddHHmmssSSS` |
| `indexPrefix` | string | 索引基名前缀，如 `mes-log-line` / `mes-log-exec` / `mes-log-monitor-issue` |
| `granularity` | `month` / `day` | 索引粒度：`month` 截 `yyyy.MM`，`day` 截 `yyyy.MM.dd` |

**出参**：完整索引名字符串 `indexPrefix-yyyy.MM` 或 `indexPrefix-yyyy.MM.dd`。环境段由框架 `prefix` 前置，本方法不拼、`PRD` / `PIRUN` 同套。

**逻辑**

1. 归一时间：datetime 或 17 位毫秒串统一成 `yyyyMMddHHmmss` 形态再截取；格式不符报错，不猜测、不兼容其他长度。
2. 按 `granularity` 截取时间戳：`month` → 前 6 位 `yyyy.MM`；`day` → 前 8 位 `yyyy.MM.dd`。
3. 与 `indexPrefix` 拼成完整索引名，得物理索引基名。
4. 一批 id / 时间跨月跨日时，逐个算索引名，按索引名分组、一组一次请求。
5. 只算物理索引基名、不扫读别名（读别名会全开 360 天分片）；环境段不在此方法处理。

> 时间来源两类（05 §4.2③ / §4.5、06 §4.1③、10 §4.5.2）：结果索引按 Oracle 行的 `IssueTime` 定月；块索引按 `blockId` 末段 17 位毫秒串定日；行索引按 `START_LINE_ID` 末段 17 位毫秒串定月。从 id 取时间是调用方的前置解码，本方法只接收"时间"本身。

## M09 `FetchMESSourceLogByIds()` — 按索引分组 ids 点查、按 `_id` 建字典

**方法名**：`M09_FetchMESSourceLogByIds()`

**入参**

| 参数 | 取值 | 说明 |
|---|---|---|
| `indexGroups` | Map<indexName, string[]> | 按索引名分好的 id 组：key = 索引名，value = 该索引内的 id 数组。**分组由调用方完成**（索引用 M08 算，或按业务规则定），本方法不解析 id、不猜索引名 |
| `sourceFields` | string[] | `_source` 字段白名单，每个文档只取这些字段 |

**出参**：`Map<id, Map<string, string>>`。外层 key = 文档 `_id`；内层 key = `sourceFields` 定义的字段名，value = 该字段在 OS 中对应的值。ES 返回顺序不保证，**必须按 `_id` 建 map，不能按下标对应**。

**逻辑**

1. 照 `indexGroups` 逐组处理：每组向 key 指定的索引发一次 `ids` 点查，带 `_source` = `sourceFields`；不搜关键字、不排序、不算分、不带 `sort`。
2. 遍历返回的 doc：按 doc 的 `_id` 作外层 key，内层按 `sourceFields` 逐字段取值组 `Map<字段名, 字段值>`（字段名 → OS 中该字段的值）作外层 value；同 id 重复按最后一次覆盖。
3. **缺失与查询解耦**：查不到的 id 不进 map；跳过还是整批失败由调用方决定（如 05 §4.5 ① 只 WARN 跳过、③ 任一块取不到整批失败）。
4. 不解析 id 内容：id **不一定**是带 17 位毫秒串的合规串，索引归属完全信 `indexGroups`，本方法不做任何时间码推断。
5. 边界：模块1 `03` 是「id 解码 → 四 `term` 查行索引」，不是纯 `ids` 点查 —— 只共用 M08 算索引名，不走本方法。

## M10 `GenerateDocDateTime()` — datetime 转落库格式时间串

**方法名**：`M10_GenerateDocDateTime()`

**入参**

| 参数 | 取值 | 说明 |
|---|---|---|
| `dateTime` | datetime | 待格式化的时间值 |

**出参**：字符串，格式 `yyyy/MM/dd HH:mm:ss.SSS`（本地时区，毫秒三位）。

**逻辑**

## M11 `ValidateTurnWhenStart()` — 启动校验轮次行

**方法名**：`M11_ValidateTurnWhenStart()`

**入参**

| 参数 | 取值 | 说明 |
|---|---|---|
| `turnName` | string | 轮次名，定位轮次行的业务键；六处取值：`FAST` / `SLOW`（06）、`MONITOR`（02）、`SRVHANGMON`（04）、`ALARMNOTIFY`（10） |

**出参**：无。失败即抛错、启动失败。

**逻辑**

1. 按 `turnName` 只读查轮次行，检查存在且可读（连不上 / 查不动一并算失败）。
2. 有问题 ⇒ **直接启动失败并报错**，不降级、不静默跳过、**不自动补行 / 补建**。
3. 为什么：`SKIP LOCKED` 返回 0 行的语义是「别人在跑」；行缺失会伪装成「每轮都被跳过」⇒ 静默全停，必须在启动阶段挡住。
4. 多实例：每台各自校验、都不写；行由初始化脚本 / 运维一次性预置。
5. 适用点：06 的 `FAST` / `SLOW`（任一行读不到即失败）、02 `MONITOR`、04 `SRVHANGMON`、10 `ALARMNOTIFY`，共六行、口径一致。

## M12 `TryLockTurn()` — 抢轮次行锁

**方法名**：`M12_TryLockTurn()`

**入参**

| 参数 | 取值 | 说明 |
|---|---|---|
| `turnName` | string | 轮次名，定位要抢的那一行 |

**出参**：轮次行对象（含游标列，供调用方取区间）/ `null`（没抢到）。

**逻辑**

1. 本轮第一条语句：`SELECT <行> FROM FvTurn WHERE <定位列> = :turnName FOR UPDATE SKIP LOCKED`。
2. 返回 **1 行** = 抢到，行锁从这条 `SELECT` 一直持到 `COMMIT`；返回 **0 行** = 别人在跑，**本轮事务直接结束**（还没做任何改动，提交与回滚等价）。
3. **必须带 `SKIP LOCKED`**：不带会阻塞排队、锁一释放接着跑第二遍 —— 周期漂移、同一刻度重复执行。
4. 不引 Redis / 分布式锁：进程崩了事务回滚、行锁自动释放，不需要租约与接管。
5. 同机防重入不在本方法：定时器 / 进程内「正在跑就跳过本次触发」由调用方自管。
6. 定位列口径差异：06 用 `Cycle`，模块2 用 `Name`；落地时按现场表对齐（见文末口径说明）。游标列按抢到的行原样带出——06 取 `FromTs` / `ToTs`、02 取 `CursorTs`、04 / 10 不读游标。
7. 适用点：全部六个轮次行（06 FAST / SLOW、02 MONITOR、04 SRVHANGMON、10 ALARMNOTIFY）。

## M13 `MarkTurnWhenRunning()` — 登记本轮归属

**方法名**：`M13_MarkTurnWhenRunning()`

**入参**

| 参数 | 取值 | 说明 |
|---|---|---|
| `turnName` | string | 轮次名，定位本轮行 |
| `nodeId` | string | 抢到本轮的节点，诊断用 |
| `fireAt` | datetime | 本轮触发时刻，诊断用 |

**出参**：无。

**逻辑**

1. 抢到锁后，同一事务 `UPDATE FvTurn SET Owner = :nodeId, StartedAt = :fireAt WHERE <定位列> = :turnName`。
2. 失败随 `ROLLBACK` 一起回滚，不留半截归属。
3. 覆盖缺口：02 / 04 文档已写这句；06 表里有 `Owner` / `StartedAt` 字段但没写 SQL、10 完全没写 —— 抽成本方法后统一补上。
4. 适用点：全部六个轮次行，**含 04 / 10 这两个不推游标的行**。

## M14 `PullTurnToTs()` — 推快轮次游标 ToTs

**方法名**：`M14_PullTurnToTs()`

**入参**

| 参数 | 取值 | 说明 |
|---|---|---|
| `turnName` | string | 轮次名，本方法固定 `FAST` |
| `toTs` | datetime | 本轮右端 = `now − ScanDelay`（停摆时封顶 `FromTs + ColdLookback`） |

**出参**：无。

**逻辑**

1. 本轮结束写回：`UPDATE FvTurn SET ToTs = :toTs WHERE <定位列> = :turnName`，作为下一轮左端 `FromTs`。
2. **无条件推**：无论有没有读到新日志都推，有没有活都推进，轮次之间不留空隙、不设延迟区。
3. 唯一例外——**没有可用 Worker**：基础名单为空则整轮回滚事务，游标不推、待办不写，等同本轮没跑；等 Worker 回来从原 `FromTs` 重扫，那批行一行不少。
4. 推的是本轮算出的右端 `ToTs`，不是「查回块里最晚的 `@timestamp`」，也不是可见水位；停摆时封顶 `FromTs + ColdLookback`，分轮追平。
5. 适用点：仅 06 `Cycle='FAST'`。

## M15 `PullTurnCursorTs()` — 推监控窗口游标 CursorTs

**方法名**：`M15_PullTurnCursorTs()`

**入参**

| 参数 | 取值 | 说明 |
|---|---|---|
| `turnName` | string | 轮次名，本方法固定 `MONITOR` |
| `cursorTs` | datetime | 本轮窗口右端 = `min(可见水位, 游标 + 上限)` |

**出参**：无。

**逻辑**

1. 整轮扫描成功后写：`UPDATE FvTurn SET CursorTs = :cursorTs WHERE <定位列> = :turnName`，同一事务 `COMMIT`。
2. **成功才推**：跳过 / 失败 `ROLLBACK`，**游标一律不动**；数据不丢，堆在区间里等下一轮。
3. 推的是本轮窗口右端（= 下一轮的游标），**不是可见水位** —— 被 6 / 18 分钟上限截掉的那一段，推可见水位会永久漏。
4. 窗口里一个块都没查到时右端照样推，否则游标卡死、后面全不扫。
5. 适用点：仅 02 `Name='MONITOR'`。

> **不推游标的行**：04 `SRVHANGMON`（全量扫未闭合块、重判）、10 `ALARMNOTIFY`（捞未发行）只走 M11 / M12 / M13，不调 M14 / M15。

## 轮次表公共方法的边界与口径

**不抽的项，都不写 Turn 表字段**

| 项 | 为什么不抽 |
|---|---|
| `COMMIT` / `ROLLBACK` | 事务控制动作，由调用方在整轮末尾执行；不写 Turn 表字段 |
| 窗口 / 区间计算 | 06 `[FromTs, ToTs)`、02 `[游标, 右端)` 业务口径各异，只读轮次行、不改 Turn 表 |
| 同机防重入标记 | 进程内「正在跑就跳过本次触发」，不动 Turn 表，各服务自管 |

**落地前要先定的列名口径**：06 用 `Cycle` / `FromTs` / `ToTs` / `Owner` / `StartedAt`，模块2 用 `Name` / `CursorTs` / `Owner` / `StartedAt`，是同一张 `FvTurn` 的两套列名口径。模块2 文档自述「现场轮次表若已有等价列，直接复用、SQL 里的列名按现场对齐，口径不变」——M11 ~ M15 的 `<定位列>` / 游标列名按现场表一次性敲定，方法本身不猜列名。
