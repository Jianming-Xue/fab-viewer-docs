## 一、全局约定

### 1.1 技术底座

| 项 | 口径 |
|---|---|
| 数据库 | **Oracle 11g** |
| 后端语言 | **Go** |
| 技术主键 | `ID`，底层发号；业务侧不感知，接口不用它定位（§1.8） |
| 审计字段 | `createdAt` / `createdBy` / `updatedAt` / `updatedBy` 四列固定随表，由底层统一赋值（§1.8） |
| 布尔字段 | Oracle 无 `BOOLEAN`，落库一律 `Number(1)`：**`0` = false 停用，`1` = true 启用**，Go 侧 `bool` ↔ 0/1 映射 |

### 1.2 Oracle 11g 硬约束

1. **没有 `IS JSON` 约束**（12.1.0.2 起才提供）—— 存 JSON 的列，合法性只能由服务端保证，库层兜不了。
2. **`VARCHAR2(n)` 默认字节语义**（`BYTE`）—— AL32UTF8 下一个汉字占 3 字节，长度按**字节**校验，超出直接报错而非截断。

### 1.3 请求分页 `PageRequest`（底层提供）

| 字段 | 类型 | 说明 |
|---|---|---|
| `pageIndex` | int | 页码 |
| `pageSize` | int | 每页条数 |

### 1.4 全局响应包

| 字段 | 类型 | 说明 |
|---|---|---|
| `code` | string | 成功**恒 `OK`**；失败为自定义业务码。业务码用 **PascalCase**（如 `RoleNotFound`，§十），登录结果码用**大写下划线**（如 `ACCOUNT_LOCKED`，§9.1.3）—— 两套风格并存，不混用 |
| `success` | bool | 内部为布尔，**输出前转成 `0` / `1`** |
| `errMsg` | string | 失败原因；成功为空串 |
| `data` | object | 业务数据；分页接口为 `Pageable`（§1.5） |
| `txId` | string | 读请求 Header 的 `txId`，**原样返回**；无则空串 |

- **HTTP 状态码**：业务类失败（参数错、无权限、业务规则拒绝）**恒 200**，成败只看 `success`；仅服务端内部错误（panic、DB 不可用等）返回 5xx，且不出本响应包。
- **登录接口例外（auth）**：登录进入业务判定后，无论登录成败，`success` **恒 `1`**、HTTP **恒 200**；登录结果由 `code` 承载 —— 成功为 `OK`，失败为 §9.1.2 的 6 个码之一。前端判「`success = 1` 且 `code != OK`」即按该码报错或跳转（详见 §9.1.3）。
- **登录接口仍有三类走普通报错**（`success = 0`，与其他接口一致）：① 入参校验失败（`userName` / `password` 为空）；② 账户不存在（按 `userName` 查不到记录）；③ **绑定策略不存在**（`policyId` 查不到策略）。这三类不进 6 个码，`code` 分别是 `RequireParameterMissing`（参数为空）、`UserNotFound`（账户不存在）、`PolicyNotFound`（绑定策略不存在），文案由 i18n 生成（§9.2）。

### 1.5 分页出参 `Pageable`

| 字段 | 类型 | 说明 |
|---|---|---|
| `pageIndex` | int | 当前页码（与入参一致） |
| `pageSize` | int | 每页条数 |
| `totalSize` | int | 总条数 |
| `totalPage` | int | 总页数 |
| `data` | array | 当前页数据 |

```json
  "errMsg": "",

    "pageSize": 20,
    "totalSize": 12,
    "totalPage": 1,
    "data": []
  },
  "txId": "3f9c1b7e2a4d"
}
```

### 1.7 URL 规则

服务内路径形如 **`/api/v1/<资源前缀>/…`**；对外完整路径由 nginx 在最前加服务名：`security-management/api/v1/…`（nginx 按路径第一段分发到本服务）。**本文只写服务内前缀。**

各资源前缀（按需求方给定名称，不统一单复数风格）：

| 资源 | 服务内前缀 |
|---|---|
| 角色 | `/api/v1/roles`（复数） |
| 登录策略 | `/api/v1/login_policy`（下划线、非复数） |
| 用户 | `/api/v1/users`（复数） |
| 认证 | `/api/v1/auth`（四个接口：`/login`、`/change_password`、`/permissions`、`/logout` —— 按需求方给定名称，`change_password` 用下划线、另三个用单词） |

### 1.8 表结构基础（所有表必备）

每张业务表都固定带下列 5 列；**`ID` 是技术主键，业务唯一键另建唯一索引**。

| 列 | 说明 |
|---|---|
| `ID` | 技术主键，底层发号；业务侧不感知，接口不用它定位 |
| `createdAt` | 创建时间 |
| `createdBy` | 创建人 |
| `updatedAt` | 更新时间 |
| `updatedBy` | 更新人 |

- **列类型由底层框架统一提供，本文不规定、不落 DDL** —— 本模块只管业务字段。
- 审计字段由底层统一赋值，**不出现在任何接口的入参**；出参默认也不带，**唯一例外是用户 `UserDto` 输出 `createdAt`**（列表 / 详情需要「创建时间」列）。
- 各表章节**只列业务字段**，基础 5 列不再逐表重复。
- 业务唯一键口径：角色用 `roleId`、策略用 `policyId`、用户用 `userName`，各自建**唯一索引**；接口一律用业务键定位，不用 `ID`。

### 1.9 字段类型与长度规则

| 用途 | 尺寸 | 判定 |
|---|---|---|
| 带 `ID` 的标识 | `varchar2(50)` | 列名以 `Id` 结尾，**未特别说明时一律 50** |
| 带「名称」的字段 | `varchar2(63)` | 列名以 `Name` 结尾，**未特别说明时一律 63** |
| 短描述 / 提示串 | `varchar2(255)` | `description`、`failMessage` 等 |
| 邮箱 | `varchar2(100)` | `email` |
| 手机号 | `varchar2(30)` | `phoneNumber` |
| IP | `varchar2(45)` | 兼容 IPv6 |
| 布尔 | `Number(1)` | `enabled`、各 `passwdRequire*` |
| 长度值 | `Number(3)` | `passwdMinLength` / `passwdMaxLength` |
| 天数 / 分钟 | `Number(6)` | 要能存 `-1` |
| 时间 | `TIMESTAMP` | 接口线格式 `yyyyMMddHHmmss`（§5.3.2）；**账户 / 密码的日期类列只到日、不带具体时点**，判定一律按日（§5.4.2） |
| JSON 集合 | `varchar2(4000)` / `CLOB` | 小的走 4000，大的走 `CLOB` |

- 长度一律按**字节**校验（§1.2）：AL32UTF8 下汉字 3 字节，50 字节约 16 个汉字，63 字节约 21 个汉字。
- **特例：`userName` 用 `varchar2(63)`** —— 账号虽不是「名称」类字段，但它是人可读的登录标识，按名称尺寸收。
- **特例：`deviceId` 用 `varchar2(255)`** —— 列名带 `Id`，按默认应为 50，但设备标识由前端上报、格式未约束，预留 255 兜长串（§9.1）。
- **日期类字段一律按日**：`accountActiveAt` / `accountExpiresAt` / `passwordExpiresAt` 这类「设定日期」的列，**设置时只填日期、不填几点**；所有判定与比较都用 `TRUNC` 取日后再比，不看小时。
- 未被本表覆盖的新字段，先按上表归类取尺寸；归不了类再单独定。

## 二、数据模型

### 2.1 表 `FabViewerRole`

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `roleId` | `varchar2(50)` | **唯一索引** | 角色标识 —— 业务唯一键，与底层技术主键无关；接口一律用 `roleId` 定位 |
| `roleName` | `varchar2(63)` | **NOT NULL** | 角色名称 |
| `description` | `varchar2(255)` | — | 描述 |
| `enabled` | `Number(1)` | 默认 `0` | 启用 / 停用（`0` = 停用，`1` = 启用） |
| `permissions` | `CLOB` | — | 权限集合，存 JSON 数组字符串 |

> 本表另含 §1.8 的 5 个基础列（`ID` + 4 个审计字段），下表只列业务字段；`roleId` 是**业务唯一索引**，不是主键。

### 2.2 字段口径

| 字段 | 口径 |
|---|---|
| `roleId` | 唯一；**创建后锁定，编辑不可改**；长度按 50 字节校验（§1.9，中文按 3 字节计，约 16 个汉字） |
| `roleName` | 必填；长度按 63 字节校验（约 21 个汉字） |
| `description` | 可空；长度按 255 字节校验（约 85 个汉字） |
| `enabled` | 新建默认 `false`；停用不删用户挂载关系，权限合并时跳过该角色 |
| `permissions` | **存什么由前端决定，后端只管存**：原样写入、原样读出；不校验 JSON 合法性、不校验路径是否存在、不校验按钮与菜单的依附关系 |

### 2.3 落库形态

| 场景 | 落库值 |
|---|---|
| 新建角色 | `enabled = 0`；`permissions = "[]"`（**空 JSON 数组的字符串，不是 `NULL`**） |
| 配置权限 | 集合序列化成 JSON 数组字符串，**整集合覆盖**，不做增量合并 |
| 出参还原 | `permissions` 由 JSON 字符串解析成字符串集合返回 |

| 4 | `DELETE` | `/api/v1/roles` | query：`roleId` | 空 | 删除角色 |
| 5 | `POST` | `/api/v1/roles/permissions` | body：`AssignRolePermissionRo` | `RoleDto` | 配置权限 |

### 3.2 角色分页 `GET /api/v1/roles/page`

**入参**

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `pageIndex` | int | 是 | 分页参数（§1.3） |
| `pageSize` | int | 是 | 分页参数（§1.3） |
| `keyword` | string | 否 | 非空时对 `roleId` / `roleName` / `description` 三列**同时模糊匹配（OR）**；为空不加条件，分页返回全部 |

**出参**：`data` = `Pageable`（§1.5），`data.data` 元素为 `RoleDto`：

| 字段 | 类型 | 说明 |
|---|---|---|
| `roleId` | string | 角色标识 |
| `roleName` | string | 角色名称 |
| `description` | string | 描述 |
| `enabled` | number | `0` = 停用，`1` = 启用 |
| `permissions` | string 集合 | 权限路径数组 |

**匹配规则**

| 项 | 口径 |
|---|---|
| 匹配列 | `roleId`、`roleName`、`description` 三列，任一命中即返回 |
| `description` 为空 | 该列不命中，不影响其他两列 |
| 空 `keyword` | `trim` 后为空即视为未传，不拼条件 |
| 大小写 | **统一转全大写后匹配**：`keyword` 与三列都经 `UPPER()` 再 `LIKE`（`admin` 能搜到 `ADMIN`） |

**排序**：`roleId` 升序。

### 3.3 新建角色 `POST /api/v1/roles`

**入参 `RoleRo`**（新建与修改共用）

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `roleId` | string | 是 | 角色标识；唯一，创建后不可改 |
| `roleName` | string | 是 | 角色名称 |
| `description` | string | 否 | 描述 |

> 入参**不含** `enabled` 与 `permissions`：新建时 `enabled` 落 `0`，`permissions` 落 `"[]"`（§2.3）。

**处理流程**

| 步 | 动作 |
|---|---|
| 1 | app 层校验：`roleId`、`roleName` 不能为空（`trim` 后判空）→ 空则 `RequireParameterMissing`（参数 `roleId` / `roleName`） |
| 2 | 按 `roleId` 查 `FabViewerRole` |
| 3 | 已存在 → 抛 `RoleIdExists`（参数 `roleId`） |
| 4 | 不存在 → 调 TXN 直接保存 |
| 5 | 保存成功 → 取返回的 `RoleEntity`，打包成 `RoleDto` 返回 |

**出参 `RoleDto`**：`roleId` / `roleName` / `description`（string）、`enabled`（number）、`permissions`（string 集合）。

### 3.4 修改角色 `PUT /api/v1/roles`

**入参**：同 `RoleRo`，`roleId` 只作定位键，**不参与修改**。

**处理流程**

| 步 | 动作 |
|---|---|
| 1 | app 层校验：`roleId`、`roleName` 不能为空（`trim` 后判空）→ 空则 `RequireParameterMissing`（参数 `roleId` / `roleName`） |
| 2 | 按 `roleId` 查是否已存在 |
| 3 | 不存在 → 抛 `RoleNotFound`（参数 `roleId`） |
| 4 | 已存在 → 调 **Modify Attribute 的 TXN**，只修改 `roleName` 与 `description` |
| 5 | 成功 → 取返回的 `RoleEntity`，打包成 `RoleDto` 返回 |

- `enabled`、`permissions` 本接口不改。

### 3.5 删除角色 `DELETE /api/v1/roles?roleId=xxx`

**入参**：query 参数 `roleId`。

**处理流程**

| 步 | 动作 |
|---|---|
| 1 | 校验 `roleId` **非空**（`trim` 后判空），为空 → `RequireParameterMissing`（参数 `roleId`） |
| 2 | 按 `roleId` 查角色：查不到 → 抛 `RoleNotFound`（参数 `roleId`） |
| 3 | 查引用该角色的用户：`FabViewerUserProfile.ROLEIDS` 中含该 `roleId` 的用户 |
| 4 | **引用判定**：存在任一 `enabled = 1` 的引用用户 → 拒删；引用者全部 `enabled = 0`，或无人引用 → 允许删除 |
| 5 | 调删除 TXN 删除该角色 |

**出参**：`data` 为空。

**「是否被用户使用」的判定与处置**

| 情形 | 处置 |
|---|---|
| 无用户引用 | 允许删除 |
| 有引用，且**至少一个引用用户 `enabled = 1`** | **拒绝删除** → `RoleInUse`（参数 `roleId`） |
| 有引用，引用用户**全部 `enabled = 0`** | 允许删除 |

- 判定只看**引用用户的 `enabled`**，不看角色自身是否启用、也不看引用人数。
- 引用者全部停用时允许删除，是因为**停用账号不参与业务**；该角色被删后，这些用户要启用时会因 `RoleNotFound` 被 §5.3.11 校验 6 拦住，必须先重配角色才能启用。
- 删除时**不级联修改用户**（已定）：停用用户的 `ROLEIDS` 里会留着这个已删的 `roleId`，本接口**不清**。这些账号下次启用时由 §5.3.11 校验 6 报「角色不存在」，提示管理员重新配置角色后再启用 —— 由人来判断该补哪个角色，系统不替他们猜。

### 3.6 配置权限 `POST /api/v1/roles/permissions`

### 3.9 角色验收规则

> 验收方式：接口级，既看响应包（`success` / `code` / `errMsg` / `data`），也回查库中实际值。删除时的引用判定已定口径（§3.5）：**存在启用用户则拒删（R-18）、仅被停用用户引用则放行（R-32）**，均纳入本表。

| 编号 | 场景 | 输入 / 操作 | 预期 |
|---|---|---|---|
| R-01 | 分页 · 无筛选 | `pageIndex=1&pageSize=20`，不传 `keyword` | `success=1`；`data.data` 为全部角色，按 `roleId` 升序；`totalSize` = 表总行数 |

## 四、策略

### 4.1 数据模型

#### 4.1.1 表 `FabViewerPolicy`

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `policyId` | `varchar2(50)` | 唯一索引 | 策略标识 |
| `policyName` | `varchar2(63)` | NOT NULL | 策略名称 |
| `description` | `varchar2(255)` | — | 描述 |
| `passwdMinLength` | `Number(3)` | — | 密码最小长度 |
| `passwdMaxLength` | `Number(3)` | — | 密码最大长度 |
| `passwdRequireDigit` | `Number(1)` | — | 至少一个数字（`0` / `1`） |
| `passwdRequireLowerChar` | `Number(1)` | — | 至少一个小写字母（`0` / `1`） |
| `passwdRequireUpperChar` | `Number(1)` | — | 至少一个大写字母（`0` / `1`） |
| `passwdRequireSpecialChar` | `Number(1)` | — | 至少一个特殊字符（`0` / `1`） |
| `passwdSpecials` | `varchar2(255)` | — | 指定的特殊字符集合 |
| `passwdValidDays` | `Number(6)` | — | 密码有效期天数，**可存 `-1`** |
| `accountValidDays` | `Number(6)` | — | 账户有效期天数，**可存 `-1`** |
| `idleLogoutMinutes` | `Number(6)` | — | 空闲登出分钟数，**可存 `-1`** |

> **本表不设 `isDefault`、不设 `enabled`** —— 策略没有「默认」与「停用」两个状态。`01` 原有的「全表恒有且仅有一条默认策略」「停用的策略视同不存在、挂它的用户回落默认」两条口径**同时作废**（用户未挂策略时的处理见 §4.3）。
>
> `passwdMinLength` / `passwdMaxLength` 为**数字**（长度值），其余 4 个 `passwdRequire*` 为布尔（`Number(1)`）。
>
> 本表另含 §1.8 的 5 个基础列（`ID` + 4 个审计字段），下表只列业务字段；`policyId` 是**业务唯一索引**，不是主键。
>
> **三条补充口径**
>
> | 项 | 口径 |
> |---|---|
> | `policyName` | **不唯一**，只是一个名字；仅要求非空，不做重名校验 |
> | `passwdValidDays` / `accountValidDays` / `idleLogoutMinutes` 的 `-1` | **表示不限制**（密码永不过期 / 账户永不过期 / 不因空闲登出） |
> | `-1` 的生效判定 | **在认证链路（auth）中处理**，本模块只负责存与取，不做折算 |

#### 4.2.4 新建策略 `POST /api/v1/login_policy`

**入参 `PolicyRo`**（13 个业务字段全给，`policyId` 由前端录入）

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `policyId` | string | 是 | 策略标识；唯一，创建后不可改 |
| `policyName` | string | 是 | 策略名称 |
| `description` | string | 否 | 描述 |
| `passwdMinLength` | number | 是 | 密码最小长度，**≥ 6** |
| `passwdMaxLength` | number | 是 | 密码最大长度，**≥ 18** 且 **> `passwdMinLength`** |
| `passwdRequireDigit` | number | 是 | `0` / `1` |
| `passwdRequireLowerChar` | number | 是 | `0` / `1` |
| `passwdRequireUpperChar` | number | 是 | `0` / `1` |
| `passwdRequireSpecialChar` | number | 是 | `0` / `1` |
| `passwdSpecials` | string | 条件必填 | **`passwdRequireSpecialChar = 1` 时不能为空，且至少含一个字符** |
| `passwdValidDays` | number | 是 | 密码有效期天数，**`-1` 或 `1 ~ 999`** |
| `accountValidDays` | number | 是 | 账户有效期天数，**`-1` 或 `1 ~ 999`** |
| `idleLogoutMinutes` | number | 是 | 空闲登出分钟数，**`-1` 或 `1 ~ 9999`** |

**校验（后端兜底，按序）**

| 序 | 规则 | 拒绝条件 | code（参数） |
|---|---|---|---|
| 1 | `policyId`、`policyName` 非空 | `trim` 后为空 | `RequireParameterMissing`（`policyId` / `policyName`） |
| 2 | `passwdMinLength` 下界 | `< 6` | `ParameterOutOfRange`（`passwdMinLength`） |
| 3 | `passwdMaxLength` 下界 | `< 18` | `ParameterOutOfRange`（`passwdMaxLength`） |
| 4 | 长度大小关系 | `passwdMaxLength <= passwdMinLength` | `ParameterOutOfRange`（`passwdMaxLength`） |
| 5 | `passwdValidDays` 取值 | 既不是 `-1`，也不在 `1 ~ 999` | `InvalidParameterValue`（`passwdValidDays`） |
| 6 | `accountValidDays` 取值 | 既不是 `-1`，也不在 `1 ~ 999` | `InvalidParameterValue`（`accountValidDays`） |
| 7 | `idleLogoutMinutes` 取值 | 既不是 `-1`，也不在 `1 ~ 9999` | `InvalidParameterValue`（`idleLogoutMinutes`） |
| 8 | 特殊字符条件必填 | `passwdRequireSpecialChar = 1` 且 `passwdSpecials` 为空（`trim` 后空串） | `RequireParameterMissing`（`passwdSpecials`） |
| 9 | `policyId` 查重 | 该 `policyId` 已存在 | `PolicyIdExists`（`policyId`） |

> 长度**上限**（`passwdMinLength ≤ 999`、`passwdMaxLength ≤ 999`）不单独校验 —— `Number(3)` 列宽自然兜住，超出由 DB 报错。密码本身**不在策略保存时校验**（那是配置动作）；用户实际设密码时由后端按策略判（改密接口 §9.3）。
>
> 4 个 `passwdRequire*` 入参为 `0` / `1`，只判真假，不做其他取值校验。

**处理流程**

| 步 | 动作 |
|---|---|
| 1 | 按上表顺序校验，任一不过即按其 `code` 返回（表见上） |
| 2 | 调**新建 TXN**保存整条记录（13 个字段全落库） |
| 3 | 取返回的 `PolicyEntity` 打包成 `PolicyDto` 返回 |

**出参 `data`**：`PolicyDto`（新建后整条记录，字段同 §4.2.1）。

#### 4.2.6 删除策略 `DELETE /api/v1/login_policy`

**入参**：query 参数 **`policyId`**（`DELETE /api/v1/login_policy?policyId=xxx`）

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `policyId` | string | 是 | 策略标识，定位用 |

**处理流程**

| 步 | 动作 |
|---|---|
| 1 | 校验 `policyId` **不能为空**（`trim` 后判空）→ 空则 `RequireParameterMissing`（参数 `policyId`） |
| 2 | 按 `policyId` 查策略是否已创建 |
| 3 | **未创建** → 抛 `PolicyNotFound`（参数 `policyId`） |
| 4 | **已创建** → 校验「是否被用户挂载」：存在 `enabled = 1` 的挂载用户 → 拒删；否则通过（见下） |
| 5 | 确认通过 → 调**删除 TXN**删除该策略 |

**「是否被用户挂载」的判定与处置**

| 情形 | 处置 |
|---|---|
| 无用户挂载 | 允许删除 |
| 有挂载，且**至少一个挂载用户 `enabled = 1`** | **拒绝删除** → `PolicyInUse`（参数 `policyId`） |
| 有挂载，挂载用户**全部 `enabled = 0`** | 允许删除 |

- 判定依据：`FabViewerUserProfile.POLICYID` 等于该 `policyId` 即视为「被挂载」。
- 判定只看**挂载用户的 `enabled`**，不看挂载人数。
- 与角色删除（§3.5）同一套口径：**启用中的用户挡住删除，停用用户不挡**。
- 删除时**不级联修改用户**（已定，与角色删除同一口径）：停用用户的 `POLICYID` 仍指向这个已删的策略，本接口**不清**。这类账号启用时由 §5.3.11 校验 8 报 `PolicyNotFound`，提示管理员重新配置策略后再启用。

**出参 `data`**：空（与删除角色一致，**推定**）。

### 4.3 校验责任划分

| 规则 | 校验方 | 口径 |
|---|---|---|
| 策略必须挂到用户 | **后端** | 保存用户时 `policyId` **必填**，不接受「不挂策略」 |
| 密码复杂度（长度区间 / 大小写 / 数字 / 特殊字符） | **后端** | **只在「修改密码」接口校验**（§9.3，按用户所挂策略逐项判）；管理员配置类动作（新建用户 / 重置密码）**不校验** |
| `-1`（不限制）的判定 | **拆两处** | 密码过期、账户过期 → **认证链路 auth**（登录时判，§9.1.2）；空闲登出（`idleLogoutMinutes = -1`）→ **前端自行判定**，后端只原样透传、不做空闲计时（§9.2.1） |

### 5.2 落库形态

| 场景 | 落库值 |
|---|---|
| `roleIds` | **JSON 数组字符串**存 `varchar2(4000)`，如 `["ADMIN","OP"]`。写入侧**至少 1 个元素**（新建校验 4、修改校验 3），`"[]"` 只可能来自历史或脏数据；出参一律还原成数组，空回 `[]` 不回 `null` |

**三条取值规则**

- `passwordValidDays` / `accountValidDays` **不落用户表**，每次查询按 `policyId` **左连接** `FabViewerPolicy` 现取；策略改了，用户出参立即跟着变。
- 关联不到策略（脏数据）时：**查询不失败，这两个字段出参为 `null`**（不是 `0` —— `0` 是合法值域外的非法天数，会误导前端）。**用到策略规则的实际业务**（改密、登录校验等）在此场景下直接报 `PolicyNotFound`（参数 `policyId`），见下方说明。

> **两处分层口径不同，别混淆**：出参组装层（查询 / 列表 / 详情）**容错**，策略缺失只让两个字段为 `null`；业务执行层（真正拿策略做校验的接口）**不放过**，发现用户无有效策略即报错。用户表 `policyId` 本身是 `NOT NULL`（§5.1.1），缺失只会来自策略表被删或数据迁移残缺。

#### 5.3.2 时间字段出参格式

| 项 | 口径 |
|---|---|
| 库侧类型 | `TIMESTAMP`（§5.1.1） |
| 出参类型 | `string` |
| **格式** | **`yyyyMMddHHmmss`** —— 14 位纯数字，无分隔符、无毫秒。例：`20261029101641` |
| 时区 | 服务器本地时区（与 `lastLoginTime` 落库口径一致） |
| 精度 | 秒级；库中毫秒部分**截断不输出** |
| 空值 | 库中为 `NULL` 时出参为 `""`（空串），不回 `null` |
| 转换位置 | 组装 `Dto` 时统一格式化（一个公共函数），业务代码里不出现 `time.Time` |
| 入参 | 同一格式：前端传 `yyyyMMddHHmmss` 字符串，反解为 `TIMESTAMP`。**日期类字段**（`accountActiveAt` / `accountExpiresAt` / `passwordExpiresAt`）前端只给到日，**时分秒固定 `000000`**，后端只取日期部分（§1.9 按日口径） |

```json
{
  "createdAt": "20261029101641",
  "accountActiveAt": "20261001000000",
  "accountExpiresAt": "20271001000000",
  "passwordChangedAt": "20261029101641",
  "passwordExpiresAt": "20270127000000",
  "lastLoginTime": "20261029091530"
}
```

> 14 位格式**不含时区信息**，跨时区展示由前端按本地时区解读；本期不做 UTC 存储与转换。

#### 5.3.4 用户分页 `GET /api/v1/users/page`

**入参**（query）

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `pageIndex` | int | 是 | 分页参数（`PageRequest`，§1.3） |
| `pageSize` | int | 是 | 分页参数（`PageRequest`，§1.3） |
| `keyword` | string | 否 | 非空时对 **`userName` / `nickName` / `email` 三列模糊匹配（OR）**；为空不加条件，分页返回全部用户 |

**匹配规则**

| 项 | 口径 |
|---|---|
| 匹配列 | `userName`、`nickName`、`email` 三列，任一命中即返回 |
| 大小写 | 统一转全大写后匹配：`keyword` 与三列都经 `UPPER()` 再 `LIKE`（与角色分页一致） |
| 空 `keyword` | `trim` 后为空即视为「未传」，不拼条件 |
| 空列 | `nickName` / `email` 为 `NULL` 时该列不命中，不影响其他两列 |

**排序**：`enabled` **降序** + `userName` **升序** —— 启用的（`1`）排在前面，停用的（`0`）沉底；同组内按账号升序。

```sql
ORDER BY ENABLED DESC, USERNAME ASC
```

- **不加任何精确筛选**：除 `keyword` 外没有 `enabled` / `roleId` / `policyId` 条件，停用用户同样出现在列表里。
- 每行都要**左连接** `FabViewerPolicy` 取 `passwordValidDays` / `accountValidDays`（§5.3.1）。
- `Oracle` 在 `DESC` 下默认 `NULLS FIRST`；本表 `enabled` 由后端计算写入（§5.2），正常不为空，故**不做 `NULLS LAST` 特判**。

**时间入参的类型与线格式**

|---|---|

| `passwordExpiresAt` | **一律落 `NULL`** —— 与上行同步置空，**不按 `passwdValidDays` 推算** |
| `lastLoginTime` / `lastLoginIp` | 新建不写，首次登录成功时回写 |

**各列取值来源（新建一条记录，20 列全覆盖）**

| # | 列 | 取值来源 | 说明 |
|---|---|---|---|
| 1 | `ID` | 框架发号 | 技术主键（§1.8） |
| 2 | `userName` | **入参** `userName` | `trim` 后落库；唯一 |
| 3 | `password` | **入参**明文 → **哈希** | **哈希算法由框架层提供，业务侧不定义、不关心**；列宽 `varchar2(255)` 已留足 |
| 4 | `nickName` | **入参** `nickName` | 可空；`trim` 后空串 → 落 **NULL** |
| 5 | `email` | **入参** `email` | 可空；`trim` 后空串 → 落 **NULL** |
| 6 | `phoneNumber` | **入参** `phoneNumber` | 可空；`trim` 后空串 → 落 **NULL** |
| 7 | `avatar` | **`NULL`** | 新建不带头像，后续由「更新属性」写 |
| 8 | `enabled` | **入参 bool ∧ §5.4.2 `CalcEnabled`** → `Number(1)` | 规则见下方「落库取值规则」 |
| 9 | `roleIds` | **入参**集合 → **JSON 数组字符串** | 至少 1 个元素，如 `["ADMIN"]` |
| 10 | `policyId` | **入参** `policyId` | 必须已存在 |
| 11 | `accountActiveAt` | **入参** | 原值写入，不做折算 |
| 12 | `accountExpiresAt` | **入参**（受策略上限约束） | 原值写入，**不做推算**；但不得晚于 `accountActiveAt + accountValidDays 天`（校验 7） |
| 13 | `passwordChangedAt` | **`NULL`** | 不接受前端传值；`NULL` = 尚未改密，登录强制提示改密 |
| 14 | `passwordExpiresAt` | **`NULL`** | 与 13 同步置空，不从 `passwdValidDays` 推算 |
| 15 | `lastLoginTime` | **`NULL`** | 首次登录成功时回写 |
| 16 | `lastLoginIp` | **`NULL`** | 同上 |
| 17 | `createdAt` | 框架赋值 | 审计列（§1.8） |
| 18 | `createdBy` | 框架赋值 | 审计列 |
| 19 | `updatedAt` | 框架赋值 | 审计列 |
| 20 | `updatedBy` | 框架赋值 | 审计列 |

> **空值统一口径**：可选字符串列（`nickName` / `email` / `phoneNumber`）**传空串或全空格一律落 `NULL`，不落空串 `''`** —— 避免库里同时出现 `NULL` 和 `''` 两种「空」，查询与判空只按一种写。
>
> **两组时间列的说明（已定）**：`accountExpiresAt` 由管理员**指定**，策略的 `accountValidDays` 只作**上限约束**（校验 7）；`passwordChangedAt` / `passwordExpiresAt` 新建时**一律置 `NULL`**，等用户自己首次改密时才写入。二者处理不同是有意的。

**落库取值规则**

`enabled` —— **入参传的是「意愿」，落库值由后端再算一次**：

| 入参 `enabled` | `CalcEnabled`（C1 ∧ C2） | 落库 `enabled` |
|---|---|---|
| `false` | 任意 | `0`（尊重入参，不再看时间） |
| `true` | `true` | `1` |
| `true` | `false` | **`0`（强制置 0）** —— 未到 `accountActiveAt`，或账户已过期 |

- `CalcEnabled` 的定义见 **§5.4.2**，只看账户两个日期，**不检查密码**。
- **本接口是 `CalcEnabled` 的唯一调用点**；其余接口一律不改 `enabled`。

> 后端**不报错、不静默改入参对象**，只影响落库值；出参 `UserDto.enabled` 以落库值为准。
>
> 两头一致：未到生效时间的账号，后续走启用接口（§5.3.11 校验 4）同样会被拦，**要等 `accountActiveAt` 之后才能启**。
>
> 入参给 `false` 时**直接落 `0`**，不再看时间 —— 管理员意愿优先于判定结果。

`passwordChangedAt` / `passwordExpiresAt` —— 新建时**两列一律置 `NULL`**：

| 字段 | 取值 | 含义 |
|---|---|---|
| `passwordChangedAt` | **`NULL`** | 密码从未由用户自己设置过 |
| `passwordExpiresAt` | **`NULL`** | 同上；**不按 `passwdValidDays` 推算** |

> **目的**：`passwordChangedAt` 为空就是「首次登录须改密」的判定依据，登录链路据此提示用户改密；本模块只负责把这两列置空，判定与拦截在 auth。
>
> `passwdValidDays` 在新建时**不参与这两个字段的计算**；策略仍必须存在（校验 6），因为出参要带 `passwordValidDays` / `accountValidDays`，且校验 7 要用 `accountValidDays`。

**出参 `data`**：**刚创建的那条记录的 `UserDto`**（§5.3.1，17 个字段全给）：

| 字段 | 取值说明 |
|---|---|
| `userName` / `nickName` / `email` / `phoneNumber` / `roleIds` / `policyId` / `accountActiveAt` / `accountExpiresAt` | 入参值（空串已转 `NULL`，`roleIds` 还原成数组） |
| `enabled` | **落库后的实际值** —— 可能因「未到生效时间」被置 `0`，与入参不同 |
| `avatar` / `lastLoginTime` / `lastLoginIp` | 均为空（新建不写） |
| `createdAt` | 本次写入的时间值（`yyyyMMddHHmmss`） |
| `passwordChangedAt` / `passwordExpiresAt` | **空串 `""`** —— 本次落的是 `NULL`（§5.3.2 空值口径） |
| `passwordValidDays` / `accountValidDays` | 取自校验 6 已查到的策略对象，不额外查库 |
| `password` | **不出参** |

**校验（按序，任一不过即按其 `code` 返回）**

| 序 | 校验项 | 规则 | 不满足 → code（参数） |
|---|---|---|---|
| 1 | `userName` 非空 | `trim` 后非空 | `RequireParameterMissing`（`userName`） |
| 2 | `password` 非空 | 非空串 | `RequireParameterMissing`（`password`） |
| 3 | `policyId` 非空 | `trim` 后非空 | `RequireParameterMissing`（`policyId`） |
| 4 | `roleIds` 非空 | 集合**至少有 1 个元素**，不允许空数组 | `RequireParameterMissing`（`roleIds`） |
| 5 | 时间先后 | `accountActiveAt` **早于** `accountExpiresAt` | `ParameterOutOfRange`（`accountExpiresAt`） |
| 6 | `policyId` 存在性 | 按 `policyId` 查得到策略 | `PolicyNotFound`（`policyId`） |
| 7 | **`accountExpiresAt` 上限** | 策略 `accountValidDays != -1` 时：最晚日期 = `accountActiveAt + accountValidDays 天`，要求 `accountExpiresAt <= 最晚日期`（**等于允许**）；`accountValidDays = -1` 时**不校验** | `ParameterOutOfRange`（`accountExpiresAt`） |
| 8 | **`roleIds` 元素有效** | 集合内**每个** `roleId` 都能在 `FabViewerRole` 查到，**且该角色 `enabled = 1`** | 查不到 → `RoleNotFound`（`roleId`）；查到但停用 → `RoleDisabled`（`roleId`） |
| 9 | `userName` 查重 | 查无同 `userName` 记录 | `UserNameExists`（`userName`） |

- **参数类校验（1 ~ 5）在前，库查询类（6 ~ 9）在后** —— 入参不合法时少打数据库；校验 7 依赖校验 6 查到的策略，故排在其后。
- `email` / `phoneNumber` **不做格式校验**（定为不校验）。
- **角色必须存在且为启用状态**：不能挂停用角色；同一 `roleIds` 里只要有一个停用角色，整单拒绝，不做「跳过停用的只挂有效的」。口径与 §5.3.7 校验 6、§5.3.11 校验 7 一致。
- 密码复杂度（长度区间 / 大小写 / 数字 / 特殊字符）**本接口不校验** —— 新建属管理员配置动作；复杂度只在「修改密码」接口由后端校验（§9.3）。

**处理流程**

| 步 | 动作 |
|---|---|
| 1 | 按上表 1 ~ 9 顺序校验 |
| 2 | 按 §5.3.5「落库取值规则」算出 `enabled`；`passwordChangedAt` / `passwordExpiresAt` 直接给 `NULL` |
| 3 | `password` 哈希后连同其余字段一并交给**新建 TXN** 保存 |
| 4 | 取返回的 `UserEntity` 打包成 `UserDto` 返回；两个策略天数字段**复用步骤 1 校验 6 已取到的策略对象**，不再查库 |

#### 5.3.6 修改用户 `PUT /api/v1/users`

**语义**：只改**资料三项** —— `nickName`、`email`、`phoneNumber`。账号、密码、启用状态、角色、策略、时间字段都不在本接口。

**入参 `ModifyUserRo`**（body，4 个字段）

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `userName` | string | 是 | **定位键**，不改 |
| `nickName` | string | 否 | 昵称 |
| `email` | string | 否 | 邮箱 |
| `phoneNumber` | string | 否 | 手机号 |

**校验（按序）**

| 序 | 校验项 | 规则 | 不满足 → code（参数） |
|---|---|---|---|
| 1 | `userName` 非空 | `trim` 后非空 | `RequireParameterMissing`（`userName`） |
| 2 | `userName` 存在性 | 按 `userName` 查得到用户 | `UserNotFound`（`userName`） |

- `nickName` / `email` / `phoneNumber` **不做格式校验**（与新建一致）。
- 密码复杂度不涉及（本接口不碰密码）。

**写入方式**：**Modify Attribute 的 TXN**，只更新三列：

| 列 | 取值 |
|---|---|
| `NICKNAME` | 入参 `nickName`，`trim` 后空串 → `NULL` |
| `EMAIL` | 入参 `email`，`trim` 后空串 → `NULL` |
| `PHONENUMBER` | 入参 `phoneNumber`，`trim` 后空串 → `NULL` |

- **三项整体替换**：没传等同于传空，会把库里原值覆盖成 `NULL`（不是「不传就不动」）。
- `userName` 只定位、**不参与更新**；`updatedAt` / `updatedBy` 由框架赋值。

**处理流程**

| 步 | 动作 |
|---|---|
| 1 | 校验 `userName` 非空 |
| 2 | 按 `userName` 查用户，不存在即抛 `UserNotFound`（参数 `userName`）；**查到的用户同时用于出参** |
| 3 | 调 **Modify Attribute 的 TXN**，只更新上述三列 |
| 4 | 按 `policyId` 取策略带出 `passwordValidDays` / `accountValidDays`，组装 `UserDto` 返回 |

**出参 `data`**：修改后的 `UserDto`（§5.3.1，17 个字段全给）。

#### 5.3.7 修改角色与策略 `PUT /api/v1/users/role-policy`

**语义**：一次改用户的**角色集合**与**所属策略**两件事。账号、密码、资料三项、启用状态都不在本接口；两个过期时间列**只随策略变更被联动重算**，不接受前端直接指定。

**入参 `ModifyUserRolePolicyRo`**（body，3 个字段，全部必填）

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `userName` | string | 是 | **定位键**，不改 |
| `policyId` | string | 是 | 新的登录策略，**整体替换** |
| `roleIds` | string 集合 | 是 | 新的角色集合，**整体替换**；至少 1 个元素 |

**校验（按序，任一不过即按其 `code` 返回）**

| 序 | 校验项 | 规则 | 不满足 → code（参数） |
|---|---|---|---|
| 1 | `userName` 非空 | `trim` 后非空 | `RequireParameterMissing`（`userName`） |
| 2 | `policyId` 非空 | `trim` 后非空 | `RequireParameterMissing`（`policyId`） |
| 3 | `roleIds` 非空 | 集合**至少有 1 个元素**，不允许空数组 | `RequireParameterMissing`（`roleIds`） |
| 4 | `userName` 存在性 | 按 `userName` 查得到用户 | `UserNotFound`（`userName`） |
| 5 | `policyId` 存在性 | 按 `policyId` 查得到策略 | `PolicyNotFound`（`policyId`） |
| 6 | **`roleIds` 元素有效** | 集合内**每个** `roleId` 都能在 `FabViewerRole` 查到，**且该角色 `enabled = 1`** | 查不到 → `RoleNotFound`（`roleId`）；查到但停用 → `RoleDisabled`（`roleId`） |

- **参数类校验（1 ~ 3）在前，库查询类（4 ~ 6）在后**（与新建用户同序）。
- `roleIds` 元素**必须存在且为启用状态**：任一角色查不到或 `enabled = 0`，整单拒绝，不做部分生效。与 §5.3.5 校验 8、§5.3.11 校验 7 同一口径。
- 该校验**与用户自身是否启用无关**：停用中的账号改角色，同样只允许挂启用角色 —— 否则一旦启用就会被 §5.3.11 校验 7 报 `RoleDisabled` 拦住。
- 本接口**不做**「角色是否已被别的用户占用」之类的限制，一个角色可被多用户共用。

**写入方式**：**Modify Attribute 的 TXN**，只更新下列列：

| 列 | 取值 |
|---|---|
| `ROLEIDS` | 入参集合 → **JSON 数组字符串**，整体覆盖；如 `["ADMIN","OP"]` |
| `POLICYID` | 入参 `policyId`，整体替换 |
| `ACCOUNTEXPIRESAT` | **仅当 `policyId` 与库中现值不同时**才写，取值见下「过期时间调整」 |
| `PASSWORDEXPIRESAT` | 同上 |

- `userName` 只定位、**不参与更新**；`updatedAt` / `updatedBy` 由框架赋值。
- `policyId` 未变时，后两列**不出现在更新集合里**（不是"写回同值"）。
- 本接口**不重算 `enabled`**：策略收紧后可能立刻把 `ACCOUNTEXPIRESAT` 算到过去，此时库里出现「`enabled = 1` 且账户已过期」—— 按 §5.4.3，这是**合法状态**，登录由 auth 拦，本模块不做补偿。

**过期时间调整**

`policyId` 与库中现值**不同**时：**账户**过期时间按新策略重算；**密码**两列只在非空时才重算 —— **两列都为空则一起不动**（F / G 条）。`policyId` 未变时这些列一律不进更新集合。

| # | 项 | 口径 | 理由 |
|---|---|---|---|
| A | 触发条件 | 入参 `policyId` 与库中该用户现值**不同**才重算；相同则 `ACCOUNTEXPIRESAT` / `PASSWORDEXPIRESAT` 都不进更新集合 | 前端保存会把现值原样回传，若每次都重算，等于点一次保存把过期时间往后推一次，策略形同虚设 |
| B | `accountExpiresAt` | 新策略 `accountValidDays = -1` → **`NULL`**；`= N` → **`accountActiveAt + N 天`** | 该列语义是「生效时间 + 有效天数」，起点不动、只换天数；`accountActiveAt` 本身不改 |
| C | `passwordExpiresAt` | `passwordChangedAt` **非空**时：新策略 `passwdValidDays = -1` → **`NULL`**；`= N` → **`passwordChangedAt + N 天`**。为空时按 F / G 条 | 同上；`passwordChangedAt` **不重置** —— 换策略不是改密码 |
| D | 方向性 | 新策略更宽松就**直接放宽**，更严格就**直接收紧**；不做「只收紧不放宽」，也不做「取两者更早」 | 管理员显式换策略，就是要按新策略执行 |
| E | 重算后已过期 | 结果**按日**早于今天时**不拦截**，照写 | 策略收紧后的正常结果；要续就再走「账户延期」，要改密就提示用户改 |
| F | 密码两列**都为空** | `PASSWORDCHANGEDAT` / `PASSWORDEXPIRESAT` **一起不动**（保持 `NULL`）；`ACCOUNTEXPIRESAT` 仍按 B 条照常重算 | 两列为空 = 用户尚未自己改过密码（新建 / 重置后即此态），此时给密码算过期时间会破坏「待首次改密」语义 |
| G | `passwordChangedAt` 为空、`passwordExpiresAt` **有值**（脏数据） | **以 `passwordChangedAt` 为准**：把 `PASSWORDEXPIRESAT` 一并**清成 `NULL`** | 没有起点算不出过期时间；留一个指向旧策略的过期值反而误导，统一归一到「待首次改密」 |
| H | `accountActiveAt` 为空 | `accountExpiresAt` 写 `NULL`，**不报错** | 没有起点算不出终点，同属脏数据兜底 |

- 比较用的「原 `policyId`」取自处理流程步骤 2 查到的用户，不额外查库。
- 重算只由「策略变更」触发；只改 `roleIds` 时不碰任何时间列。

**处理流程**

| 步 | 动作 |
|---|---|
| 1 | 校验 1 ~ 3（参数类） |
| 2 | 按 `userName` 查用户：不存在 → 抛 `UserNotFound`；**查到即记下原 `policyId`**，该用户同时留作出参 |
| 3 | 按 `policyId` 查策略：不存在 → 抛 `PolicyNotFound`；策略对象后续复用，不重复查库 |
| 4 | 校验 6：`roleIds` 逐个查 `FabViewerRole` |
| 5 | 比对入参 `policyId` 与原 `policyId`，变化则按「过期时间调整」算出 `accountExpiresAt` / `passwordExpiresAt` |
| 6 | 调 **Modify Attribute 的 TXN**，按「写入方式」表落列 |
| 7 | 组装 `UserDto` 返回（两个天数字段取步骤 3 的策略对象） |

**出参 `data`**：修改后的 `UserDto`（§5.3.1，17 个字段全给）。`roleIds` 按新集合还原成数组；两个天数取自新策略。

#### 5.3.8 重置密码 `POST /api/v1/users/password`

**语义**：管理员给指定用户**重设密码**，同时把两个密码时间列**清空**，让用户下次登录被强制要求改密。只动密码，不动资料、角色、策略、启用状态。

**入参 `ResetPasswordRo`**（body，2 个字段）

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `userName` | string | 是 | **定位键** |
| `password` | string | 是 | **新密码明文**，落库前哈希；出参永不返回 |

**校验（按序，任一不过即按其 `code` 返回）**

| 序 | 校验项 | 规则 | 不满足 → code（参数） |
|---|---|---|---|
| 1 | `userName` 非空 | `trim` 后非空 | `RequireParameterMissing`（`userName`） |
| 2 | `password` 非空 | 非空串 | `RequireParameterMissing`（`password`） |
| 3 | `userName` 存在性 | 按 `userName` 查得到用户 | `UserNotFound`（`userName`） |

- `password` **不做 `trim`**（已定）：原值逐字参与哈希，首尾空格是密码的一部分。相应地，前端也必须原样提交，不能在提交前 `trim`；登录校验同样按原值比对。

**写入方式**：**Modify Attribute 的 TXN**，只更新下列三列：

| 列 | 取值 |
|---|---|
| `PASSWORD` | 入参明文 → **哈希**（算法由框架层提供，与新建同口径，§5.3.5） |
| `PASSWORDCHANGEDAT` | **`NULL`** |
| `PASSWORDEXPIRESAT` | **`NULL`** |

- 两列**与新建同口径**：清空即「用户尚未自己设置密码」，登录时强制提示改密。
- 不按 `passwdValidDays` 推算，故**本接口不依赖策略做校验**；策略只用于出参带两个天数，查不到时为 `null`（§5.3.1 出参容错）。
- 与 §5.3.7 的 F 条一致：本接口置空后两列都为空，此时管理员换策略，这两列**一起不动**。

**本接口不做的**（边界）

| 不做的事 | 原因 |
|---|---|
| 密码复杂度校验（长度区间 / 大小写 / 数字 / 特殊字符） | 与新建一致（§5.3.5）：属管理员配置动作，**本接口不校验**；复杂度只在「修改密码」接口由后端校验（§9.3） |
| 新旧密码相同校验 | 库里只存哈希，本接口也不收旧密码，无从比对 |
| 清 `lastLoginTime` / `lastLoginIp` | **不清**：重置密码不是登录，不动这两个字段 |
| 踢掉已有会话（强制下线） | **暂缓**：本期不实现、不纳入验收（U-50 ~ U-55），后续版本再定。当前口径是重置密码后旧会话**继续有效**，直到 token 自然过期（`jwt.ttl`，默认 1 小时，§9.2.1）；后端不做空闲计时，前端的空闲登出只影响本地 token |
| 解锁「密码错误次数」 | 本表无该字段，不做 |

**处理流程**

| 步 | 动作 |
|---|---|
| 1 | 校验 1 ~ 2（参数类） |
| 2 | 按 `userName` 查用户：不存在 → 抛 `UserNotFound`；用户对象留作出参 |
| 3 | `password` 哈希 |
| 4 | 调 **Modify Attribute 的 TXN**：写 `PASSWORD`，另两列写 `NULL` |
| 5 | 按该用户 `policyId` 查策略带出 `passwordValidDays` / `accountValidDays`，组装 `UserDto` 返回；查不到策略时这两字段出参 `null`（§5.3.1 出参容错） |

**出参 `data`**：重置后的 `UserDto`（§5.3.1，17 个字段全给）。`password` 不出参；`passwordChangedAt` / `passwordExpiresAt` 为**空串 `""`**（本次置 `NULL`）。

#### 5.3.9 删除用户 `DELETE /api/v1/users?userName=xxx`

**语义**：物理删除一整行用户记录。**只允许删已停用的账号** —— 启用中的必须先停用再删，防止误删在线账号。

**入参**（query）

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `userName` | string | 是 | 用户账号，定位用 |

**校验（按序，任一不过即按其 `code` 返回）**

| 序 | 校验项 | 规则 | 不满足 → code（参数） |
|---|---|---|---|
| 1 | `userName` 非空 | `trim` 后非空 | `RequireParameterMissing`（`userName`） |
| 2 | `userName` 存在性 | 按 `userName` 查得到用户 | `UserNotFound`（`userName`） |
| 3 | **启用状态** | 库中 `enabled = 0` | `UserDeleteWhileEnabled`（`userName`） |

- 校验 2 查到的用户对象同时用于校验 3，**不重复查库**；因出参为空，查完不再组装 `UserDto`。
- **不做任何管理员保护判定**（如「是否为最后一个管理员」）—— 哪个账号算管理员由前端判定，后端不识别，见 §6.3。

**删除方式**：**删除 TXN**，按 `userName` 物理删除整行。本表**无逻辑删除标记列**，不做软删。

**出参 `data`**：**空** —— 与角色删除（§3.5）、策略删除（§4.2.6）统一。成功与否只看响应包 `success` / `code`，不回被删对象。

**处理流程**

| 步 | 动作 |
|---|---|
| 1 | 校验 `userName` 非空 |
| 2 | 按 `userName` 查用户：不存在 → 抛 `UserNotFound`；查到即校验 `enabled = 0`，否则抛 `UserDeleteWhileEnabled` |
| 3 | 调**删除 TXN** 物理删除该行 |
| 4 | 返回成功，`data` 为空 —— **不组装 `UserDto`**，步骤 2 查到的用户只用于存在性与 `enabled` 校验 |

#### 5.3.10 更新属性 `POST /api/v1/users/attribute`

**语义**：**一次只改一个属性**，属性名由入参给。可选属性固定四个：`nickName` / `email` / `phoneNumber` / `avatar`；要改多个就调多次。

**入参 `UserAttributeRo`**（body，3 个字段）

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `userName` | string | 是 | **定位键**，不改 |
| `attName` | string | 是 | **属性名**，仅限 `nickName` / `email` / `phoneNumber` / `avatar` |
| `attValue` | string | 否 | 该属性的新值；`trim` 后为空 → 落 `NULL` |

**`attName` → 列名映射**

| `attName` | 列名 | 说明 |
|---|---|---|
| `nickName` | `NICKNAME` | `varchar2(63)` |
| `email` | `EMAIL` | `varchar2(100)` |
| `phoneNumber` | `PHONENUMBER` | `varchar2(30)` |
| `avatar` | `AVATAR` | `CLOB`，存头像 **hash**，不存图片本体 |

**校验（按序，任一不过即按其 `code` 返回）**

| 序 | 校验项 | 规则 | 不满足 → code（参数） |
|---|---|---|---|
| 1 | `userName` 非空 | `trim` 后非空 | `RequireParameterMissing`（`userName`） |
| 2 | `attName` 非空 | `trim` 后非空 | `RequireParameterMissing`（`attName`） |
| 3 | **`attName` 白名单** | 必须是上述四个之一（**大小写敏感**，不做别名、不做转换） | `InvalidParameterValue`（`attName`） |
| 4 | `userName` 存在性 | 按 `userName` 查得到用户 | `UserNotFound`（`userName`） |

- `attValue` **不做非空校验** —— 传空串就是「把该属性清成 `NULL`」，这是合法的清空动作。
- `attValue` **不做格式校验**：邮箱格式、手机号格式、`avatar` 值是否合法都不管（与新建一致，§5.3.5）；`avatar` 只当作不透明字符串存。
- 一次请求**只允许一个属性**，不做批量 —— 入参结构本身不支撑多属性。

**写入方式**：**Modify Attribute 的 TXN**，按 `attName` 映射到列后**只写这一列**，其余列一个都不动：

| 场景 | 更新列 |
|---|---|
| `attName = nickName` | 仅 `NICKNAME` |
| `attName = email` | 仅 `EMAIL` |
| `attName = phoneNumber` | 仅 `PHONENUMBER` |
| `attName = avatar` | 仅 `AVATAR` |

- `userName` 只定位、**不参与更新**；`updatedAt` / `updatedBy` 由框架赋值。
- 一次请求只产生**一列**更新，不会顺带改其他属性（区别于 §5.3.6「修改用户」的整体替换三项）。

**出参 `data`**：修改后的 `UserDto`（§5.3.1，17 个字段全给）。

**处理流程**

| 步 | 动作 |
|---|---|
| 1 | 校验 1 ~ 3（参数类） |
| 2 | 按 `userName` 查用户：不存在 → 抛 `UserNotFound`；用户对象留作出参 |
| 3 | `attName` 映射到列名；`attValue` `trim` 后为空则取 `NULL`，否则取 `trim` 后的值 |
| 4 | 调 **Modify Attribute 的 TXN**，只写映射到的那一列 |
| 5 | 组装 `UserDto` 返回（两个天数字段按 `policyId` 左连接取，取不到为 `null`） |

#### 5.3.11 启用 / 停用 `POST /api/v1/users/enabled`

**语义**：切换单个用户的启用状态。**入参给的目标状态必须与库里现值不同**，同值即报错 —— 本接口**不幂等**，重复提交会失败。启用方向（`false → true`）要过**五道**校验：账户已生效、账户未过期（口径同 §5.4.2 的 C1 / C2），角色已配置、角色全部启用、策略已配置；**密码是否过期不在本接口拦**，由登录判定（§5.4.7）。停用方向（`true → false`）五道**全部跳过** —— 不看账户有效期，也不看角色与策略。

**入参 `UserStateRo`**（body，3 个字段）

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `userName` | string | 是 | **定位键**，不改 |
| `enabled` | bool | 是 | **目标状态**：`true` 启用、`false` 停用 |
| `remark` | string | 否 | 操作备注，**只打日志**，不落库、不出参 |

**校验（按序，任一不过即按其 `code` 返回）**

| 序 | 校验项 | 规则 | 不满足 → code（参数） |
|---|---|---|---|
| 1 | `userName` 非空 | `trim` 后非空 | `RequireParameterMissing`（`userName`） |
| 2 | `userName` 存在性 | 按 `userName` 查得到用户 | `UserNotFound`（`userName`） |
| 3 | **状态必须变更** | 入参 `enabled` **不等于**库中 `enabled` | `UserEnabledStateUnchanged`（无参数） |
| 4 | **账户已生效**（仅启用方向） | 口径同 §5.4.2 **C1**：`accountActiveAt` 非空且**按日**不晚于今天（`TRUNC(accountActiveAt) <= TRUNC(now())`） | `UserAccountNotEffective`（无参数） |
| 5 | **账户未过期**（仅启用方向） | 口径同 §5.4.2 **C2**：`accountExpiresAt` 为空 或**按日**不早于今天（`TRUNC(accountExpiresAt) >= TRUNC(now())`） | `UserAccountExpired`（无参数） |
| 6 | **角色已配置**（仅启用方向） | `roleIds` 非空（至少一个），且每个 `roleId` 都能查到角色 | 为空 → `UserRoleNotConfigured`（无参数）；某个查不到 → `RoleNotFound`（`roleId`） |
| 7 | **角色必须启用**（仅启用方向） | 校验 6 查到的每个角色都满足 `enabled = 1` | `RoleDisabled`（`roleId`） |
| 8 | **策略已配置**（仅启用方向） | `policyId` 非空，且能按 `policyId` 查到策略 | 为空 → `UserPolicyNotConfigured`（无参数）；查不到 → `PolicyNotFound`（`policyId`） |

- 校验 4 ~ 8 **只在 `false → true` 时执行**；`true → false`（停用）全部跳过，四个时间列一个都不看，角色与策略也不查。
- 校验 6 ~ 8 是**启用前置条件**：角色与策略是账号可用的最低配置，缺一项就不放行；一旦启用后角色被停用、策略被删，本接口**不回溯**（下次启用时才拦）。
- 校验 7 与 §5.3.5 校验 8、§5.3.7 校验 6 判的是同一件事，但**不是重复**：配角色时角色是启用的，之后仍可能被停用，所以启用这一刻要复查一次。
- 校验 6 / 8 报 `RoleNotFound` / `PolicyNotFound` 的典型来源：该用户停用期间，其角色或策略被删掉了（删除**不做级联清理**，§3.5 / §4.2.6）。**本接口不自动修复、不猜替代项**，只报错；处置是管理员先用 §5.3.7 重配角色与策略，再重新启用。
- 先看「有没有生效」，再看「有没有过期」—— 账户还没到生效时间就谈不上过期。
- **`accountActiveAt` 为 `NULL` → 不允许启用**（不视为「已生效」）。
- **`accountExpiresAt` 为 `NULL` → 不构成阻碍**，仍可启用（策略 `accountValidDays = -1` 时的真实状态）。
- 时间比较**一律按日、不看小时**：`accountActiveAt` **等于今天算已生效**；`accountExpiresAt` **等于今天算未过期**，明天才算过期。两侧都取 `TRUNC` 后比（`TRUNC(accountActiveAt) <= TRUNC(now())`、`TRUNC(accountExpiresAt) >= TRUNC(now())`）。
- **`enabled` 是管理员开关**：本接口是唯一能改**已存在用户** `enabled` 的入口（另一处写 `enabled` 只有新建算初值，§5.3.5），改完就是管理员的最终决定，不会被任何后台动作覆盖（§5.4.3）。
- 校验 2 查到的用户对象直接用于校验 3 和出参；校验 4 ~ 8 另查 `roleIds` / `policyId` 与角色、策略表，**用户表只查这一次**。

**本接口不校验的**

| 项 | 现状 |
|---|---|
| 管理员账号是否可停用 | 不校验，由前端管控（§6.3） |

**写入方式**：**Modify Attribute 的 TXN**，只写 `ENABLED` 一列（`true → 1`、`false → 0`）；其余列不动。

**`remark` 的处置**

- **只打日志**，不落库（本表无备注列）、不进响应包。
- 日志内容必须带三样：`userName`、`from`（库中旧值）、`to`（入参新值），外加 `remark` 原文。例如：

```
user enabled changed: userName=zhangsan, from=0, to=1, remark=账号已确认归属
```

- 日志级别、输出目标、是否附带操作人与时间，按框架日志规范，本模块只规定上述要素必须出现。

**出参 `data`**：切换后的 `UserDto`（§5.3.1，17 个字段全给），`enabled` 为新值。

**处理流程**

| 步 | 动作 |
|---|---|
| 1 | 校验 `userName` 非空 |
| 2 | 按 `userName` 查用户：不存在 → 抛 `UserNotFound`；**记下库中 `enabled`**，用户对象留作出参 |
| 3 | 比对入参 `enabled` 与库中值：相同 → 抛 `UserEnabledStateUnchanged` |
| 4 | 入参为 `true` 时，依次校验账户已生效（4）、账户未过期（5）、角色已配置（6）、角色全部启用（7）、策略已配置（8）；`false` 时全部跳过 |
| 5 | 调 **Modify Attribute 的 TXN**，只写 `ENABLED` |
| 6 | 打变更日志（含 `remark`） |
| 7 | 组装 `UserDto` 返回（两个天数字段按 `policyId` 左连接取，取不到为 `null`） |

#### 5.3.12 账户延期 `POST /api/v1/users/expire`

**语义**：改账户的失效时间（可延长、也可缩短）。**只改这一列，不碰 `enabled`、不碰密码、不碰角色、不碰策略、不碰资料。**

**入参 `UserExpireRo`**（body，3 个字段）

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `userName` | string | 是 | **定位键**，不改 |
| `preAccountExpiresAt` | time | 是 | 前端读到的**旧失效时间**，只用于比对，不落库 |
| `newAccountExpiresAt` | time | 否 | **新失效时间**；策略 `accountValidDays = -1` 时可为空，非 `-1` 时必填 |

- 时间线格式同 §5.3.2：`yyyyMMddHHmmss` 字符串。

**校验（按序，任一不过即按其 `code` 返回）**

| 序 | 校验项 | 规则 | 不满足 → code（参数） |
|---|---|---|---|
| 1 | `userName` 非空 | `trim` 后非空 | `RequireParameterMissing`（`userName`） |
| 2 | `userName` 存在性 | 按 `userName` 查得到用户 | `UserNotFound`（`userName`） |
| 3 | **旧值一致性**（并发控制） | `preAccountExpiresAt` 与库中 `accountExpiresAt` **按日期比对（不含时间）** 必须相同 | `UserExpireDateChanged`（无参数） |
| 4 | 策略可取 | 按该用户 `policyId` 查得到策略 | `PolicyNotFound`（`policyId`） |
| 5 | **新值必填判定** | 策略 `accountValidDays != -1` 时，`newAccountExpiresAt` **必须有值**；`= -1` 时**可为空** | `RequireParameterMissing`（`newAccountExpiresAt`） |

**校验 3 的比对口径**

| 项 | 口径 |
|---|---|
| 比对粒度 | **只比到日**，`TRUNC(库中 accountExpiresAt)` 与 `TRUNC(preAccountExpiresAt)` 相等即可通过 |
| 为什么忽略时间 | 前端拿到的旧值可能被格式化过（时间部分精度不同），比到日足够拦住「别人已经改过」的并发场景 |
| 库中为 `NULL` | 入参也应为空 —— **两边都为空视为一致**；库空而入参有值（或反过来）→ 视为不一致，报校验 3 的异常 |

**明确不校验的**

| 不校验 | 说明 |
|---|---|
| `newAccountExpiresAt` 与库中旧值的大小关系 | **不管是延长还是缩短都放行**，不做「必须更晚」的限制 |
| `newAccountExpiresAt` 与今天的关系 | 允许填一个已经过去的日期（等于把账户直接置为过期）；按日判断，**填今天不算过去**。本接口**不改 `enabled`**，账户过期后能否登录由 auth 拦（§5.4.7），`enabled` 仍保持管理员设定值 |
| `newAccountExpiresAt` 与策略 `accountValidDays` 的上限关系 | 本接口**不做**上限校验（区别于 §5.3.5 新建时的校验 7） |

**写入方式**：**Modify Attribute 的 TXN**，只更新一列：

| 列 | 取值 |
|---|---|
| `ACCOUNTEXPIRESAT` | 入参 `newAccountExpiresAt`；为空 → `NULL` |

**`enabled` 不重算**

- 本接口**不调 `CalcEnabled`、不写 `ENABLED`**。
- 原来「延期后自动重算 `enabled`」的做法**作废**：它会把管理员手动停用的账号悄悄置为启用。现在 `enabled` 只由新建（初值）和启停（人工）决定。
- 延期后账户确实过期了，库里会出现「`enabled = 1` 且账户已过期」—— 按 §5.4.3 这是**合法状态**，登录时由 auth 拦（§5.4.7）。要禁止登录就再走一次停用。

**出参 `data`**：延期后的 `UserDto`（§5.3.1，17 个字段全给）；`enabled` **与入参前相同**，本接口不改它。

**处理流程**

| 步 | 动作 |
|---|---|
| 1 | 校验 `userName` 非空 |
| 2 | 按 `userName` 查用户：不存在 → 抛 `UserNotFound`；用户对象留作出参，并记下 `accountExpiresAt` / `enabled` |
| 3 | 比对 `preAccountExpiresAt` 与库中 `accountExpiresAt`（**只比到日**），不一致 → 抛 `UserExpireDateChanged` |
| 4 | 按 `policyId` 查策略：不存在 → 抛 `PolicyNotFound`；取 `accountValidDays` 判断新值是否必填 |
| 5 | 调 **Modify Attribute 的 TXN**，只写 `ACCOUNTEXPIRESAT` |
| 6 | 组装 `UserDto` 返回（两个天数字段取步骤 4 的策略对象） |

### 5.4 时间列与 `enabled` 的联动

#### 5.4.1 五个字段的分工

| 组 | 字段 | 管什么 | 谁写 |
|---|---|---|---|
| 账户时间 | `accountActiveAt`、`accountExpiresAt` | 账号**能不能用** | 新建写入两列；改策略（§5.3.7）、账户延期（§5.3.12）只重写 `ACCOUNTEXPIRESAT`。**`ACCOUNTACTIVEAT` 只在新建写入，其余任何接口都不改** |
| 密码时间 | `passwordChangedAt`、`passwordExpiresAt` | 密码**能不能用**、要不要首次改密 | 新建（§5.3.5）与重置密码（§5.3.8）**一律置 `NULL`**；改策略（§5.3.7）按 C / F / G 条重算；**用户自助改密写这两列在 auth（§9.3）**（`passwordChangedAt = now()`、按策略重算到期日）。用户管理模块**本身不提供改密接口**。密码是否过期**只在登录时判**（§5.4.7），与 `enabled` 无关 |
| 开关 | `enabled` | 管理员的**启用 / 禁用开关** | **只有两处**：新建（§5.3.5，按 `CalcEnabled` 算初值）、启停（§5.3.11，人工）。其余接口一律不动 |

> `passwordChangedAt` 为空 **不等于过期**，它表示「用户从未自己设过密码」，是「首次登录强制改密」的判定依据（§5.1.1）。

#### 5.4.2 `enabled` 公共判定 `CalcEnabled`

**用途**：**只给新建（§5.3.5）算 `enabled` 初值**。只看**账户的两个日期**，**不检查密码**。其余接口一律不调用本函数、不改 `enabled`。

**入参**：`accountActiveAt`、`accountExpiresAt`、`now`。**出参**：`bool`。

**两个条件**

| # | 条件 | 具体规则 |
|---|---|---|
| C1 | 账户已生效 | `accountActiveAt` **不为空** 且 **按日**不晚于今天（`TRUNC(accountActiveAt) <= TRUNC(now())`） |
| C2 | 账户未过期 | `accountExpiresAt` **为空** 或 **按日**不早于今天（`TRUNC(accountExpiresAt) >= TRUNC(now())`） |

- **`true`** ⇔ C1 ∧ C2
- 任一不成立 → **`false`**

**`NULL` 的处理**

| 列 | 为 `NULL` 时 |
|---|---|
| `accountActiveAt` | C1 不成立 → **`false`** |
| `accountExpiresAt` | C2 **不构成阻碍**（视为不限制） |

**时间比较口径**：**一律按日，只比到天、不看小时**。`accountActiveAt` 等于今天 = 已生效；`accountExpiresAt` 等于今天 = 未过期，次日才算过期。两列虽存 `TIMESTAMP`，但**设置时只带日期、不带具体几点**，所以比较前统一取 `TRUNC`：`TRUNC(accountActiveAt) <= TRUNC(now())`、`TRUNC(accountExpiresAt) >= TRUNC(now())`。

**与入参的组合**：落库值 = **入参意愿 ∧ `CalcEnabled`**

| 入参 `enabled` | `CalcEnabled` | 落库 |
|---|---|---|
| `false` | 任意 | `0`（尊重入参，不看时间） |
| `true` | `true` | `1` |
| `true` | `false` | `0` |

**为什么不检查密码**

`enabled` 是管理员开关，密码状态不该影响它。新建时密码两列本来就是 `NULL`（待首次改密），若拿密码来判，新用户会被直接判成停用。密码是否过期**只在登录时**由 auth 判（§5.4.7）。

**调用点**

| 调用点 | 用法 |
|---|---|
| §5.3.5 新建 | **唯一的调用点**，用于算 `enabled` 初值 |
| 其他接口 | **一律不调用**。启停是管理员直接置值（§5.3.11），延期只改失效时间（§5.3.12） |

#### 5.4.3 `enabled` 的定义

| 项 | 口径 |
|---|---|
| 语义 | **管理员的启用 / 禁用开关**：是否允许该账号使用。**不是**随时间自动变化的派生值 |
| 值从哪来 | 只有两处：① 新建（§5.3.5）算初值；② 启停（§5.3.11）由管理员显式修改 |
| 其他接口 | **一律不动 `enabled`** —— 改策略、重置密码、账户延期、改资料、改属性都不碰 |
| 库里 `enabled = 1` 但账户已过期 | **合法状态**，不视为脏数据、不补偿、不引定时任务或触发器 |
| 能否登录 | 由 auth 在登录时按时间字段**实时判定**（§5.4.7）；`enabled = 0` 一定进不去 |
| 启用的前置配置 | 启用那一刻还要求**角色与策略就绪**（§5.3.11 校验 6~8）；这是启用时的快照校验，不随时间变化，也不在登录时复查 |

> 一句话：**`enabled = 0` 是人工禁令，一定拦；`enabled = 1` 只是没有禁令，能不能进还要看时间。**

#### 5.4.7 登录时的判定（归 auth，本模块只保证数据自洽）

本模块**不实现**登录拦截，只把五个字段写成上表的样子。auth 侧按下列口径判定（**实现与提示文案归 auth，本节只做对齐**）：

| 判定 | 条件 | 结果 |
|---|---|---|
| 账号停用 | `enabled = 0` | `ACCOUNT_LOCKED`，拒绝 |
| 账户未生效 | `accountActiveAt` 为空 或 按日晚于当前日期 | `ACCOUNT_NOT_EFFECTIVE`，拒绝 |
| 账户已过期 | `accountExpiresAt` 非空 且 按日早于当前日期 | `ACCOUNT_EXPIRED`，拒绝 |
| 密码错误 | 哈希比对不通过 | `AUTH_FAILED`，拒绝 |
| 密码待首次修改 | `passwordChangedAt` 为空 | `FIRST_LOGIN`，**不发 `token`，登录页跳转改密** |
| 密码已过期 | `passwordChangedAt` 非空 且 `passwordExpiresAt` 非空 且 按日早于当前日期 | `PASSWORD_EXPIRED`，拒绝 |

> **时间判定一律按「日」比较**：到期当天仍有效，次日才失效（详见 §9.2）。
> **密码过期只在这里判**，本模块的 `enabled` 不看密码（§5.4.2）—— 所以密码过期的账号可能 `enabled = 1`，但登不进去，这是设计如此。

### 5.5 用户验收规则

> 验收方式与角色 / 策略一致：接口级，既看响应包（`success` / `code` / `errMsg` / `data`），也回查库中实际值。编号 U-01 ~ U-94，按接口顺序排列；每个接口先验「成功路径」，再验「拒绝路径」，拒绝路径需同时确认**库中未被改动**。

| `CreatedAt` | `string` | `createdAt` | `yyyyMMddHHmmss` |
| `AccountActiveAt` / `AccountExpiresAt` / `PasswordChangedAt` / `PasswordExpiresAt` / `LastLoginTime` | `string` | 同名 | `NULL` → **空串 `""`**（§5.3.2） |

- 时间列在 Dto 里是 `string`（`yyyyMMddHHmmss`），`time.Time` 只出现在 Entity / Po（§5.3.2）。
- `Password` 不在 Dto 里（§5.3.1）。

## 九、认证（auth）

### 9.1 表 `FabViewerLoginHist`

登录历史记录表。业务字段 7 列，类型与长度见下表，字段口径见 §9.1.1；基础列按 §1.8 由底层对象统一提供，本文不规定。

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `userName` | `varchar2(63)` | NOT NULL | 登录账号（与用户表同宽，§1.9） |
| `loginTime` | `TIMESTAMP` | NOT NULL | 登录时间 |
| `loginIp` | `varchar2(45)` | — | 登录来源 IP（兼容 IPv6） |
| `success` | `Number(1)` | NOT NULL | 登录是否成功（`0` / `1`） |
| `failCode` | `varchar2(50)` | — | 失败码（标识类，§1.9 默认 50） |
| `deviceId` | `varchar2(255)` | — | 设备标识（**预留 255**，不按 `Id` 默认 50 收） |
| `failMessage` | `varchar2(255)` | — | 失败信息（提示串） |

> 本表另含 §1.8 的基础列，**由底层框架统一提供，本文不规定、不落 DDL**。
>
> `deviceId` 是本表**唯一的宽度特例**：列名带 `Id`，按 §1.9 默认应为 50，但设备标识由前端上报、格式未约束，**预留 255** 兜住较长串。

#### 9.1.1 字段口径（已定）

| 项 | 口径 |
|---|---|
| `success` | `1` = **登录成功**（只有正常登录这一种）；`0` = **登录未成功**（其余 6 个码全部记 `0`），`failCode` 与 `failMessage` 由失败码枚举指定（§9.1.2）。**`success = 1` 时两列必为空** |
| `success` 与接口响应包无关 | **本列记的是「登录这件事成不成」，不是「接口调用成不成」**。进入业务判定后，不论登录成功还是失败，响应包的 `success` **恒为 `1`**（§1.4 例外）；登录结果改由响应包 `code` 承载（§9.1.3）。所以**同一个 `FIRST_LOGIN`，响应包 `success = 1`、本列 `success = 0`** |
| `deviceId` | **由前端上报**，服务端不生成 |
| 记录范围 | **进入业务判定后每次尝试都记一条**。`success = 1` 只有「正常登录」一种；其余 6 个码（含 `FIRST_LOGIN`）一律 `success = 0`。**接口层响应包 `success` 始终为 `1`**（三类普通报错除外，见 §9.2 校验 1 ~ 4） |

#### 9.1.2 失败码 `failCode` 取值

**码值已定，共 6 个**，含义与触发条件如下（表的顺序**就是判定顺序**）：

| 序 | `failCode` | 含义 | 触发条件（登录时判定） | `success` 列 |
|---|---|---|---|---|
| 1 | `ACCOUNT_NOT_EFFECTIVE` | 账户未生效 | `accountActiveAt` **为空** 或 **按日晚于当前日期**（`TRUNC(accountActiveAt) > TRUNC(now())`） | `0` |
| 2 | `ACCOUNT_LOCKED` | 账户已停用 | `enabled = 0`（`false`） | `0` |
| 3 | `ACCOUNT_EXPIRED` | 账户已过期 | `accountExpiresAt` **非空** 且 **按日早于当前日期**（`TRUNC(accountExpiresAt) < TRUNC(now())`） | `0` |
| 4 | `AUTH_FAILED` | 密码错误 | 入参密码与库中哈希比对不通过 | `0` |
| 5 | `FIRST_LOGIN` | 首次登录未改密 | `passwordChangedAt` **为空** | `0` |
| 6 | `PASSWORD_EXPIRED` | 密码已过期 | `passwordExpiresAt` **非空** 且 **按日早于当前日期**（`TRUNC(passwordExpiresAt) < TRUNC(now())`） | `0` |

**判定顺序（已定，按序执行、命中即返回）**

`ACCOUNT_NOT_EFFECTIVE` → `ACCOUNT_LOCKED` → `ACCOUNT_EXPIRED` → `AUTH_FAILED` → `FIRST_LOGIN` → `PASSWORD_EXPIRED`

- 顺序**固定**：先判账户三项可用性，再验密码，密码通过后才看密码的两个时间关系。
- **命中即返回**，不再往下判 —— 一次登录只落一个 `failCode`，登录历史表里也只有一行。
- 密码比对放在账户三项之后：账户本身不可用时**不验密码**，避免白算哈希。

> **账户不存在不在这 6 个码里，也不写登录历史**：按 `userName` 查不到用户记录时，登录接口**直接走普通失败壳**（`success = 0`，`code` 用 `UserNotFound` / `PolicyNotFound`，文案由 i18n 生成），与其余接口的报错方式一致，见 §9.2 校验 3。**账号本身不存在，登录历史没有可归属的主体，不落 `FabViewerLoginHist`** —— 历史表只记「进入业务判定」的尝试。**绑定策略不存在同理**：策略缺失是数据问题、不是一次登录尝试，同样直接抛错、不写历史（§9.2 校验 4）。

> **`FIRST_LOGIN` 在响应包与历史表里的 `success` 取值不同**：响应包 `success = 1`（接口调用本身成功，用户还在登录页），**历史表 `success = 0`**（这次没登进去，只是「要求改密」而非「拒绝」）。前端收到该码后**自动跳转到修改密码页**。
>
> **`ACCOUNT_LOCKED` 不是「密码错误次数超限锁定」** —— 本模块不引入失败次数计数、不引入锁定计时、不新增锁定标记列。该码只表达「库里 `enabled = 0`」这一件事（§5.4.3：`enabled = 0` 即人工禁令），失败次数不锁号见 §9.2.2。
>
> **三处 `NULL` 均不构成拒绝**：`accountExpiresAt` 为空不判 `ACCOUNT_EXPIRED`；`passwordExpiresAt` 为空不判 `PASSWORD_EXPIRED`；`passwordChangedAt` 为空判 `FIRST_LOGIN`（`NULL` 是「从未改密」这个正常态，见 §5.1.1）。
>
> **入参为空同样不入码**：`userName` / `password` 为空属参数校验失败，直接 `success = 0` 返回，`code` 取 `RequireParameterMissing`、文案由 i18n 生成，不写登录历史。
>
> **`failMessage` 取值走框架 i18n**：后端**不硬编码文案**，按「`failCode` → i18n 资源键」的映射取当前语言的译文写入 `failMessage` 列；返回给前端时同样取译文。**6 个码的中文与 English 文案见 §10.2**。

#### 9.1.3 响应包与历史记录的码值对应

**同一个码在三个地方用，取值完全一致**：响应包 `code`、历史表 `failCode`、i18n 资源键（一一对应）。

| 场景 | 响应包 `success` | 响应包 `code` | 历史表 `success` | 历史表 `failCode` | 历史表 `failMessage` |
|---|---|---|---|---|---|
| 正常登录成功 | `1` | `OK` | `1` | 空 | 空 |
| 首次登录未改密（`FIRST_LOGIN`） | `1` | `FIRST_LOGIN` | **`0`** | `FIRST_LOGIN` | 取 i18n 译文 |
| 五种拒绝登录 | `1` | 各失败码 | `0` | 各失败码 | 取 i18n 译文 |
| 参数校验失败 / 账户不存在 / 绑定策略不存在 | **`0`** | `RequireParameterMissing` / `UserNotFound` / `PolicyNotFound` | 不写 | 不写 | 不写 |

- **前端判定**：`success = 1` 且 `code = OK` → 登录成功，用 `data` 里的 `token` 进系统；`success = 1` 且 `code` 为上述码 → 不进系统，按码执行后续动作（弹错 / 在登录页跳转修改密码）。
- **进入业务判定后响应包 `success` 恒为 `1`**：登录结果不通过 `success` 表达（§1.4 例外）；参数校验失败、账户不存在、绑定策略不存在这三类仍为 `success = 0`。
- **`code` 与 `failCode` 是同名字面值**：不在响应里转成别的写法，历史表和响应包都用 `ACCOUNT_LOCKED` 这类大写码。
- **i18n 一一对应**：每个 `failCode` 在框架 i18n 资源里有**且只有一个**对应键；`failMessage` 列存的、以及返回给前端的文案，都从该键取当前语言译文，**后端不硬编码任何文案**。6 个码的中英文案见 §10.2。
- **登录历史 `success` 的写法**：**只有正常登录记 `1`**，6 个码（含 `FIRST_LOGIN`）一律记 `0`。注意 `FIRST_LOGIN` 的**响应包** `success` 是 `1`、**历史表**是 `0`，两者故意不同：接口没失败，但这次确实没登进去。
- **`data` 只有 `code = OK` 时才有内容**：正常登录成功返回 `LoginDto`（§9.1.4）；其余 6 个码（含 `FIRST_LOGIN`）`data` 一律为**空对象 `{}`**。
- **`FIRST_LOGIN` 不单独走放行分支**：不发 `token`、不返回 `LoginDto`，与其余 5 个码一样只给 `code`；区别在于它是「要求改密」而不是「拒绝」，前端在**登录页**据该码自动跳转到修改密码。
- **响应包 `errMsg` 一律留空串**（仅指 6 个登录结果码）：错误信息不通过 `errMsg` 下传，前端只认 `code`，文案由前端按同一个 i18n 资源自行取；`errMsg` 只在服务端内部错误场景由框架填充。
- **三类普通报错不同**：参数校验失败、账户不存在、绑定策略不存在属普通失败壳 —— 响应包 `success = 0`、`code` 取 §7.1 / §7.2 的业务码（不在 6 个登录结果码之内）、`errMsg` 由 i18n **照常填写**；这三类**不写登录历史**。

#### 9.1.4 登录出参 `LoginDto`

**仅当 `code = OK`**（正常登录成功）时，响应包 `data` 为 `LoginDto`：

| # | 字段 | 类型 | 说明 |
|---|---|---|---|
| 1 | `token` | string | 会话令牌 —— JWT，调**库的生成 token 方法**生成；**有效期由 `jwt.ttl` 换算（空 → 1 小时，非法或 > 24 → 24 小时）**（§9.2.1） |
| 2 | `idleLogoutMinutes` | number | 空闲登出分钟数，**取自该用户所挂策略的 `idleLogoutMinutes`**；`-1` = 不因空闲登出 |
| 3 | `user` | object | `UserDto`（§5.3.1），17 个字段带出。**用步骤 9 改完 `lastLoginTime` / `lastLoginIp` 之后的那个对象组装** —— 本次登录的时间与 IP 当场就能看到 |

- `idleLogoutMinutes` 与策略表同值、**不做换算**：`-1` 原样返回 `-1`，前端自行判断是否启用空闲登出。
- **三个天数字段同源**：`idleLogoutMinutes`、`user.passwordValidDays`、`user.accountValidDays` 一起来自**同一条策略记录**（`policyId` 那条）—— 分别取策略的 `idleLogoutMinutes` / `passwdValidDays` / `accountValidDays`，`-1` 一律原样透出。
- 策略按用户身上的 `policyId` 查（§4.3 策略必挂）；查不到时**登录在校验 4 就直接报错**（§9.2），走不到这里 —— 所以**登录返回的 `user` 里 `passwordValidDays` / `accountValidDays` 一定非 `null`**，区别于通用 `UserDto`「策略缺失时出 `null`」的容错口径（§5.3.1，那种容错只用于列表 / 详情查询）。

> **`FIRST_LOGIN` 时 `data` 为空对象 `{}`**，不返回 `LoginDto`、不发 `token` —— 用户此时还没有可用的会话，只能留在登录页完成改密。
>
> **首次改密的鉴权方式（已定，方案 A）**：因为拿不到 `token`，「首次登录改密」**不依赖会话鉴权**，改密接口需**再收一次 `userName` 与 `原密码`**，后端重新查用户、比对哈希通过后才允许改密。这条与用户管理侧的「重置密码」（§5.3.8，管理员操作、无需原密码）**是两回事，不可复用**。改密接口本身见 §9.3。

#### 9.1.5 待补清单（已清零）

> 表结构、码值、`LoginDto` 与 `token` 口径**均已定**，本节**无待补**。登录接口的入参、校验与九步流程见 §9.2，`token` 的生成与携带见 §9.2.1。

### 9.2 登录 `POST /api/v1/auth/login`

**入参 `LoginRo`**

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `userName` | string | **是** | 登录账号，非空 |
| `password` | string | **是** | 登录密码**明文**（后端哈希比对，不落库），非空 |
| `clientIp` | string | 否 | 登录来源 IP，**由入参传入**（服务端不另行取请求头）；写入登录历史的 `loginIp`，为空则落 `NULL` |
| `deviceId` | string | 否 | 设备标识，由前端上报；写入登录历史的 `deviceId`，为空则落 `NULL` |

**出参**

- 进入业务判定后：`success` 恒 `1`、`errMsg` 恒空串（§9.1.3）
- `code = OK` 时 `data` 为 `LoginDto`（§9.1.4）；其余 6 个码 `data` 为空对象 `{}`
- 三类普通报错例外：参数校验失败、账户不存在、绑定策略不存在 —— `success = 0`、`data` 为空对象、`errMsg` 由 i18n 生成

**入参校验**

字段级规则见下表；**执行顺序与命中后的返回见下方「处理流程」步骤 1 ~ 2**，两处一一对应，不另立口径。

| # | 校验项 | 规则 | 不满足 |
|---|---|---|---|
| 1 | `userName` 非空 | `trim` 后非空 | **`success = 0`**，`code = RequireParameterMissing`（参数 `userName`），`errMsg` 由 i18n 生成；**不写登录历史** |
| 2 | `password` 非空 | 原值非空（**不做 `trim`**，沿用 §5.3.8 口径） | **`success = 0`**，`code = RequireParameterMissing`（参数 `password`），`errMsg` 由 i18n 生成；**不写登录历史** |
| 3 | `userName` 存在 | 按 `userName` 查得到用户 | **`success = 0`**，`code = UserNotFound`，`errMsg` 由 i18n 生成；**不写登录历史**，也不落 6 个码 |
| 4 | **绑定策略存在** | 该用户 `policyId` 在 `FabViewerPolicy` 中**查得到** | **`success = 0`**，`code = PolicyNotFound`，`errMsg` 由 i18n 生成；**不写登录历史**，也不落 6 个码 |

- 校验 1、2 是**参数校验**，`code` 都是 `RequireParameterMissing`，只有占位参数不同（`userName` / `password`）。
- 校验 3 **不在** 6 个登录结果码之列：账户不存在按普通失败壳返回（`success = 0`），`code = UserNotFound`，与 §七 E-31 同口径。
- 校验 4 **只判「策略存不存在」**：`policyId` 指向的策略能查到即通过；策略表**没有 `enabled` 状态**（§4.1），所以不存在「策略停用」这一层判断。
- **用户绑定的角色不检查**：`roleIds` 为空、含已删除角色、含已停用角色，**都不影响登录**；登录全程**不查角色表**，角色只在权限判定时用到，与能否登录无关。
- `clientIp`、`deviceId` **完全不校验**：可为空、不校验格式、不校验长度（长度由列宽兜住，超长由 DB 报错）。
- 校验 1 ~ 4 全部通过后，才进入 §9.1.2 的 6 个码判定；此时响应包 `success` 恒 `1`、`errMsg` 恒空。

**处理流程**

按序执行、**前一步不通过即返回**，不再往下走（一次登录只落一条历史、只回一个 `code`）：

| 步 | 动作 | 不通过时 |
|---|---|---|
| 1 | 校验 `userName`、`password` 非空 | **直接抛错**（=「入参校验」第 1、2 条）：`success = 0`，`code = RequireParameterMissing`（参数 `userName` / `password`），`errMsg` 由 i18n 生成；**不查库、不写登录历史** |
| 2 | 按 `userName` 查 `FabViewerUserProfile`；查到后再按其 `policyId` 查 `FabViewerPolicy` | 用户查不到 → **直接抛错**（=「入参校验」第 3 条）；策略查不到 → **直接抛错**（=「入参校验」第 4 条）。两者都是 `success = 0`、`code` 分别取 `UserNotFound` / `PolicyNotFound`、`errMsg` 由 i18n 生成，**不写登录历史** |
| 3 | 判账户是否已生效 | `ACCOUNT_NOT_EFFECTIVE`：写失败历史 → 返回，`success = 1`、`code = ACCOUNT_NOT_EFFECTIVE` |
| 4 | 判 `enabled` | `ACCOUNT_LOCKED`：写失败历史 → 返回，同上 |
| 5 | 判账户是否过期 | `ACCOUNT_EXPIRED`：写失败历史 → 返回，同上 |
| 6 | 哈希比对 `password` 与库中 `PASSWORD` | 见下方「步骤 6 的两种错误」 |
| 7 | 判是否为首次登录 | `FIRST_LOGIN`：写历史（**历史 `success = 0`** + `failCode`）→ 返回，**响应包 `success = 1`**、`code = FIRST_LOGIN`，**不下发 `token`** |
| 8 | 判密码是否过期 | `PASSWORD_EXPIRED`：写失败历史 → 返回，`success = 1`、`code = PASSWORD_EXPIRED` |
| 9 | 全部通过 | 写成功历史；改用户表两个登录字段；生成 `token`；返回 `LoginDto` |

**各步判定条件**

| 步 | 对应码 | 判定 |
|---|---|---|
| 3 | `ACCOUNT_NOT_EFFECTIVE` | `accountActiveAt` **为空** 或 **按日晚于当前日期**（`TRUNC(accountActiveAt) > TRUNC(now())`） |
| 4 | `ACCOUNT_LOCKED` | `enabled = 0` |
| 5 | `ACCOUNT_EXPIRED` | `accountExpiresAt` **非空** 且 **按日早于当前日期**（`TRUNC(accountExpiresAt) < TRUNC(now())`） |
| 7 | `FIRST_LOGIN` | `passwordChangedAt` **为空** |
| 8 | `PASSWORD_EXPIRED` | `passwordExpiresAt` **非空** 且 **按日早于当前日期**（`TRUNC(passwordExpiresAt) < TRUNC(now())`） |

> **三处时间判定一律按「日」比较，不比较时分秒**：生效日晚于今天才算未生效；过期日早于今天才算过期 —— **到期当天仍有效，次日才失效**。同一账号在今天任何时刻登录，判定结果都相同。

**步骤 6 的两种错误**

| 返回 | 处置 |
|---|---|
| `ErrMismatchedHashAndPassword`（密码不匹配） | 视为业务失败：读 `AUTH_FAILED` 的 i18n 文案，写失败历史，`success = 1`、`code = AUTH_FAILED` |
| **其他任何错误** | **不当作登录失败**：直接抛错，`success = 0`、`code` 取框架内部错误码；**不写登录历史**（不是「密码错」，是哈希组件本身出问题） |

**步骤 3 ~ 8 命中后的共同动作**

- **写一条登录未成功的历史**（6 个码的历史 `success` 一律记 `0`，含 `FIRST_LOGIN`），列值见下表
- **不修改用户表的两个登录字段**（`lastLoginTime`、`lastLoginIp`）—— 只有步骤 9 才写
- 响应包 `success = 1`、`errMsg` 为空串、`data` 为空对象 `{}`

**步骤 9 的动作**

1. 写一条成功登录历史（`success = 1`，`failCode` / `failMessage` 为空）
2. 用 Modify Attribute 的 TXN 改 `FabViewerUserProfile` 两列：`lastLoginTime = now()`、`lastLoginIp = 入参 clientIp`（入参为空则写 `NULL`）
3. 生成 `token`：调**库的读取配置文件方法**取 `jwt.ttl`，按 §9.2.1 规则换算成过期小时数（空则不传），连同**登录成功的 `userName`** 一起传给**库的生成 token 方法**
4. 用**步骤 2 已查到的策略**＋**步骤 2 改完两个登录字段后的 `user` 对象**，组 `LoginDto{token, idleLogoutMinutes, user}` 返回（§9.1.4）；**策略不重复查**，用户对象也不再回查

**登录历史 `FabViewerLoginHist` 的列值来源**

| 场景 | `userName` | `loginTime` | `loginIp` | `success` | `failCode` | `deviceId` | `failMessage` |
|---|---|---|---|---|---|---|---|
| 步骤 1 / 2 失败 | **不写记录** | — | — | — | — | — | — |
| 步骤 3 ~ 6、8 失败 | 入参 `userName` | `now()` | 入参 `clientIp` | `0` | 对应码 | 入参 `deviceId` | 该码的 i18n 译文 |
| 步骤 7（`FIRST_LOGIN`） | 入参 `userName` | `now()` | 入参 `clientIp` | **`0`** | `FIRST_LOGIN` | 入参 `deviceId` | 该码的 i18n 译文 |
| 步骤 9 成功 | 入参 `userName` | `now()` | 入参 `clientIp` | `1` | `NULL` | 入参 `deviceId` | `NULL` |

- `loginTime` **取服务端 `now()`**，不取前端时间。
- `loginIp` / `deviceId` 入参为空时落 `NULL`（两字段均不校验，§9.2 入参校验）。
- 失败码的 `failMessage` 一律从 i18n 取当次语言的译文落库，不硬编码（§9.1.2）。

#### 9.2.1 会话令牌 `token`

**生成方式**

| 项 | 口径 |
|---|---|
| 生成组件 | **库提供的「生成 token」方法**，本模块**只调用、不实现**：不碰签名算法、不持有密钥、不做编码 |
| 调用时机 | **登录成功后调用一次**（§9.2 步骤 9）；6 个失败码（含 `FIRST_LOGIN`）**一律不调** |
| 入参 ① `userName` | **登录成功的那个 `userName`** —— 即本次通过校验的 `LoginRo.userName`；不取昵称、不取登录历史、不取其他来源 |
| 入参 ② 过期小时数 | 由 yml 的 `jwt.ttl` 换算后传入，规则见下；**配置为空时该参数不传**（留空，由库用默认 1 小时） |
| 出参 | token 字符串，原样放进 `LoginDto.token`（§9.1.4），不做二次包装 |
| 过期时刻 / 载荷 | **均由库按入参算与封装**；本模块**不传时间、不自己算过期时刻、不约定载荷字段**，也不往里塞角色 / 权限 |

**`jwt.ttl` 怎么读、怎么传**

**读取**

- 读取方式：调**库提供的「读取配置文件」方法**取值 —— 本模块**不自己解析 yml、不硬编码配置路径**。
- 配置位置：本服务 yml 中 **`jwt` 节下的 `ttl`**（即 `jwt.ttl`）。

**换算成传给生成方法的过期小时数**

| yml `jwt.ttl` | 传给生成方法的参数 | 实际有效期 | 说明 |
|---|---|---|---|
| **空**（未配置 / 空串 / 只有空白） | **不传（空）** | **1 小时** | 用库内默认值，本模块**不补 `1`、不自己兜底** |
| 可解析为 int，且 **`1 ≤ 值 ≤ 24`** | 传该值 | 该小时数 | 常态区间，原样传 |
| 可解析为 int，且 **值 > 24** | 传 **24** | 24 小时 | 上限封顶 |
| 可解析为 int，但 **值 ≤ 0**（`0` / 负数） | **原值传**（`0` 传 `0`、`-3` 传 `-3`） | **24 小时** | 本模块**不拦、不改、不兜底**；由**库的生成 token 方法**在收到 `≤ 0` 时兜底 24 小时 |
| **无法解析为 int**（如 `abc`、`1.5`、`2h`、`24h`） | 传 **24** | 24 小时 | 配错时保证「最长有效」而不是「配错即失效」 |

- 判断顺序固定：**先判空 → 再解析 int → 再判是否 > 24**；空值**不参与解析**，也不套 24。
- 分工要说清：**`1 ~ 24` 原值传**；**`> 24` 与「无法解析」由本模块改写成 24**；**`≤ 0` 原值照传、本模块不兜底，由库按 24 小时签发** —— 三种异常最终都落在 24 小时这一档，但动手的人不同。
- 改了 `jwt.ttl` **只影响之后签发的 token**；已签发的 token 过期时刻已写在 token 里，不回溯。

**状态与生命周期**

- **无状态**：服务端**不存会话** —— 不落库、不写 Redis、不放内存。token 自身即凭证，每次请求由**库**验签还原身份。
- **不续期、不刷新**：本模块**不提供刷新 / 续签接口**，也不在业务请求里延长 token 的过期时间。到点即失效，用户重新登录换新 token。
- **签发时机**：登录流程**步骤 9**（§9.2）才签发；其余 6 个码（含 `FIRST_LOGIN`）**一律不签发**。

**服务启动时接入 token 验证**

- **注册时机**：**服务启动时一次性注册**（初始化阶段挂上库的拦截器 / 过滤器），不是每个请求里临时判断，也不在业务代码里逐个接口手写校验。
- **验证范围**：**除白名单外，其余接口全部按库的设定接入 token 验证** —— 验签逻辑、未带 token / 验签失败 / 已过期的返回口径，**一律用库的统一实现**，本模块**不自定义**返回码、不自己写拦截处理。
- **白名单构成**：三个 auth 接口（登录 / 登出 / 改密）+ **6 个查询类 `GET` 接口**（`GET` 只放行查询用的，**取权限那个 `GET` 不放行**）。
- **白名单按路径匹配**：命中即放行、不进验签；白名单只放接口路径，**不按用户 / 角色放**。

| 接口 | 是否免 token 验证 | 依据 |
|---|---|---|
| `POST /api/v1/auth/login` | **免**（白名单） | 登录时还没有 token（§9.2） |
| `POST /api/v1/auth/logout` | **免**（白名单） | 空接口，登出后本就无 token 可用（§9.5） |
| `POST /api/v1/auth/change_password` | **免**（白名单） | 首次登录改密时还没有 token（§9.3） |
| **6 个查询类 `GET` 接口** | **免**（白名单） | `GET /api/v1/roles/page`、`GET /api/v1/roles/name/list`、`GET /api/v1/login_policy/list`、`GET /api/v1/login_policy/name/list`、`GET /api/v1/login_policy/detail`、`GET /api/v1/users/page` —— 本模块 GET 共 7 个，**除下面这一个全部免** |
| **`GET /api/v1/auth/permissions`** | **必须带 token** | 虽为 `GET`，但**不进白名单**：它是「按账号查该账号的权限」，属数据查询而非公共信息，要求调用方已有登录身份（§9.4） |
| 其余接口（上述之外的全部） | **必须带 token** | 角色 / 策略 / 用户的全部写操作（新建 / 修改 / 删除 / 配权限 / 启停 / 重置密码 / 更新属性 / 延期 / 保存）+ `GET /api/v1/auth/permissions` —— 统一走库的验证 |

- 除白名单外的接口，token 缺失或无效时由**库统一拦截**，业务代码不感知、也不重复判 token。

**前端携带方式**

| 项 | 口径 |
|---|---|
| 位置 | 请求 header：**`Authorization: Bearer <token>`** |
| 取值 | 后端只从该 header 取 token，**不从 query、cookie、请求体取** |
| 例外 | **白名单接口不带 token**：三个 auth 接口（登录 §9.2、登出 §9.5、改密 §9.3）+ **6 个查询类 `GET`**（各分页 / 列表 / 详情）。`GET /api/v1/auth/permissions` **不在例外内**，必须带 token（§9.4） |

**与策略 `idleLogoutMinutes` 无关**

| 项 | 口径 |
|---|---|
| token 有效期 | 只由 yml 的 `jwt.ttl` 换算决定（空 → 1 小时；非法 / > 24 / ≤ 0 → 24 小时），与该用户所挂策略的 `idleLogoutMinutes` **完全无关**；策略改大改小都不影响已签发的 token |
| 服务端空闲计时 | **不做**。后端不记录「最后一次操作时间」，不因空闲提前作废 token，也没有「活跃即续期」 |
| `LoginDto.idleLogoutMinutes` | 仍随登录成功结果**原样透传**（`-1` 不折算，§9.1.4），供**前端**做自己的空闲登出判定；后端不参与该判定 |

> 一句话：**token 只按 `jwt.ttl` 换算出的小时数硬过期（空 → 1 小时，非法或超 24 → 24 小时），期间有没有操作都一样**；空闲登出是前端的事，与后端 token 生命周期两条线。

**两条已定**

| # | 事项 | 结论 |
|---|---|---|
| 1 | `jwt.ttl` 配成 `0` 或负数 | **按原值传**（`0` 传 `0`、负数传负数），本模块**不拦不改**；**兜底由库的生成 token 方法承担** —— 收到 `≤ 0` 一律按 24 小时签发 |
| 2 | `GET` 接口是否免 token 验证 | **除 `/auth/permissions` 外全免**：6 个查询类 `GET` 与三个 auth 接口一起留白名单；**`GET /api/v1/auth/permissions` 移出白名单、要求带 token**，与全部写操作一起走库的验证 |

#### 9.2.2 会话与登录策略（明确不做）

| # | 事项 | 口径 | 说明 |
|---|---|---|---|
| 1 | **并发登录** | **不限制** | 同一账号可在多个终端同时登录，各自持有独立 token、**互不踢下线**；每次登录都按 §9.2 步骤 9 各写一条成功历史、各签一个 token |
| 2 | **登录失败次数** | **不限制、不锁号** | 密码错只落一条 `AUTH_FAILED` 失败历史，**不累计次数、不触发锁定、不因连续失败改 `enabled`**；`ACCOUNT_LOCKED` 只表达「管理员把 `enabled` 置 0」（§5.4.3），与失败次数无关 |
| 3 | **设备 / 来源绑定** | **不绑定** | token 载荷只装 `userName`（时间信息由库加），**不带也不校验** `deviceId` / `clientIp`；换设备、换 IP 带同一个未过期 token 仍放行。这两个字段**只作 `FabViewerLoginHist` 的记录** |

- 三条的共同前提：**服务端无会话存储**（§9.2.1），没有「在线用户表」可以用来踢人、计数、绑定设备。
- 账号安全只由**管理员的显式动作**承担：停用走 §5.3.11、延期走 §5.3.12、重置密码走 §5.3.8 —— **不引入自动锁定、不引入失败计数列**。
- 失败历史（`FabViewerLoginHist`）的用途是**事后排查**：谁在什么时候、从哪个 IP / 设备、以什么失败码试过；**不参与任何自动判定**。


### 9.3 修改密码 `POST /api/v1/auth/change_password`

**用途与鉴权**

- 用户**自己**改密码，两条路径共用这一个接口：① 首次登录被 `FIRST_LOGIN` 拦下后的改密；② 已登录用户的常规改密。
- **不依赖 `token`**：首次登录时还没有 token（§9.1.4 方案 A），身份由入参 `userName` + `oldPassword` 当场验证。前端**不必**带 `Authorization`。
- 与管理员侧的「重置密码」（§5.3.8）**是两个接口**：重置不要旧密码、并把两个密码时间列清 `NULL`；本接口要旧密码、并把两个时间列写上值。

**入参 `ChangePasswordRo`**

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `userName` | string | **是** | 登录账号，`trim` 后非空 |
| `oldPassword` | string | **是** | 旧密码**明文**，**不做 `trim`**（首尾空格是密码的一部分，与登录同口径） |
| `newPassword` | string | **是** | 新密码**明文**，**不做 `trim`**；落库前哈希，任何返回都不带出 |

**出参**

- `data` 为**空对象 `{}`**（不回 `null`）
- 成功：`success = 1`、`code = OK`
- 失败：全部走**普通失败壳** —— `success = 0`、`code` 取 §7.1 / §7.6 对应业务码、`errMsg` 由 i18n 生成
- **本接口不写登录历史**：`FabViewerLoginHist` 只记登录尝试，改密不是登录

**处理流程**（按序执行、命中即返回）

| 步 | 动作 | 不通过时的含义 |
|---|---|---|
| 1 | 三个入参非空 | `RequireParameterMissing`（参数 `userName` / `oldPassword` / `newPassword`） |
| 2 | 按 `userName` 查 `FabViewerUserProfile` | `UserNotFound` |
| 3 | 判 `enabled` 是否为 `true`（`= 1`） | `AccountDisabled` |
| 4 | 按该用户 `policyId` 查 `FabViewerPolicy` | `PolicyNotFound` |
| 5 | 旧密码与库中 `PASSWORD` **哈希比对**（与登录同一方法，§9.2 步骤 6） | `OldPasswordIncorrect` |
| 6 | 按策略的 6 项要求校验 `newPassword` | `PasswordTooShort` / `PasswordTooLong` / `PasswordNeedDigit` / `PasswordNeedLowerChar` / `PasswordNeedUpperChar` / `PasswordNeedSpecialChar`（按序命中第一个） |
| 7 | 落库（见下） | — |

- 步骤 3 只看 `enabled`，**不复用登录的 `ACCOUNT_LOCKED` 码** —— 那是登录结果码（响应包 `success` 恒 `1`），本接口走普通失败壳。
- 步骤 5 的哈希比对**与登录完全同一套方法**；若返回的是「哈希组件本身出错」（不是密码不匹配），按内部错误抛，不当成「旧密码错」（同 §9.2 步骤 6 的两种错误）。
- 步骤 6 的明细见下。

**步骤 6：按策略校验新密码**

| 序 | 项 | 规则 |
|---|---|---|
| 1 | 最小长度 | `newPassword` 长度 **≥** 策略 `passwdMinLength` |
| 2 | 最大长度 | 长度 **≤** 策略 `passwdMaxLength` |
| 3 | 数字 | 策略 `passwdRequireDigit = 1` → 至少 1 个数字；`= 0` 不校验 |
| 4 | 小写字母 | `passwdRequireLowerChar = 1` → 至少 1 个小写字母 |
| 5 | 大写字母 | `passwdRequireUpperChar = 1` → 至少 1 个大写字母 |
| 6 | 特殊字符 | `passwdRequireSpecialChar = 1` → 至少 1 个字符属于策略 `passwdSpecials` 列出的集合 |

- 长度按**字符数**算（`len([]rune)`），**不按字节** —— 与列宽的字节口径（§1.2）不是一回事。
- 按上表顺序**逐条判、命中即返回**；`errMsg` 指向具体是哪一项不满足（i18n 按项分别维护文案）。
- 策略这 6 项在策略侧已有取值约束（`passwdMinLength ≥ 6`、`passwdMaxLength ≥ 18` 且大于最小长度、特殊字符开关打开时 `passwdSpecials` 非空，§4.2），所以这里拿到的区间一定有效。

**步骤 7：落库**

写入方式：**Modify Attribute 的 TXN**，只写三列。

| 列 | 取值 |
|---|---|
| `PASSWORD` | `newPassword` 明文 → **框架提供的哈希方法**加密后覆盖（与新建 / 重置同一套，§5.3.5） |
| `PASSWORDCHANGEDAT` | **当前时间 `now()`** |
| `PASSWORDEXPIRESAT` | 策略 `passwdValidDays = -1` → **`NULL`**（永不过期）；`= N` → **`TRUNC(now()) + N 天`**，时分秒 `000000`（日期类字段口径，§1.9） |
| 其余列 | **一律不动**：`ENABLED`、`ACCOUNTACTIVEAT`、`ACCOUNTEXPIRESAT`、`roleIds`、`policyId`、`lastLoginTime` / `lastLoginIp` |

- 落库后 `passwordChangedAt` 有值 → 该用户**不再被判 `FIRST_LOGIN`**；`passwordExpiresAt` 已按策略重算 → **不再被判 `PASSWORD_EXPIRED`**（这两个判定都在下次登录时做，§9.1.2）。

**本接口不校验的**

| 项 | 说明 |
|---|---|
| 账户是否生效 / 过期 | `accountActiveAt`、`accountExpiresAt` **不判**，只看 `enabled` |
| 密码是否已过期 | `passwordExpiresAt` **不判** —— 过期了来改密正是这条路的用法 |
| 角色 | **不查角色表**；`roleIds` 为空或含已删 / 已停用角色都不影响 |
| 新旧密码是否相同 | **不限制** —— 策略里没有「不能与旧密码相同」这一项，本接口也不额外加 |
| `token` | **不校验、不需要**（见上「用途与鉴权」） |

**改密后旧 `token` 仍可用**：token 无状态、服务端无会话表（§9.2.1），所以**改密不会让已签发的 token 失效** —— 旧 token 在到期前（默认 1 小时）仍能通过验签。要立刻断掉旧会话，只能等它自然过期，或由管理员停用账号（§5.3.11）。


### 9.4 获取权限 `GET /api/v1/auth/permissions`

**用途**：按用户名取该用户的全部权限码，供前端做菜单 / 按钮级控制。

**鉴权**

- **本接口需要鉴权**：请求必须带 **`Authorization: Bearer <token>`**，由**库**在服务启动时注册的拦截器统一验签（§9.2.1）—— 本接口**不在白名单**。
- 未带 token / 验签失败 / token 已过期：由**库统一拦截**并返回库的既定口径，**不进本接口业务逻辑**、不返回权限数组。
- 返回谁的权限仍由 query 的 `username` 决定；但**调用方必须是已登录身份** —— 换个 `username` 就能查别人权限的前提不再成立，因为拿不到有效 token 就进不来。
- 与登录（§9.2）、改密（§9.3）、登出（§9.5）不同：那三个在白名单里，**本接口不在**。

**入参（query 参数）**

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `username` | string | **是**（允许为空） | 用户名。**参数名全小写 `username`**，与出参里的 `userName` 大小写不同，实现时按 query 原样取，不要转成驼峰再取 |

**出参**

`data` 为**字符串数组**。三种「取不到」的情况**正常返回空数组**、不报错；唯一会报错的是角色 `permissions` 脏数据（步骤 4）：

- **正常返回**：`success = 1`、`code = OK`、`errMsg` 空
  - `data = []`：入参为空 / 用户未配置 / 无启用角色
  - `data = ["...", "..."]`：合并去重排序后的权限码
- **报错**：`success = 0`、`code = RolePermissionDataInvalid`、`errMsg` 由 i18n 生成（仅步骤 4 解析失败）

**处理流程**（按序执行、命中即返回空数组）

| 步 | 判断 | 结果 | 日志要素 |
|---|---|---|---|
| 1 | `username` 为空（`trim` 后空串） | `data = []` | **输入用户名为空** |
| 2 | 按 `username` 查 `FabViewerUserProfile`，查不到 | `data = []` | **用户未配置**（带 `username`） |
| 3 | 取 `roleIds` 的全部角色（一次批量查），过滤出 `enabled = 1` 的 | 过滤后为空 → `data = []` | **用户无角色**（带 `username`） |
| 4 | 取每个角色的 `permissions`，合并 → 去重 → 按字符升序 | 返回数组；**任一角色的 `permissions` 解析不了（非法 JSON）→ 整体报错** | 正常不记；解析失败记 `username` + 出错角色 `roleId` |

- 步骤 1 只判「传没传」，**不校验用户是否存在**；用户名不存在走步骤 2。
- 步骤 3 起**才查角色**；`roleIds` 为空、角色已被删除、角色全部停用，都归到「无启用角色」这一种结果。
- 三步异常都是**同一套壳**：`success = 1`、`code = OK`、`errMsg` 空、`data = []` —— 前端只看数组是否为空。

**用户状态不影响本接口**

- 流程里**没有判账号状态这一步**：不判 `enabled`、不判 `accountActiveAt` / `accountExpiresAt`。
- 所以**用户停用（`enabled = 0`）也照常返回其角色权限** —— 停用的效果是「登不进去」（登录侧判 `ACCOUNT_LOCKED`，§9.1.2），不是「权限消失」。
- 同理，账户已过期、尚未生效的用户，本接口也照常返回权限。

**步骤 4 解析失败的处理**

| 项 | 口径 |
|---|---|
| 触发 | 任一**被保留**角色的 `permissions` 不是合法 JSON 数组字符串（脏数据） |
| 处理 | **整体报错** —— `success = 0`、`code = RolePermissionDataInvalid`、`errMsg` 由 i18n 生成；**不跳过、不降级成空数组** |
| 日志 | 记 `username` + 出错角色的 `roleId`（便于定位是哪一行脏数据） |
| 为什么 | 静默跳过会让前端拿到「少一段权限」的结果却毫无察觉；权限少了比报错更难查 |

**步骤 3 的过滤口径**

| 情况 | 处理 |
|---|---|
| `roleIds` 为空数组 | 过滤结果为空 → 返回 `[]` |
| `roleIds` 指向的角色**已被删除** | 查询结果里没有该行，**跳过**，不报错 |
| 角色存在但 `enabled = 0` | 过滤掉 |
| 角色存在且 `enabled = 1` | 保留，参与步骤 4 |

**步骤 4 的合并口径**

| 项 | 口径 |
|---|---|
| 来源 | 每个保留角色的 `permissions` 列（库里存 JSON 数组字符串，§2.1） |
| 合并 | 所有保留角色的权限码放进同一个集合 |
| 去重 | 同一权限码出现在多个角色里只保留一个 |
| 排序 | 按**字符升序**（区分大小写的字典序）—— 保证同一份数据每次返回的顺序一致 |
| 空权限 | 某角色 `permissions` 为空或 `[]` → 不贡献元素，不影响其余角色 |

**日志**：步骤 1 ~ 3 各打一条，要素必须含 **`username`** 与**原因**（输入用户名为空 / 用户未配置 / 用户无角色）。日志级别、输出目标按框架日志规范，本模块不另定（同 §5.3.11）。


### 9.5 登出 `POST /api/v1/auth/logout`

**现状：占位空接口**

- 本节**只定「路径 + 返回壳」**，**不定义任何业务逻辑**；实现上就是一个直接返回成功的空方法。
- 用途**尚未确定** —— 需求方暂时没有明确这个接口要做什么，先把这个 URL 占住，避免前端后续改动路径。

**入参**：无。前端可以带 `Authorization`，但**本接口不读、不校验**。

**出参**：`data` 为空对象 `{}`；`success = 1`、`code = OK`、`errMsg` 空。

**明确不做**

| 项 | 说明 |
|---|---|
| 让 `token` 失效 | **不做**（本期已确认）。token 无状态、服务端无会话表（§9.2.1），没有可注销的会话；调完登出，旧 token 在到期前（默认 1 小时）**照样能用** |
| 删会话 / 清缓存 | **不做** —— 服务端本来就没有会话存储可删 |
| 写登录历史 | **不写** —— `FabViewerLoginHist` 只记登录尝试 |
| 改用户表 | **不改**：`lastLoginTime` / `lastLoginIp` 保持上次登录的值 |
| 鉴权 | **不校验 `token`**：未登录状态调用也照常返回成功 |

> 目前前端「登出」实际只做一件事：**把本地存的 token 丢掉**。这个接口留着是给将来可能的变化预留位置（例如引入 token 黑名单、强制单点登出），到真要做事时再回来补本节，现在**不要往里面加逻辑**。

### 9.6 认证验收规则

> 验收方式与角色 / 策略 / 用户一致：接口级，既看响应包（`success` / `code` / `errMsg` / `data`），也回查库中实际值（`FabViewerUserProfile`、`FabViewerLoginHist`）。编号 **A-01 ~ A-92**，按接口顺序排列（登录 → 改密 → 获取权限 → 登出）；每个接口先验「成功路径」，再验「拒绝路径」，拒绝路径需同时确认**库中未被改动**。

### 10.2 登录结果码（6 个）

| # | code | 中文 message | English message | 参数 |
|---|---|---|---|---|
| 1 | `ACCOUNT_NOT_EFFECTIVE` | 账户尚未生效 | Account is not effective yet | 无 |
| 2 | `ACCOUNT_LOCKED` | 账户已停用 | Account is disabled | 无 |
| 3 | `ACCOUNT_EXPIRED` | 账户已过期 | Account has expired | 无 |
| 4 | `AUTH_FAILED` | 用户名或密码错误 | Incorrect username or password | 无 |

- 这 6 个的响应包 `errMsg` **留空串**（§9.1.3），文案由前端按同一 i18n 键自行取；只有写入历史表的 `failMessage` 才落译文。
- `ACCOUNT_LOCKED`（登录结果码）与 `AccountDisabled`（改密业务码）中文都叫「账户已停用」，但**分属两条通道**：前者 `success = 1`、只用于登录结果；后者 `success = 0`、只用于改密报错。不要互相替代。

### 10.3 约定

| 项 | 口径 |
|---|---|
| 键名 | **i18n 键就是 code 字面值**，不加前缀、不做大小写转换 |
| 语言 | 每个 code **中英各一条**，缺一不允许上线 |
| 占位符 | 统一写成 `[{0}]`、`[{1}]`，按 §10.1「参数」列的顺序填；无参数的不带占位 |
| 业务码 `errMsg` | 由后端按当前语言取译文填入 `errMsg`，前端直接展示 |
| 登录结果码 `errMsg` | **留空**，前端按 `code` 自行取译文（§9.1.3） |
| 命名风格 | 业务码 **PascalCase**；登录结果码 **大写下划线**。两套并存，**新码按所属通道选风格**，不混用 |
| 新增码 | 同一批改动里必须同时补：§七 报错点、§10.1 / §10.2 中英两条、对应接口正文 |
| 不在本表的情况 | **服务端内部错误**（哈希组件异常、DB 不可用、Redis 不可用等）**不走本表**，由框架统一按内部错误处理（§1.4：这类才允许 5xx），业务代码不自定义码 |
